Break-and-Fix Labs — Learn Like On-Call Work

Phase 2 · The Rest of DevOps

What this is and why it matters

These labs teach you fixing: each one breaks something on purpose, so you practise finding the cause.

Think of a driving test where the teacher quietly lets one tyre down. You learn to notice the wobble, find the flat tyre, and fix it — instead of only reading about flat tyres.

In real work, fixing is the job itself. A broken system stays broken until someone reads the symptom and finds the cause.

  • A symptom is what you can see: an error message, a blank page, a container that stopped.
  • A cause is the real reason behind it: a wrong name, a missing file, a missing door.
  • On-call work means being the person who fixes things when they break, even outside normal hours. The order is always the same: symptom, logs, cause, fix.
  • Logs are the lines of text a program prints while it runs.

Each lab follows the same order: break it, read the symptom, find the cause, fix it. Do not read the fix first.

Try to find the cause with the commands you know, then check the fix.

Practice labs — Docker, Git and ports
These labs are extra practice, not one topic’s ladder. Six small breaks to fix: a wrong image name, a container that dies, a missing test file, a merge conflict, a closed port, a wrong Dockerfile. They practise Docker, Git and ports — the same skills the Docker, Linux and on-call ladders teach.

Test status

Syntax-checked only. The labs were NOT run end-to-end on a clean machine yet. Nothing in this lesson promises a step works on a real machine. Where a step is unverified, this lesson says so.

What you need first

  • Docker running (from zero-cost-lab.md).
  • Git installed (from zero-cost-lab.md Step 2).
  • A GitHub account (from zero-cost-lab.md Step 7), for Lab 3 only.
  • A working folder: ~/devops-practice.
  • ~/devops-practice is a learner-created folder. You made it in zero-cost-lab.md Step 6. It does NOT come with the kit.
  • Labs 4 and 6 make their own folders inside it (see each lab).
  • Labs 1, 2, and 5 can run from any folder, because they only use Docker commands. Lab 3 needs a repository folder on GitHub (see Lab 3 setup).
  • Clean up at the end of each lab. Stopped and running containers are left behind if you skip clean-up, and the next lab may fail with "port is already allocated" because door 8080 is still taken. Each lab below ends with its clean-up commands.

Words you will see in every lab

  • Image — a saved, ready-to-run copy of an app.
  • Tag — the version label after the colon in an image name, for example 1.0 in my-site:1.0.
  • Daemon — the background program that does Docker's work for you. When an error says "Error response from daemon", it means Docker's background program is the one reporting the problem.
  • Port — a numbered door for network traffic.
  • localhost — this machine. Your own computer.
  • PATH — the list of folders the computer searches when you run a command by name. If a program is not in any of those folders, the computer says "executable file not found in $PATH".
  • Foreground program — the main program a container runs. A container lives only as long as its main program runs. When the main program ends, the container stops.

Lab 1 — The container that will not start

What is this?

  • A container that will not start because the image name is wrong.
  • Think of ordering a pizza called "pizzza" from a shop that has no such pizza. The shop says "we do not have that". Docker does the same.

Break it

  • WHAT we are doing: trying to start a container from an image that does not exist.
  • WHY: so you see the exact error Docker gives for a wrong image name, and learn to read it.
Try it Yourself »Open the practice terminal and run it yourself — nothing installs. Included with Phase 2. Simulation — practice version. Run the real lab with Docker to do it for real.
Command
docker run -d --name broken-web nginxg
  • Word by word: docker run (start a container) + -d (run in the background) + --name broken-web (call it broken-web) + nginxg (the image name — nginxg is a typing mistake on purpose. The real image is called nginx. There is no image called nginxg.)
  • -d means detached: run in the background, so your terminal stays free.

Symptom

  • Docker prints an error and no container runs.
  • You should see an error like:
Command
Unable to find image 'nginxg:latest' locally
docker: Error response from daemon: pull access denied for nginxg, repository does not exist or may require 'docker login'.
  • How to read it, line by line:
  • Unable to find image 'nginxg:latest' locally: Docker looked on your machine for an image called nginxg, version latest, and did not find it. latest is the default tag. When you write no tag, Docker reads it as latest.
  • Error response from daemon: Docker's background program is reporting the problem.
  • pull access denied for nginxg: Docker tried to download (pull) the image from the internet and was refused.
  • repository does not exist: a repository here means the named image on Docker Hub. Docker Hub is the public place where ready-made images live. There is no image called nginxg there.
  • or may require 'docker login': Docker adds this guess because the same error can also mean "this image is private, sign in first". Here the image simply does not exist. You do not need to sign in.

Find it

Command
docker ps -a
  • WHAT: list all containers, including stopped ones.
  • WHY: to prove no broken-web container was made.
  • Word by word: docker ps (list running containers) + -a (all — include stopped ones too).
  • You should see: no broken-web container in the list.
  • The error message says the image could not be found. Docker could not download something that does not exist.

Fix it

Command
docker run -d --name working-web nginx
docker ps
  • Line 1: docker run -d --name working-web nginx.
  • WHAT: start a container from the real image nginx, and call it working-web.
  • WHY: the only mistake was the image name. The real name fixes it.
  • Line 2: docker ps.
  • WHAT: list running containers.
  • WHY: to see working-web running.
  • You should see: working-web in the list with STATUS "Up".
  • Up means running.
  • The container runs.
  • Lesson: when a container will not start, read Docker's error and check the image name and tag first.
  • Two extra checks you can use: docker image ls (list the images on your machine — ls means list), or try docker pull IMAGE:TAG (download one image by name and tag, to test whether it exists).
  • Use docker logs only when a container actually exists and printed output. For an image that was never pulled, there is no container to read logs from. docker logs means "show what this container printed".

Second version (try this yourself)

  • First, check what is using door 8080. Run docker ps and look at the PORTS column. If working-web is running without a -p door mapping, it uses no door on your machine, so this second version will NOT clash. The clash below only happens if another container already uses door 8080 — for example the my-site container from zero-cost-lab.md Step 4, if it is still running.
Command
docker run -d --name second-web -p 8080:80 nginx
  • Word by word: docker run (start a container) + -d (background) + --name second-web (call it second-web) + -p 8080:80 (connect door 8080 on your machine to door 80 in the container) + nginx (the web server program).
  • You should see an error like (only if door 8080 is already taken):
Command
Bind for 0.0.0.0:8080 failed: port is already allocated
  • How to read it: Bind ... failed means "I could not take door 8080". port is already allocated means "door 8080 is already in use by something else". 0.0.0.0 means "all addresses on this machine".
  • If your first web container is still using port 8080, this one fails. Fix: stop the first one (docker stop working-web — but note: if working-web has no -p mapping, it is not the one using the door; stop the container that does use 8080, which you found in docker ps), or use a different port (-p 8081:80 — same box, door 8081 on your machine instead of 8080).

Clean up Lab 1

Command
docker stop working-web second-web
docker rm working-web second-web
  • WHAT: stop both containers, then delete them.
  • WHY: so door 8080 is free for the next lab.
  • Word by word: docker stop (stop) + the two names. docker rm (remove, delete) + the two names. If second-web was never made (because it failed), the stop line will say "no such container" for it. That is fine. Remove the one that exists.

Lab 2 — The container that starts, then dies

What is this?

  • A container that starts, then stops at once, because the command inside it does not exist.
  • Think of a music player told to play a song that is not on the playlist. It has nothing to play, so it stops.

Break it

Command
docker run --name dying-app ubuntu badcommand
  • Word by word: docker run (start a container) + --name dying-app (call it dying-app) + ubuntu (the image: Ubuntu, a version of Linux, as a ready-made box) + badcommand (the command to run inside the box — badcommand does not exist. That is the mistake, on purpose.)
  • Note: there is no -d here. Without -d, the container runs in your terminal, in the foreground, and you see its error directly.

Symptom

  • The container appears, then stops at once.
  • You should see an error like:
Command
exec: "badcommand": executable file not found in $PATH
  • How to read it: exec means "run this program". "badcommand" is the program name. executable file not found in $PATH means "there is no program called badcommand in any folder the computer searches". An executable file is a file the computer can run as a program. $PATH is the list of folders the computer searches.

Find it

Command
docker ps -a
docker logs dying-app
  • Line 1: docker ps -a.
  • WHAT: list all containers, including stopped ones.
  • WHY: a dead container disappears from plain docker ps, but still shows in docker ps -a.
  • Line 2: docker logs dying-app.
  • WHAT: show what the container printed before it stopped.
  • WHY: the printed lines name the problem.
  • You should see: dying-app in the list with STATUS "Exited", and the log shows the error above. Exited means stopped.
  • The command does not exist, so the container had nothing to do and exited. A container lives only as long as its main program runs.

Fix it

Command
docker rm dying-app
docker run -d --name living-app ubuntu sleep 1000
docker ps
  • Line 1: docker rm dying-app.
  • WHAT: delete the dead container.
  • WHY: the name dying-app is taken until you delete it. Also, a dead container only clutters the list.
  • Line 2: docker run -d --name living-app ubuntu sleep 1000.
  • WHAT: start a new container from the ubuntu image, running the command sleep 1000, in the background, called living-app.
  • WHY: sleep 1000 is a program that simply waits for 1000 seconds, doing nothing. 1000 means 1000 seconds, which is about 16 minutes. While it waits, the container stays alive, so you can see STATUS "Up".
  • Word by word: docker run + -d (background) + --name living-app (call it living-app) + ubuntu (the image) + sleep 1000 (the command: wait 1000 seconds).
  • Line 3: docker ps.
  • WHAT: list running containers.
  • WHY: to see living-app with STATUS "Up".
  • You should see: living-app in the list with STATUS "Up".
  • If it breaks: if living-app exits at once too, check the command spelling. sleep 1000 must be typed exactly.
  • sleep 1000 is a process-lifetime demonstration only, not a real fix. Never hide a broken app behind a waiting command.
  • Process-lifetime means "how long the main program runs".
  • The real-app version: run a program that is meant to stay in the foreground, for example docker run -d --name living-web nginx. nginx itself is the foreground program, so the container stays alive doing real work. A container stops when its main program exits.
  • The foreground program is the main program. Foreground means "the one in front, doing the work".

Clean up Lab 2

Command
docker stop living-app
docker rm living-app
  • WHAT: stop the waiting container, then delete it.
  • WHY: sleep 1000 ends after about 16 minutes anyway, but stopping it now keeps your machine tidy and frees the name.

Lab 3 — The pipeline that fails

What is this?

  • A pipeline is an automatic chain of steps, like a factory line.
  • GitHub Actions is GitHub's built-in pipeline tool. It runs steps for you every time you push code to GitHub.
  • Pushing means sending your saved work from your machine to GitHub.
  • This lab breaks a pipeline on purpose: the pipeline is told to run a file that does not exist.
  • Think of a recipe that says "open the blue tin" when there is no blue tin in the cupboard. The cook stops and says "tin not found". The pipeline does the same.

The setup

  • WHAT we are doing: making a folder with a GitHub Actions workflow file in it, and putting that folder on GitHub.
  • WHY: the pipeline only runs on GitHub. It cannot run on your machine alone. You need a repository on GitHub first.
  • A workflow file is a settings file that describes the pipeline steps.
  • A repository is a folder on GitHub that holds your project. People usually say "repo" for short.
  • Do this setup in ~/devops-practice (learner-created, from zero-cost-lab.md Step 6), in a folder for this lab, for example ~/devops-practice/pipeline-lab. Make it first:
Command
mkdir -p ~/devops-practice/pipeline-lab
cd ~/devops-practice/pipeline-lab
  • WHAT: make a folder called pipeline-lab inside ~/devops-practice, and move into it.
  • WHY: all the files for this lab live in one place.
  • Word by word: mkdir -p (make a folder, making missing parents too) + the folder path. cd (move into the folder) + the folder path.
  • Then make the repository on GitHub, exactly as in zero-cost-lab.md Step 7: make a free account, click "New repository", name it, leave it empty (do NOT tick "Add a README file"), create it, and copy the repository address. It looks like https://github.com/<you>/<repo>.git.
  • Then connect this folder to it and push, exactly as in zero-cost-lab.md Step 7 (git init, git add ., git commit -m "first commit", git branch -M main, git remote add origin <your repository address>, git push -u origin main). If you have not done Step 7 yet, do it now. This lab assumes it is done.

The workflow file

  • The file lives at .github/workflows/check.yml in the repository.
  • That path means: inside your repository folder, a folder called .github, inside it a folder called workflows, inside it a file called check.yml.
  • .github starts with a dot. A name that starts with a dot is a hidden folder. Hidden means your file manager does not show it by default, but it is really there. In the terminal, ls -a shows hidden files. ls alone hides them.
  • workflows is GitHub's name for the folder that holds pipeline files.
  • check.yml is the file name. .yml means it is a YAML settings file.
  • Make the folders and the file. From inside ~/devops-practice/pipeline-lab, run:
Command
mkdir -p .github/workflows
cat > .github/workflows/check.yml << 'EOF'
name: check
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run the tests
        run: ./run-tests.sh
EOF
  • Line 1: mkdir -p .github/workflows.
  • WHAT: make the hidden folder .github and the folder workflows inside it.
  • WHY: the workflow file must live at exactly this path, or GitHub will not find it.
  • Lines 2 to 11: cat > .github/workflows/check.yml << 'EOF' … EOF.
  • WHAT: write the lines between the markers into the file .github/workflows/check.yml.
  • WHY: this creates the workflow file.
  • cat > writes the lines that follow into a file until it sees the line EOF. EOF means "end of file". It is just a marker word.
  • Inside the file, line by line:
  • name: check — WHAT: call this pipeline check. WHY: so you can find it by name on GitHub.
  • on: [push] — WHAT: run this pipeline every time someone pushes code. WHY: a push is the trigger. [push] means "on a push".
  • jobs: — WHAT: the list of jobs in this pipeline. WHY: a job is a set of steps that runs on one machine. This pipeline has one job.
  • build: — WHAT: call the job build. WHY: so you can refer to it by name.
  • runs-on: ubuntu-latest — WHAT: run this job on GitHub's newest Ubuntu machine. WHY: the steps need a machine to run on, and GitHub provides one. Ubuntu is a version of Linux.
  • steps: — WHAT: the list of steps in this job. WHY: the steps run one after another.
  • - uses: actions/checkout@v4 — WHAT: use GitHub's ready-made step called checkout, version 4. WHY: it downloads your repository files onto the machine, so the later steps can use them. The - starts one item in the list. actions/checkout@v4 means "the checkout step, version 4, made by GitHub".
  • - name: Run the tests — WHAT: call the next step "Run the tests". WHY: so you can see which step failed, by name, in the log.
  • run: ./run-tests.sh — WHAT: run the file called run-tests.sh in the repository folder. WHY: that file holds the tests. ./ means "in this folder". run-tests.sh is the file name. .sh means it is a shell script file.
  • YAML uses spaces for structure. Never use the Tab key in a .yml file. If a YAML file fails with a strange error, check the spaces first.
  • Push this file to GitHub (git add ., git commit -m "add pipeline", git push). Those three lines are the same short push from zero-cost-lab.md Step 7: stage, save, send.

Break it

  • Do not create run-tests.sh in the repository. Push the code.
  • That is the whole break: the pipeline is told to run a file that does not exist.
  • run-tests.sh must live in the repository folder (~/devops-practice/pipeline-lab), at the top level, next to the .github folder — not inside .github, and not in another folder. That is where ./run-tests.sh looks for it.

Symptom

  • The pipeline runs and fails at the "Run the tests" step.
  • How to see it: on GitHub, open your repository, click the "Actions" tab at the top. The Actions tab lists every pipeline run. The newest run is at the top. A failed run shows a red X. A passing run shows a green tick. Click the failed run, then click the job called build, then click the step called "Run the tests". Its log is the list of lines that step printed.
  • The log says the file was not found. The pipeline did exactly what it was told. It tried to run a file that does not exist.
  • How long to wait: a run usually starts within a minute of the push and finishes in under two minutes. If the Actions tab shows no run after two minutes, check that the push really went through (git push printed no error) and that the file is at .github/workflows/check.yml exactly.

Find it

  • Open the failed run on GitHub and read its log.
  • The log says the file was not found.
  • The pipeline did exactly what it was told. It tried to run a file that does not exist.

Fix it

  • Write a real run-tests.sh file — one that checks something true about the project — and push it.
  • For a static site, this is enough to start. A static site is a website made of plain files, with no program running behind it.
  • First, you need an index.html in the repository folder, because the tests below check it. If you do not have one yet, make it:
Command
cat > index.html << 'EOF'
<h1>My DevOps practice site</h1>
EOF
  • WHAT: write a tiny web page file called index.html with one heading.
  • WHY: the tests below check this file, so it must exist first.
  • Then make the test file, in the same folder (~/devops-practice/pipeline-lab):
Command
#!/bin/bash
test -f index.html
grep -q "My DevOps practice site" index.html
  • HOW to write it: cat > run-tests.sh << 'EOF', then the three lines above, then EOF on its own line.
  • Inside the file, line by line:
  • #!/bin/bash — WHAT: the first line says "run this file with Bash". WHY: Bash is the command language. Without this line, the computer would not know which language the file is written in. Type it exactly as shown.
  • test -f index.html — WHAT: check that a file called index.html exists. WHY: if the file is missing, the test fails, and you want to know that. Word by word: test (check something) + -f (a file exists) + index.html (the file name).
  • grep -q "My DevOps practice site" index.html — WHAT: check that the file index.html holds the words "My DevOps practice site". WHY: if someone deletes the heading, the test fails, and you want to know that. Word by word: grep (search inside a file) + -q (quiet — print nothing, only say yes or no by passing or failing) + "My DevOps practice site" (the words to look for) + index.html (the file to search in).
  • Make it runnable, then push again, and watch the pipeline go green:
Command
chmod +x run-tests.sh
git add .
git commit -m "add tests"
git push
  • Line 1: chmod +x run-tests.sh.
  • WHAT: mark the file as runnable.
  • WHY: a new text file is not runnable yet. The pipeline would say "permission denied" if you skip this. This is the same chmod +x you met in zero-cost-lab.md Step 8. On GitHub, the pipeline runs the file, so the file must be runnable there too — and Git remembers the runnable mark when you push.
  • Word by word: chmod (change the file's permissions) + +x (add the "can run" permission) + run-tests.sh (the file).
  • Lines 2 to 4: git add ., git commit -m "add tests", git push.
  • WHAT: stage, save with the message "add tests", and send to GitHub.
  • WHY: the pipeline only runs on what is on GitHub. Until you push, GitHub cannot see the new files.
  • You should see: the pipeline run turns green on the Actions tab.
  • Green means passed. Go to the Actions tab, find the newest run, and look for a green tick. Click it to see the "Run the tests" step with a green tick too.
  • If it breaks: if it is still red, open the failed run, read the failed step's log, and find the first error line. That is the one thing to fix first.
  • Then break it on purpose once: delete the heading from index.html, watch the test step fail, restore it, and watch it pass.
  • HOW to delete the heading: open index.html, delete the line with "My DevOps practice site", save, push. The pipeline will fail.
  • HOW to restore it: put the line back, save, push. The pipeline will pass again.
  • WHY this matters: it proves the test really checks something.
  • Never replace a missing test with a command that only prints "tests passed". A green pipeline that checked nothing is worse than a red one.
  • WHAT that means: a line like echo "tests passed" always passes, even when everything is broken. It lies. A real test checks a real file.

Lesson

  • Most pipeline failures are not mysterious. Read the failed step's log, find the first error line, and fix that one thing first.

Clean up Lab 3

  • There is nothing to stop or delete on your machine: the pipeline runs on GitHub, not in a container here.

Lab 4 — The Git merge conflict

What is this?

  • A merge conflict is when two people (or two lines of work) changed the same lines, and Git stops and asks you to choose.
  • Think of two people editing the same sentence in a shared document. One writes "the cat sat". The other writes "the dog sat". The document cannot hold both. Someone must pick one.
  • Git shows you both versions side by side. You pick, you delete the marker lines, and you save. That is all a conflict is.

The setup

  • WHAT we are doing: making a small folder with a small Git history, so we can create a conflict on purpose.
  • WHY: you cannot practise fixing a conflict without one. This setup makes one.
  • Git needs to know who you are before your first commit, so set that once. These settings are for this folder only, not for your whole machine. That is why there is no --global here. --global would mean "for all projects on this machine".
Command
mkdir -p ~/devops-practice/git-conflict
cd ~/devops-practice/git-conflict
git init
git branch -M main
git config user.name "Learner"
git config user.email "learner@example.com"
  • Line 1: mkdir -p ~/devops-practice/git-conflict.
  • WHAT: make a folder called git-conflict inside ~/devops-practice.
  • WHY: this lab lives in its own folder, so it does not mix with other work.
  • Line 2: cd ~/devops-practice/git-conflict.
  • WHAT: move into that folder.
  • WHY: every Git command after this runs inside it.
  • Line 3: git init.
  • WHAT: start tracking this folder with Git.
  • WHY: until you do this, Git does not watch the folder at all.
  • Line 4: git branch -M main.
  • WHAT: name your main line of work "main".
  • WHY: so the main line has the usual name from the start.
  • Word by word: git branch (work with lines of work) + -M (rename) + main (the name).
  • Line 5: git config user.name "Learner".
  • WHAT: save the name "Learner" for this folder's Git work.
  • WHY: every save (commit) is stamped with a name. Git refuses to save without one.
  • Use your own name if you like. "Learner" is just the example.
  • Line 6: git config user.email "learner@example.com".
  • WHAT: save the email learner@example.com for this folder's work.
  • WHY: every save is stamped with an email too.
  • learner@example.com is a fake example email, for practice only. It is not a real address. Do not use it for real work. For real work, use your own email, as in zero-cost-lab.md Step 7.
  • You should see:
Command
Initialized empty Git repository in /home/learner/devops-practice/git-conflict/.git/
  • How to read it: Initialized empty Git repository in ... means Git started tracking this folder. The path ends in .git/. .git is Git's hidden folder inside your folder, where it keeps the history. Your home folder name will be different from /home/learner. That is fine.
  • The config lines print nothing when they work. That is normal.
  • If it breaks: "No such file or directory" means the folder was not made. Run the mkdir line again first.

Make a first version and save it

Command
cat > notes.txt << 'EOF'
Line one
EOF
git add notes.txt
git commit -m "first version"
  • Lines 1 to 3: cat > notes.txt << 'EOF' … EOF.
  • WHAT: write the line Line one into a file called notes.txt.
  • WHY: this is the file the two lines of work will both change.
  • cat > writes the lines that follow into a file until it sees the line EOF. EOF means "end of file".
  • Line 4: git add notes.txt.
  • WHAT: stage the file notes.txt.
  • WHY: staging marks it to be saved in the next commit.
  • Line 5: git commit -m "first version".
  • WHAT: save the staged file, with the message "first version".
  • WHY: a commit is a saved snapshot. The message says what changed.
  • You should see a commit line like:
Command
[main (root-commit) abc1234] first version
  • How to read it: [main ...] means the save is on the main line. root-commit means the first save in this folder. abc1234 is the short code for this save. Yours will be different. first version is your message.

Make a branch and change the same line there

Command
git checkout -b feature
cat > notes.txt << 'EOF'
Line one, edited on feature
EOF
git add notes.txt
git commit -m "feature edit"
  • Line 1: git checkout -b feature.
  • WHAT: make a new branch called feature and move onto it.
  • WHY: a branch is a separate line of work, so you can try changes without touching the main line.
  • Word by word: git checkout (move to a line of work) + -b (make a new one first) + feature (the name).
  • Lines 2 to 4: cat > notes.txt << 'EOF' … EOF.
  • WHAT: replace the file with the line Line one, edited on feature.
  • WHY: this is the feature branch's version of the same line.
  • Line 5: git add notes.txt.
  • WHAT: stage the file.
  • Line 6: git commit -m "feature edit".
  • WHAT: save it, with the message "feature edit".
  • You should see:
Command
Switched to a new branch 'feature'
[feature abc1234] feature edit
  • How to read it: Switched to a new branch 'feature' means you are now on the feature line. [feature abc1234] feature edit is the save, on feature, with your message. Your commit code will be different.

Go back to the main line and change the same line differently

Command
git checkout main
cat > notes.txt << 'EOF'
Line one, edited on main
EOF
git add notes.txt
git commit -m "main edit"
  • Line 1: git checkout main.
  • WHAT: move back to the main line.
  • WHY: so you can make a different change to the same line there.
  • Word by word: git checkout (move to a line of work) + main (the line's name). There is no -b this time, because main already exists.
  • Lines 2 to 4: cat > notes.txt << 'EOF' … EOF.
  • WHAT: replace the file with the line Line one, edited on main.
  • WHY: this is the main line's version of the same line.
  • Line 5: git add notes.txt. Line 6: git commit -m "main edit".
  • WHAT: stage and save, with the message "main edit".
  • You should see:
Command
Switched to branch 'main'
[main abc1234] main edit
  • How to read it: you are back on main, and the save is on main.

Break it

  • Try to merge the branch in:
Command
git merge feature
  • WHAT: merge the feature line into the line you are on (main).
  • WHY: merging is how a finished branch joins the main line.
  • Word by word: git merge (join lines of work) + feature (the line to join in).

Symptom

  • Git stops and says there is a CONFLICT in notes.txt.
  • Nothing is merged yet.
  • This is normal. Git is asking you to choose, not telling you something broke badly.

Find it

Command
cat notes.txt
  • WHAT: print the file notes.txt.
  • WHY: to see the two versions and the marker lines Git added.
  • You should see markers like this:
Command
<<<<<<< HEAD
Line one, edited on main
=======
Line one, edited on feature
>>>>>>> feature
  • How to read it, line by line:
  • <<<<<<< HEAD — WHAT: the start of your current line's version. WHY: Git marks where it begins. HEAD means "the line you are on right now", which is main. The < marks are just markers. They are not part of your file's real text.
  • Line one, edited on main — WHAT: the main version of the line.
  • ======= — WHAT: the divider between the two versions. WHY: it separates "yours" (above) from "theirs" (below).
  • Line one, edited on feature — WHAT: the feature version of the line.
  • >>>>>>> feature — WHAT: the end of the incoming version, and the name of the line it came from (feature). WHY: Git marks where it ends.

Fix it

  • Edit notes.txt so it holds the one version you want, and delete all three marker lines.
  • HOW: open notes.txt in nano (type nano notes.txt, change the text, press Ctrl+O then Enter to save, Ctrl+X to leave).
  • For example, keep:
Command
Line one, edited on main
  • That means the file holds exactly one line, and none of the three marker lines (<<<<<<< HEAD, =======, >>>>>>> feature) remain.
  • Never commit a file with marker lines still in it. They are not real text. They would stay in your file forever.
  • Then finish the merge:
Command
git add notes.txt
git commit
  • Line 1: git add notes.txt.
  • WHAT: stage the fixed file.
  • WHY: staging tells Git "this conflict is resolved, use this version".
  • Line 2: git commit.
  • WHAT: save the merge, with no message of your own.
  • WHY: Git already wrote a merge message for you, like "Merge branch 'feature'". It opens your editor so you can read it.
  • Which editor opens: Git opens the editor it is set to use. On a fresh machine this is usually nano or vim. If nano opens, press Ctrl+O then Enter to save, Ctrl+X to leave. If vim opens, press Esc, then type :wq and press Enter. :wq means "write (save) and quit". If you do not know which editor you are in, look at the bottom of the screen: nano shows its shortcuts at the bottom; vim shows nothing there and shows -- INSERT -- at the bottom when you are typing.
  • To avoid the editor entirely, you can run git commit --no-edit instead. --no-edit means "use Git's message as it is, do not open the editor".
  • You should see: your editor opens with the merge message. Save and close it, and the merge is done.
  • If it breaks: "nothing to commit" means the markers are still in the file, or you forgot git add. Open notes.txt, remove all three marker lines, then run git add notes.txt and git commit again.
  • The merge is done.
  • Lesson: a conflict is Git showing you both versions side by side. Read the markers, pick the right lines, remove the markers, and commit.

Clean up Lab 4

  • There is nothing to stop or delete on your machine: no container runs in this lab.

Lab 5 — The app runs, but the browser shows nothing

What is this?

  • The app works, but your browser cannot reach it, because no door was opened into the container.
  • Think of a shop that is open, but its front door is bricked up. The shop is fine. You just cannot get in.

Break it

Command
docker run -d --name quiet-web nginx
  • WHAT: start the nginx web server in a container called quiet-web, in the background.
  • WHY: this is the break. There is no -p door mapping this time. That missing mapping is the mistake, on purpose.
  • Word by word: docker run (start a container) + -d (background) + --name quiet-web (call it quiet-web) + nginx (the web server).
  • You should see: a long container ID printed, then your prompt back. A container ID is a code for this container. You do not need it.
  • No port mapping this time. That is the mistake, on purpose.

Symptom

  • docker ps shows quiet-web running.
  • But opening http://localhost:8080 in your browser says the site cannot be reached.
  • localhost means "this machine". 8080 is the door number.
  • The app is fine. The door to it is missing.

Find it

Command
docker ps
docker logs quiet-web
  • Line 1: docker ps.
  • WHAT: list running containers.
  • WHY: to see quiet-web running, and to look at its PORTS column.
  • Line 2: docker logs quiet-web.
  • WHAT: show what the container printed.
  • WHY: to check the app itself started normally.
  • You should see: quiet-web running, but the PORTS column is empty. docker logs shows nginx started normally.
  • How to read that: the PORTS column is where the door mapping would show, like 0.0.0.0:8080->80/tcp. Empty means no door was opened. The logs prove the app started. They do not prove a port is published. The PORTS column in docker ps is the evidence for that.
  • So the container works. Your machine simply has no door into it. A container's own port 80 does not reach your browser by itself. The -p mapping is what connects the two.

Fix it

Command
docker stop quiet-web
docker rm quiet-web
docker run -d -p 8080:80 --name quiet-web nginx
  • Line 1: docker stop quiet-web.
  • WHAT: stop the container called quiet-web.
  • WHY: you cannot add a door to a running container. You must make a new one with the door included.
  • Line 2: docker rm quiet-web.
  • WHAT: delete the stopped container.
  • WHY: the name quiet-web is taken until you delete it. The new container needs the same name.
  • Line 3: docker run -d -p 8080:80 --name quiet-web nginx.
  • WHAT: start a new container, same name, same image, but this time with door 8080 on your machine connected to door 80 in the container.
  • WHY: the -p 8080:80 mapping is the door. Without it, the browser cannot reach the app. With it, it can.
  • You should see: the welcome page at http://localhost:8080.
  • Open http://localhost:8080 again. The welcome page appears. The welcome page says "Welcome to nginx!". If you see it, the door works.

Second version (try this yourself)

  • Stop the first container, then run one with a different host port:
Command
docker stop quiet-web
docker run -d -p 8081:80 --name second-quiet nginx
  • Line 1: docker stop quiet-web.
  • WHAT: stop the container called quiet-web.
  • WHY: so door 8080 is free, and so you can see the difference between the two doors.
  • Line 2: docker run -d -p 8081:80 --name second-quiet nginx.
  • WHAT: start a new container called second-quiet, with door 8081 on your machine connected to door 80 in the container.
  • WHY: to prove the first number in -p is your machine's door.
  • You should see: http://localhost:8080 shows nothing. Nothing answers there any more, because quiet-web is stopped and nothing uses door 8080 now. Open http://localhost:8081 and it works.
  • Lesson: the first number in -p is your machine's door; the second is the container's. Check which door you actually opened.

Clean up Lab 5

Command
docker stop second-quiet
docker rm second-quiet
  • WHAT: stop the second container, then delete it.
  • WHY: so door 8081 is free and no container is left running.

Lab 6 — The build fails: file not found

What is this?

  • A build fails because the Dockerfile asks for a file that does not exist.
  • Think of a recipe that says "add the flour from the blue tin" when the blue tin is empty. The cook stops. The build stops the same way.

The setup

  • WHAT we are doing: making a folder with a web page file and a Dockerfile that copies a file which does not exist there.
  • WHY: so the build fails in the exact way this lab teaches you to fix.
  • A Dockerfile is a short recipe file. It says how to build an image.
  • The build context is the folder you build from. The build can only see files in that folder. Files outside it are invisible to the build.
Command
mkdir -p ~/devops-practice/build-fail
cd ~/devops-practice/build-fail
cat > index.html << 'EOF'
<h1>My site</h1>
EOF
cat > Dockerfile << 'EOF'
FROM nginx
COPY app.html /usr/share/nginx/html/app.html
EOF
  • Line 1: mkdir -p ~/devops-practice/build-fail.
  • WHAT: make a folder called build-fail inside ~/devops-practice.
  • WHY: this lab lives in its own folder.
  • Line 2: cd ~/devops-practice/build-fail.
  • WHAT: move into that folder.
  • WHY: every command after this runs inside it, and the build in the next step uses this folder as its build context.
  • Lines 3 to 5: cat > index.html << 'EOF' … EOF.
  • WHAT: write a tiny web page file called index.html.
  • WHY: this is the file that DOES exist. The Dockerfile below asks for a different file, which does not exist.
  • Lines 6 to 9: cat > Dockerfile << 'EOF' … EOF.
  • WHAT: write a file called Dockerfile with two lines.
  • WHY: this is the recipe the build will follow, and it holds the mistake.
  • Inside the file, line by line:
  • FROM nginx — WHAT: start from the nginx image. WHY: every Dockerfile starts with a FROM line that names the base image. The base image is the ready-made starting point. nginx with no tag means version latest, the default tag.
  • COPY app.html /usr/share/nginx/html/app.html — WHAT: copy a file called app.html from this folder into the image, to the path /usr/share/nginx/html/app.html. WHY: that path is where nginx looks for web pages inside the image. The first part (app.html) is the file in your folder. The second part is where it goes inside the image. The mistake is that app.html does not exist in your folder. Only index.html does.
  • You should see: nothing. These commands print nothing when they work. That is normal.

Break it

Command
docker build -t fail-demo:1.0 .
  • WHAT: build an image called fail-demo:1.0 from the files in this folder.
  • WHY: the build will fail at the COPY step, because app.html is missing.
  • Word by word: docker build (build an image) + -t (give it this name) + fail-demo:1.0 (the name and version — fail-demo is the name, 1.0 is the tag) + . (this folder — the dot means "build from the files right here". This folder is the build context.)
  • You should see an error like:
Command
COPY failed: file not found in build context
  • How to read it: COPY failed means the COPY step failed. file not found in build context means the file was not found in the folder you are building from. The build context is the folder you build from.

Symptom

  • The build stops at the COPY step with an error like "file not found".
  • The folder holds index.html, but the Dockerfile asks for app.html, which is not there.

Find it

  • Read the failed step in the build output: it names the missing file.
  • Then check what is actually in the folder:
Command
ls
  • WHAT: list the files in this folder.
  • WHY: to see with your own eyes which files really exist.
  • Word by word: ls (list files).
  • You should see: index.html listed, but no app.html.
  • The build can only see files in the folder you build from. The dot in docker build -t fail-demo:1.0 . means "this folder". That folder is called the build context, and files outside it are invisible to the build.
  • If a file that IS in the folder is still missing from the build, check .dockerignore. It can exclude files from the context.
  • WHAT .dockerignore is: a file that lists files the build must ignore, even though they sit in the folder. Its name starts with a dot, so it is a hidden file.
  • WHY it matters: if app.html were listed in .dockerignore, the build would say "file not found" even though you can see the file in the folder. Check it with cat .dockerignore (print the file). If the missing file is listed there, remove that line.

Fix it

  • Either create the missing file, or fix the Dockerfile to copy the file that exists. The honest fix here is the second one: the file that exists is index.html, so the Dockerfile should copy that.
Command
cat > Dockerfile << 'EOF'
FROM nginx
COPY index.html /usr/share/nginx/html/index.html
EOF
docker build -t fail-demo:1.0 .
  • Lines 1 to 4: cat > Dockerfile << 'EOF' … EOF.
  • WHAT: replace the Dockerfile with a fixed version.
  • WHY: the fixed version copies index.html, the file that exists, to /usr/share/nginx/html/index.html, where nginx looks for it.
  • cat > writes the lines that follow into the file until EOF, replacing what was there before.
  • Line 5: docker build -t fail-demo:1.0 ..
  • WHAT: build the image again, from this folder.
  • WHY: to prove the fix works.
  • You should see: the build finish with no error, and the last line names fail-demo:1.0.
  • If it breaks: if it still says "file not found", check you are in the build-fail folder. Run pwd and ls first.
  • WHAT pwd is: print the folder you are in right now.
  • WHY: if you are in the wrong folder, the build looks in the wrong place. pwd tells you where you are. ls tells you what is there.
  • The build passes.
  • Lesson: when a build says a file is not found, check two things: does the file exist, and is it inside the folder you are building from?

Clean up Lab 6

Command
docker rmi fail-demo:1.0
  • WHAT: delete the image called fail-demo:1.0.
  • WHY: it was only a practice image. Deleting it keeps your machine tidy.
  • Word by word: docker rmi (remove an image) + fail-demo:1.0 (the image name and tag). rmi means "remove image".
