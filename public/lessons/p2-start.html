Start Here — Phase 2: Linux, Git, Docker and More

Phase 2 · The Rest of DevOps

What this is and why it matters

Phase 2 teaches you DevOps: the tools that build and run modern software, from files to the pipeline that ships code.

In real work, the costliest failure is not knowing how your software runs — a small problem becomes a long outage.

You learn by doing, on your own computer, one small thing at a time, and finish with four finished projects you can show.

Who this is for

A beginner who wants to learn DevOps but does not know where to start. You need only a computer and internet. No paid course is needed to start. This is Phase 2 of the DevOps Kit. Phase 1 teaches the data tier (Kafka, PostgreSQL, Redis, object store, load balancer) — do Phase 2 first if you cannot yet use a terminal and Docker, then do Phase 1.

What is DevOps, in plain words?

  • DevOps is a way of working.
  • One group of people writes the software.
  • Another group runs the software, so other people can use it.
  • In DevOps, those two jobs are done together, not by two separate teams.
  • The tools in this phase are the tools that build software and run it.

What is Phase 2, in plain words?

  • Phase 2 teaches you seven tools, in this order: Linux, Git, Docker, Kubernetes, Terraform, CI/CD, Monitoring.
  • Linux is the operating system you type commands into.
  • Git saves versions of your work, so you can go back.
  • Docker runs one program in a sealed box, called a container.
  • Kubernetes runs many of those boxes and keeps them running.
  • Terraform writes down what computers and settings you want, in a file.
  • CI/CD is an automatic chain of steps: test the code, then build it.
  • Monitoring watches your app and tells you if it is up, slow, or out of memory.

What is Phase 1, and which phase do I do first?

  • Phase 1 teaches the data tier.
  • The data tier is where your app keeps its data: Kafka, PostgreSQL, Redis, a file store, and a load balancer.
  • Do Phase 2 first if you cannot yet use a terminal and Docker.
  • A terminal is a window where you type commands instead of clicking.
  • Docker is the sealed-box tool above.
  • After you can run Docker and read logs, do Phase 1.
  • If you only have the Phase 2 download, that is fine.
  • Phase 1 is a separate pack. You do not need it to start Phase 2.

If you get stuck

  2. WHAT it is: kit-doctor.sh is a script that checks Docker, ports, disk, and memory, and prints a plain-English FIX line for anything wrong.
  3. WHERE it lives: in the Phase 1 kit folder, at phase1/kit-doctor.sh. A port is a numbered door for network traffic. Disk is your storage space. Memory is your computer's short-term working space.
  4. HOW to run it: open a terminal in the Phase 1 kit folder and run bash kit-doctor.sh. bash means "run this with Bash", the command language. kit-doctor.sh is the file name.
  5. If you only have Phase 2, skip to step 2. There is no kit-doctor script in the Phase 2 folder.

Words you will see a lot

  • DevOps — a way of working where building software and running software are done together, not by two separate teams.
  • Server — a computer that runs your app for other people to use.
  • Cloud — renting servers on the internet instead of owning them.
  • Pipeline — an automatic chain of steps: test the code, then build it. Putting it live (deployment) is a separate later stage, with its own checks.
  • Container — a small box that holds an app and the things it needs to run. It helps the app run the same way on machines that are set up the same way. The machine, its settings, and outside services can still change the result.
  • Terminal — a window where you type commands instead of clicking.
  • Image — a saved, ready-to-run copy of an app, built from a Dockerfile (the recipe file). A container is an image running.
  • Repository (repo) — a project folder that Git tracks, usually stored on GitHub.
  • YAML — a plain-text way of writing settings with indentation. Spaces matter. Pipelines, Compose files, and Kubernetes files all use it. Never use the Tab key in a YAML file.
  • Script — a small text file full of commands, which runs them one by one for you.
  • DNS — the internet's address book: it turns a name like example.com into a computer's address.
  • HTTP — the language a browser uses to ask a web server for a page.

The order

Step 1 — Linux (about 2 weeks, 1–2 hours a day)

  • What you learn: moving around folders, listing files, reading files, file permissions, running and stopping programs, checking what is using the machine, and writing one tiny script.
  • A script is a small text file full of commands. It runs them one by one for you.
  • File permissions are the rules that say who can read, change, or run a file.
  • You also learn three network basics: a port (a numbered door for network traffic), DNS (the internet's address book: it turns a name like example.com into a computer's address), and HTTP (the language a browser uses to ask a web server for a page).
  • Skip for now: deep system setup, kernel details, advanced networking.
  • Kernel means the core of the operating system. You do not need it yet.
  • You are done when: you can set up a folder, install a tool, and find why a program stopped, using only the terminal.
  • How to know you are on track: by the end of week 1 you can move around folders and list files without looking at notes. By the end of week 2 you can write the tiny script in zero-cost-lab.md Step 8 and it runs.
  • If you are slower than 2 weeks, that is fine. Slow is fine.
  • Finished projects beat finished videos.

Step 2 — Git (about 1 week)

  • What you learn: save your work, look at past versions, make a branch, merge it back, fix a merge conflict, and push to GitHub.
  • A branch is a separate line of work, so you can try changes without touching the main line.
  • A merge conflict is when two people changed the same lines.
  • Git stops and asks you to choose. That is normal, not a disaster.
  • GitHub is a website that stores your Git work online.
  • Skip for now: rewriting history, complex merge tricks.
  • You are done when: your practice work lives on GitHub with a clear history of changes.
  • How to know you are on track: by day 3 you can save a change and see it in the history. By day 7 you can make a branch, change a line, and merge it back.
  • The hands-on practice for a conflict is break-and-fix-labs.md Lab 4.

Step 3 — Docker (about 2–3 weeks)

  • What you learn: what a container is, how to build one from a Dockerfile, how to run it, map ports, stop it, and share files with a container.
  • A Dockerfile is a short recipe file. It says how to build an image.
  • An image is a saved, ready-to-run copy of an app.
  • A container is an image running.
  • A named volume keeps data after the container is removed.
  • A bind mount shares one of your folders into the container.
  • Files written only inside a container are lost when it is removed.
  • That is the difference: a volume saves data, a bind mount shares a folder, and plain files inside a container disappear with it.
  • Skip for now: Docker Swarm, advanced networking, building your own base images.
  • You are done when: you can put a small website in a container and open it in your browser.
  • How to know you are on track: by the end of week 1 you can run the ready-made nginx web server in a container. By the end of week 2 or 3 you can build your own image from a Dockerfile.
  • The hands-on lab is zero-cost-lab.md Steps 3 to 5.

Step 4 — Kubernetes (about 3–4 weeks)

  • What you learn: pods, deployments, services, and reading logs.
  • A pod is the smallest thing Kubernetes runs, usually one container.
  • A deployment is a way to say how many copies of your app should run.
  • You set the number. The usual starting point is 1 copy.
  • One copy is enough while you are learning. More copies are for when many people use your app at once.
  • A service is a stable address inside the cluster for your app.
  • A cluster is a group of machines (here, one pretend machine on your own computer) that Kubernetes runs your app on.
  • Logs are the lines of text your app prints while it runs.
  • Reading logs is how you find out why something broke.
  • Skip for now: service mesh, operators, running a big production cluster.
  • A service mesh is a tool that manages traffic between many services. An operator is a program that runs another program for you. You do not need either yet.
  • You are done when: you can run your container app on a small local cluster, expose it with a Service, and fix it when it crashes.
  • How to know you are on track: by the end of week 2 you can start the local cluster and see one node that says Ready. By the end of week 3 or 4 your app runs as a pod and you can open it in a browser.
  • The hands-on lab is kubernetes-lab.md. It walks you through kind (a tool that runs a small cluster as containers on your machine), your Project 1 app, a Service, and fixing a crashed pod.
  • The tools kind and kubectl are installed in that lab, not in this lesson. Do not try to install them from this map alone.

Step 5 — Terraform (about 2 weeks)

  • What you learn: writing down what infrastructure you want in a file, and letting Terraform create it.
  • Terraform is called "infrastructure as code".
  • Infrastructure means servers, networks, and settings.
  • "As code" means you write it down in a file, instead of clicking buttons each time.
  • Terraform keeps a state file.
  • A state file is a file that maps each thing in your file to the real thing Terraform created. It stores what Terraform needs to plan the next change.
  • State can hold private details, so never put it in a public repository.
  • A repository is a project folder that Git tracks, usually stored on GitHub. Public means anyone on the internet can see it.
  • Skip for now: remote state servers, workspaces, writing your own modules.
  • A remote state server is a shared place to keep the state file. A workspace is a separate copy of the settings for one environment. A module is a re-usable block of Terraform files. You do not need any of these yet.
  • You are done when: one Terraform file creates your practice setup, and running terraform plan again shows nothing to change.
  • terraform plan is a command that shows what Terraform would change, without changing anything yet.
  • "Nothing to change" means your file and the real setup already match.
  • If the plan shows changes, read it before you apply.
  • Apply means: go ahead and make the changes.
  • Drift is the word for when the real setup changed without Terraform knowing — for example, someone changed a setting by hand. If drift happened, the plan will show changes. Read them first.
  • How to know you are on track: by the end of week 1 you can write a file that describes one small setup. By the end of week 2 you can run terraform plan and read what it says.
  • Terraform has no install step in this lesson. Its lab will tell you how to install it when you reach it. Do not install it now.

Step 6 — CI/CD (about 2 weeks)

  • What you learn: a pipeline that runs on every code change — run a simple test, then build it.
  • A pipeline is an automatic chain of steps, like a factory line.
  • CI means continuous integration: merging code often and testing it.
  • CD can mean two things. Continuous delivery means a change is kept tested and ready to release. Continuous deployment means a passing change is released automatically, with no human step.
  • This kit's pipeline tests and builds. It does not deploy.
  • Deploy means putting a new version live for real users.
  • That is a separate later stage, with its own checks.
  • So when this kit says "pipeline", it means test, then build.
  • When it says "deployment", it means putting it live. They are different steps.
  • Skip for now: multi-environment release rules, canary deployments.
  • A canary deployment sends a new version to a few users first, to check it works, before sending it to everyone.
  • You are done when: pushing code to GitHub starts your pipeline by itself and you can read its log when it fails.
  • Pushing means sending your saved work from your machine to GitHub.
  • How to know you are on track: by the end of week 1 you can read a pipeline log and find the first error line. By the end of week 2 your own push starts the pipeline on its own.
  • The hands-on practice is break-and-fix-labs.md Lab 3.

Step 7 — Monitoring (about 1–2 weeks)

  • What you learn: Prometheus and Grafana, and what to watch.
  • Prometheus collects numbers about your app, like how much memory it uses.
  • Grafana turns those numbers into charts you can look at.
  • Learn what to watch: is the app up, is it slow, is it out of memory?
  • Up means running and answering. Slow means answering, but late. Out of memory means it ran out of working space and may crash.
  • Skip for now: alerting rules for big teams, log analysis platforms.
  • Alerting rules are automatic messages that say "something is wrong". A log analysis platform is a tool that searches through huge piles of log lines. You do not need either yet.
  • You are done when: you have a Grafana chart showing your monitoring targets are up.
  • A monitoring target is one thing Prometheus checks, for example your app's address.
  • How to know you are on track: by the end of week 1 you can open Grafana and see a chart. By the end of week 2 the chart shows your app as up.
  • The setup is in Project 3 in portfolio-projects.md.
  • Prometheus and Grafana have no install step in this lesson. Project 3 tells you how to set them up when you reach it. Do not install them now.

After Step 7 — Phase 1 (the data tier)

  • When you can run Docker and read logs, do Phase 1.
  • Phase 1 teaches: Kafka (a message queue — a line of messages waiting to be handled, one by one), PostgreSQL with a standby copy and Patroni failover, Redis (a fast memory store), Moto (a file store), and NGINX as a load balancer.
  • A standby copy is a second copy of the database, waiting in case the first one fails.
  • Failover means the standby copy takes over when the main one fails.
  • A load balancer shares incoming visits across more than one copy of your app, so no single copy gets all the traffic.
  • Phase 1 ends with an end-to-end lab where a fake order flows through all of them at once, and you kill the main database and watch the standby take over.
  • End-to-end means from the first step to the last step, all together.

Rough total

  • About 3–4 months at 1–2 hours a day for Phase 2, plus about 1 week for Phase 1.
  • These are rough guides, not promises.
  • Topics overlap, so the total is not the sum of the longest estimates.
  • For example, you use Git every day while you learn Docker, so the Git week and the Docker weeks overlap. You do not add them all up.
  • If you miss a day, just continue the next day. The weeks are guides, not deadlines.
  • Slow is fine. Finished projects beat finished videos.

What to skip entirely for now

  • Learning every tool at once.
  • Paid certificates before you have projects.
  • Copying commands you do not understand. If a command fails, read the error message first. That is the real skill.
