Redis Lab — A Fast Memory Store

Phase 1 · The Data Tier

What this is and why it matters

Redis is a fast memory store. It keeps small answers in memory so they can be read in a blink.

Think of it like a small whiteboard next to a shop counter.

  • The big record book sits in the back room. Finding an answer in it takes time.
  • The whiteboard on the counter holds the few answers people ask for again and again.
  • A worker glances at the whiteboard and answers at once.
  • Nobody opens the big book for every small question.

In real systems, asking the main record store for every small answer is slow. A memory store takes that load off it.

This lab runs two Redis stores on your own computer: a main one and a copy that follows it. You will save fake values, set expiry times, use a counter, and see what happens when you try to write to the copy. Then the copy stops following and becomes a main store itself.

One idea per line, in order:

  • Memory is the fast working space of a computer. Reading from memory is fast.
  • A store keeps things by name, so you can ask for them back by that name.
  • The main store is called redis-a in this lab.
  • The copy is called redis-b in this lab. It follows redis-a.
  • A copy takes reads only. It refuses writes.
  • Expiry means a saved answer deletes itself after a set time.
  • A counter is a number that goes up by one each time something happens.

All data in this lab is fake: made-up users, made-up login codes, made-up counts.

What this lab is

You will run two Redis stores on your own machine: a main one and a copy that follows it. You will save fake values, set expiry times, use a counter, and see what happens when you try to write to the copy. All data is fake.

What you need first

  • Docker running. Lesson 0 shows how to install it and check it.
  • The file in the folder phase1/redis-lab/ — verified on disk: docker-compose.yml. That is the only file the lab needs. It also holds a helper file called drill.sh, which the lab does not ask you to run. You do not need to open either file. The lab steps tell you the commands to run.
  • Do the Kafka lab and the PostgreSQL lab first if you are following the phase order.

Words you need, before you use them

  • Redis — a store that keeps data in memory, so reads are very fast. It is used for caches, counters and short-term data.
  • Key and value — Redis stores things by name. The name is the key. The thing stored is the value. Example: key user:101, value Asha. The colon : in user:101 is only a naming habit. It separates the kind of thing (user) from its number (101). Redis does not treat the colon specially. You could name the key user101 instead. The colon only makes it easier for humans to read.
  • Cache — a fast copy of an answer, kept so you do not have to ask the slow record store again.
  • Expiry (TTL) — a time limit on a key. TTL is short for "time to live", meaning how many seconds the key has left to live. When the time runs out, Redis deletes the key by itself.
  • Replica — a copy that follows the main store. It takes reads only.
  • Counter — a number stored in Redis that you add 1 to, again and again. Each add is one step.
  • CRDT — short for Conflict-free Replicated Data Type. It is a way for two stores to accept writes at the same time and merge them. It is a paid feature in Redis products. This lab shows the idea in plain words in Step 7, and shows the free one-way copy instead. The free Redis in this lab does not have CRDT.
  • One-way copy — one store follows another. Writes go to the main store only. The copy only reads.
  • Two-way sync — two stores both accept writes, and merge the changes so both end up the same. That merge rule is the CRDT idea.
  • (nil) — the word redis-cli prints when a key has nothing stored under it. It means "nothing here". It is not an error. It is the answer "this key does not exist right now".
  • redis-cli — the command-line tool for talking to Redis. It runs inside the container. The letters cli are short for "command-line interface", meaning a tool you use by typing.
  • PONG — the answer Redis gives when you ask it "are you alive?" with the ping command. ping is the question, PONG is the answer. If you see PONG, the store is up and answering.
  • Volume — a named place on your machine where Docker keeps a container's data. The data lives in a volume, so it survives a restart. Wiping the volume wipes the data.
  • Append-only file — a file Redis writes every change into, so data survives a restart. The lab turns this on with --appendonly yes in the file phase1/redis-lab/docker-compose.yml. You do not type that flag yourself. It is already in the compose file. In real work, check the disk settings before you trust it.
  • Practice data — all values in this lab are fake, on your own machine, for learning only.

The doors (ports) in this lab

  • redis-a, the main store, answers on door 6379 on your machine.
  • redis-b, the copy, answers on door 6380 on your machine. Inside its own container, the copy still uses door 6379, but from outside you reach it on 6380. That is why two stores can run on one machine without fighting over the same door.
  • You do not type these door numbers in the commands below, because the commands run inside the containers. The door numbers matter only if another program on your machine already uses door 6379. If a start fails with port is already allocated, it means the door is already held. Stop the other program that uses it, or stop the old containers, then try again.

Step 1 — Start both stores

First, move your terminal into the lab folder. The folder is phase1/redis-lab/. Open your terminal in that folder. If your terminal opens somewhere else, move into it first with cd followed by the path to that folder on your machine.

What this is: start both Redis stores together. Why we run it: nothing else in this lab can work until both stores are running.

Type this, then press Enter:

Try it Yourself »Open the practice terminal and run it yourself — nothing installs. Included with Phase 1. Simulation — practice version. Run the real lab with Docker to do it for real.
Command
docker compose up -d

Word by word:

  • docker — the Docker tool.
  • compose — the part of Docker that starts several containers together from one file.
  • up — start everything listed in the file.
  • -d — short for detached. It means run in the background and give me my terminal back, instead of filling my screen with logs.

What you should see, line by line:

Command
[+] Running 2/2
 ✔ Container redis-a  Started
 ✔ Container redis-b  Started
  • [+] Running 2/2 — 2 out of 2 containers are running.
  • Container redis-a Started — the main store container started.
  • Container redis-b Started — the copy container started.
  • How to tell it worked: both lines say Started.

Now check they are both up. What this is: ps lists the containers Compose is running. Why we run it: the start lines scroll past fast, and this check proves both containers are still up right now.

Type this, then press Enter:

Command
docker compose ps

Word by word:

  • docker compose — the Docker Compose tool, as above.
  • ps — short for "process status". It lists the running containers.

What you should see: a table with redis-a and redis-b, each with STATUS Up. The real table has more columns than the example below. What matters is both names, each with STATUS Up.

Command
NAME       STATUS
redis-a    Up
redis-b    Up

Now check they answer. What this is: ping asks a Redis store "are you alive?" Why we run it: a container can say Up and still not be ready to answer. PONG proves it is answering.

Type this, then press Enter:

Command
docker exec redis-a redis-cli ping

Word by word:

  • docker exec — run a command inside a container that is already running. exec means execute, or run.
  • redis-a — the container name. This is the main store container. Check the name: redis-a, not redis-b.
  • redis-cli — the tool for talking to Redis. It runs inside the container.
  • ping — the Redis command that asks "are you alive?"

What you should see:

Command
PONG
  • PONG is the answer to ping. It means the store is up and answering.

If it breaks: if ping shows nothing, wait 10 seconds and try again. Redis starts fast, but the first start downloads the image. An image is the recipe Docker uses to build a container. The first download takes time. You can tell the download is done when the ping command answers PONG.

Step 2 — Save and read a value

What this is: save one fake user in the main store, then read it back. Why we run it: it proves the main store saves and returns values.

Save a fake user. Type this, then press Enter:

Command
docker exec redis-a redis-cli SET user:101 Asha

Word by word:

  • docker exec redis-a redis-cli — run the Redis tool inside the main store container, as in Step 1.
  • SET — the Redis command that saves a value. SET means "store this".
  • user:101 — the key, or the name to store it under. user is the kind of thing. 101 is its number. The colon is only a naming habit, as explained above.
  • Asha — the value, or the thing stored. This is a fake name, made up for this lab.

What you should see:

Command
OK
  • OK means the save worked. That is the whole answer. There is no more detail to read.

If it breaks: Could not connect means redis-a is not up yet. Run docker compose ps and wait until it shows Up.

Read it back. Type this, then press Enter:

Command
docker exec redis-a redis-cli GET user:101

Word by word:

  • docker exec redis-a redis-cli — run the Redis tool inside the main store container.
  • GET — the Redis command that reads a value back. GET means "give me the value stored under this name".
  • user:101 — the key to read. It must match the key you saved exactly, including the colon and the number.

What you should see:

Command
"Asha"
  • "Asha" is the value you saved. The quotes are part of how redis-cli shows a value. The value stored is Asha, without quotes. The quotes are only display marks.
  • How to tell it worked: the answer is the name you saved.

If it breaks: if you see (nil) ("nothing here"), the SET step never saved. (nil) means no value is stored under that key. Run the SET command again and check it prints OK.

Step 3 — Set a value that deletes itself

What this is: save a login code that lasts 60 seconds, then watch it disappear. Why we run it: this is how login codes and short-lived sessions work. The store cleans up by itself. Nobody has to delete the code by hand.

Save a login code that lasts 60 seconds. Type this, then press Enter:

Command
docker exec redis-a redis-cli SETEX login-code:101 60 482913

Word by word:

  • docker exec redis-a redis-cli — run the Redis tool inside the main store container.
  • SETEX — the Redis command that saves a value with an expiry time. SETEX means "set with expiry". It is SET plus a time limit.
  • login-code:101 — the key. login-code is the kind of thing. 101 is its number.
  • 60 — the time limit, in seconds. The key will live for 60 seconds from this command. This number comes before the value. The order matters: key, then seconds, then value.
  • 482913 — the value, the fake login code. This is a made-up six-digit code, not a real code. It is fake, for practice only.

What you should see:

Command
OK
  • OK means the save worked.

Check how long is left. What this is: TTL asks how many seconds a key has left to live. Why we run it: it proves the countdown is running.

Type this, then press Enter:

Command
docker exec redis-a redis-cli TTL login-code:101

Word by word:

  • TTL — short for "time to live". It asks "how many seconds does this key have left?"
  • login-code:101 — the key to check.

What you should see: a number near 60. It counts down: 58, 57, and so on. Your number depends on how many seconds passed between the SETEX command and this check.

Command
58
  • 58 means 58 seconds are left. The key was saved 60 seconds ago in the example, and 2 seconds passed before the check. Your number will be different. That is fine.
  • How to tell it worked: the answer is a number near 60, counting down.

Two other TTL answers you may see, and what they mean:

  • -2 means the key is already gone. Its 60 seconds ran out before you checked. Run the SETEX command again.
  • -1 means the key exists but has no expiry time. That should not happen for this key, because SETEX always sets an expiry. If you see -1, you are checking a different key, or the key was saved with plain SET instead of SETEX.

Wait 65 seconds and read it again. Type this, then press Enter, after waiting a full 65 seconds:

Command
docker exec redis-a redis-cli GET login-code:101

What you should see:

Command
(nil)
  • (nil) means "nothing here". The key deleted itself when its time ran out.
  • How to tell it worked: the code is gone. That is the expected result, not a failure.

If it breaks: if the code is still there after 65 seconds, check you waited long enough. The key lives for a full 60 seconds from the SETEX command, not from when you first read it. Count 65 seconds from the moment you pressed Enter on the SETEX command, then read it again.

Step 4 — Use a counter

What this is: a number that goes up by one each time something happens. Why we run it: counters are the simplest thing Redis does well. In the end-to-end lab, a worker does this every time an order is saved. That is how the app shows "how many orders" without asking the record store.

Type these five commands, one at a time, pressing Enter after each:

Command
docker exec redis-a redis-cli SET orders:count 0
docker exec redis-a redis-cli INCR orders:count
docker exec redis-a redis-cli INCR orders:count
docker exec redis-a redis-cli INCR orders:count
docker exec redis-a redis-cli GET orders:count

Word by word:

  • SET orders:count 0 — save a key called orders:count with the value 0. This sets the counter to zero before you start counting.
  • INCR — short for increment, which means add 1. It adds 1 to the stored number and prints the new number.
  • INCR orders:count — add 1 to the counter. There are three INCR commands, so the counter goes 0, then 1, then 2, then 3.
  • GET orders:count — read the counter back.

Each of the five commands prints its own answer:

  • After SET orders:count 0, you should see OK.
  • After the first INCR orders:count, you should see 1.
  • After the second INCR, you should see 2.
  • After the third INCR, you should see 3.
  • After GET orders:count, you should see "3".

What you should see at the end:

Command
"3"
  • "3" is the final counter value. Each INCR added 1. Three INCRs after starting at 0 gives 3.
  • The quotes are part of how redis-cli shows a value. The value stored is 3.
  • How to tell it worked: the final answer is "3", and the three INCR answers before it were 1, 2, and 3, in order.

If it breaks: if GET shows "0", the first SET step was skipped, and the counter never started. Run SET orders:count 0 first, then the three INCRs. If GET shows a number higher than "3", you ran the INCR commands more than three times. That is fine for learning, but start again from SET orders:count 0 if you want a clean "3".

Step 5 — Read the same values from the copy

What this is: read the values you saved on the main store, but ask the copy instead. Why we run it: it proves the copy follows the main store. The copy should already have the same values.

Type these two commands, one at a time, pressing Enter after each:

Command
docker exec redis-b redis-cli GET user:101
docker exec redis-b redis-cli GET orders:count

Word by word:

  • docker exec redis-b — run a command inside the copy container. Check the name: redis-b, not redis-a.
  • redis-cli GET user:101 — read the value stored under the key user:101.
  • redis-cli GET orders:count — read the value stored under the key orders:count.

What you should see, one answer per command:

Command
"Asha"
"3"
  • "Asha" is the answer to the first command.
  • "3" is the answer to the second command.
  • How to tell it worked: the copy shows the same two values you saved on the main store.

If it breaks: if either shows (nil), the copy has not caught up yet. Wait 10 seconds and read again.

Now check what the copy thinks it is. What this is: INFO replication asks a Redis store to describe its replication state: what role it has, and which store it follows. Why we run it: the two values above prove the data copied. This command proves the copy knows it is a follower.

Type this, then press Enter:

Command
docker exec redis-b redis-cli INFO replication

Word by word:

  • docker exec redis-b redis-cli — run the Redis tool inside the copy container.
  • INFO — the Redis command that prints information about the store.
  • replication — the topic to print. It means "tell me about copying and following".

What you should see, line by line:

Command
# Replication
role:slave
master_host:redis-a
master_port:6379
  • # Replication — a heading. The # mark means this line is a section heading, not data.
  • role:slave — the copy's role is slave. Older Redis still calls a replica "slave". In this output, slave means the same thing as replica: a copy that follows the main store. It is an old word for the same job. The lab's own words call it a replica.
  • master_host:redis-a — the main store it follows is named redis-a. master is the old word for the main store, the same as primary. host means the machine or container name.
  • master_port:6379 — the main store's door number is 6379. That is redis-a's door, as listed at the top of this lesson.
  • The real output is longer than the four lines above. It has more lines about the copy state. The lines that matter are the role line and the master_host line.
  • How to tell it worked: the role line says slave and the host line says redis-a. That is the proof it is following the main store.

If it breaks: if the role shows master, the copy never linked to the main store. master as a role means "I am a main store, I follow nobody". Restart the copy with the command below, then wait 10 seconds. What this is: restart stops a service and starts it again. Why we run it: a fresh start makes the copy link to the main store again.

Command
docker compose restart redis-b

Word by word: docker compose restart redis-b — restart the service named redis-b.

Step 6 — Try to write on the copy (it must refuse)

What this is: a save command aimed at the copy. Why we run it: a one-way copy takes reads only. Trying a write and watching it fail is the proof. The error is the expected result. Do not try to fix it.

Type this, then press Enter:

Command
docker exec redis-b redis-cli SET user:102 Ravi

Word by word:

  • docker exec redis-b redis-cli — run the Redis tool inside the copy container. Check the name: redis-b, not redis-a.
  • SET user:102 Ravi — save a key called user:102 with the value Ravi, a fake name.

What you should see:

Command
(error) READONLY You can't write against a read only replica.
  • (error) — the command failed.
  • READONLY — the reason: this store is read-only.
  • You can't write against a read only replica. — the plain-English reason: you cannot save a value on a copy that only follows.
  • How to tell it worked: you see this error. The error IS the proof. A one-way copy takes reads only. This is correct and expected.

If it breaks: if the SET returns OK instead of the READONLY error, you ran it on redis-a by mistake. Check the container name in the command (redis-b, not redis-a) and try again.

Step 7 — The two-way idea, in plain words

What this is: an idea, not a command. There is nothing to type in this step. Why it is here: so you understand what the free lab does NOT do.

What if two stores both accept writes at the same time? Then they must merge the changes. That merge rule is called a CRDT. It is a paid feature in Redis products. The free Redis in this lab does not have it.

The idea is the same as a shared document. If two people change the same line at the same time, the system needs a rule for which change wins. With a CRDT, the rule is built into the data itself, so both copies end up the same without arguing.

For this lab, remember this: one-way copy is free and simple. Two-way copy is a paid feature with rules you must understand before you use it. The lesson does not name which paid Redis product sells it. Do not go and buy anything for this step. The idea is the lesson. The free one-way copy in Steps 1 to 6 is the skill.

Clean up

What this is: stop both stores and remove their containers. Why we run it: the lab is done, and the next lab should start clean.

Type this, while you are inside the phase1/redis-lab/ folder, then press Enter:

Command
docker compose down

Word by word:

  • docker compose down — stop the containers and remove them. down is stronger than stop: stop leaves the containers in place so you can start them again; down removes them.

What you should see:

Command
✔ Container redis-a  Removed
✔ Container redis-b  Removed
  • The tick ✔ means done. Each line says one container was removed.

If it breaks: No such container means the stores are already stopped. Nothing to do.

down versus down -v — read this before you wipe anything

The data is in named volumes, so it survives a restart. A volume is a named place on your machine where Docker keeps a container's data. docker compose down removes the containers but leaves the volumes, so the data is still there the next time you start. Run the command below to wipe it. What this is: down -v stops the containers, removes them, and wipes the volumes too. Why we run it: only when you want the data gone for good.

Command
docker compose down -v

Word by word: docker compose down stops and removes the containers. -v means also wipe the volumes. Without -v, the data survives. With -v, the data is gone.

The data was fake, so losing it is fine. But do not run down -v by accident when you meant to keep your counter and values for the next step. If you run the drill below, do it before this wipe.

What you can now say, truthfully

"I ran two Redis stores, saved and read values, set keys that expire by themselves, used a counter, and proved a replica takes reads only."

What this lab does NOT cover

  • Redis Cluster (many nodes sharing the data) is a bigger setup. The ideas are the same; the setup is bigger. A cluster splits the data across many nodes instead of copying all of it to one follower.
  • Redis persistence (saving to disk) is on in this lab with --appendonly yes, so data survives a restart. That flag lives in the file phase1/redis-lab/docker-compose.yml, on the line that starts each store. You do not type it. In real work, check the disk settings before you trust it.

Failure drill — Promote the copy

This drill proves a copy can become a main store, and take writes, when you tell it to stop following. Do Steps 1 to 5 first, so the copy already holds the same data as the main store. Step 6 is not needed before the drill, because Step 6 only proves the copy refuses writes. The drill is the opposite: it makes the copy accept writes.

Drill Step 1 — Tell the copy to stop following

Run this from inside the folder phase1/redis-lab/. Type this, then press Enter:

Command
docker exec redis-b redis-cli REPLICAOF NO ONE

Word by word:

  • docker exec redis-b redis-cli — run the Redis tool inside the copy container.
  • REPLICAOF — the Redis command that sets which store this store follows. REPLICAOF means "be a replica of".
  • NO ONE — follow nobody. The two words together mean "stop following". After this command, the copy follows no main store. It stands alone.

What you should see:

Command
OK
  • OK means the command worked. The copy stopped following.

If it breaks: if it shows an error, redis-b is not up. Run docker compose ps and wait until it shows Up.

Drill Step 2 — Check what the copy thinks it is now

Type this, then press Enter:

Command
docker exec redis-b redis-cli INFO replication

This is the same command as Step 5. What you should see now is one line:

Command
role:master
  • role:master — the copy is now a main store. master is the old word for a main store. It no longer follows redis-a.
  • The real output is longer than this one line. Find the role: line in it. That is the line that matters.
  • How to tell it worked: the role line changed from slave to master.

If it breaks: if the role still shows slave, wait 10 seconds and check again. The change takes a moment.

Drill Step 3 — Prove it takes writes now

Type this, then press Enter:

Command
docker exec redis-b redis-cli SET user:102 Ravi

This is the same save command that failed in Step 6. Word by word: save a key called user:102 with the value Ravi, inside the copy container.

What you should see:

Command
OK
  • OK means the save worked. The copy now accepts writes.

Read it back. Type this, then press Enter:

Command
docker exec redis-b redis-cli GET user:102

What you should see:

Command
"Ravi"
  • "Ravi" is the value you just saved. The copy saved a value of its own.

If it breaks: if the SET still shows the READONLY error, Drill Step 1 did not take. Run REPLICAOF NO ONE again and check it prints OK.

Checklist — tick each one when you have seen it:

  • ☐ The copy stopped following: REPLICAOF NO ONE printed OK.
  • ☐ The copy is now a main store: INFO replication shows role:master.
  • ☐ The copy takes writes: the new value saved and read back.

Reset after the drill

Run this from the phase1 folder to wipe the drill and start fresh. What this is: reset.sh is a helper script in the phase1 folder. Its argument tells it which lab folder to wipe. Why we run it: it stops both stores and wipes the data, then prints that it is done.

Move your terminal into the phase1 folder first. Then type this and press Enter:

Command
bash reset.sh redis-lab

Word by word:

  • bash — the program that runs script files.
  • reset.sh — the script file. It lives in the phase1 folder. That is why you must be inside phase1 first.
  • redis-lab — the argument. It tells the script which lab folder to wipe. It is the folder name redis-lab, inside phase1.

What you should see: the script stops both stores and wipes the data, then prints that it is done.

If it breaks: Permission denied means the script is not marked runnable. Runnable means the file is allowed to run as a program. Fix it with the command below, then try again. What this is: chmod +x adds the run permission to a file. Why we run it: without the run permission, your machine refuses to run the script.

Command
chmod +x reset.sh

Word by word: chmod changes file permissions. +x means add the execute (run) permission. reset.sh is the file.

Or, from inside the folder phase1/redis-lab/, the plain way: run the command below. What this is: down -v stops the containers, removes them, and wipes the volumes. That stops both stores and wipes the data. The data was fake.

Command
docker compose down -v

One honest note: after this drill you have two main stores, redis-a and redis-b, and they do not talk to each other. A value saved on one does not appear on the other. That is why the reset matters. Start fresh before the next lab.

Save your proof

The proof for this lab is the promoted copy: role:master in its replication info, and the counter value it holds. Save both with these commands, run from inside the folder phase1/redis-lab/, after the drill.

First, make the proof folder if it does not exist. Type this and press Enter:

Command
mkdir -p ../portfolio/proof

Word by word:

  • mkdir — short for "make directory". It makes a new folder.
  • -p — make the parent folders too, if they are missing, and do not complain if the folder already exists.
  • ../portfolio/proof — the path to the folder. The two dots .. mean "go up one folder". You are in phase1/redis-lab/. .. takes you up to phase1/. Then portfolio/proof takes you down into the portfolio folder, then into the proof folder inside it. So the full folder is phase1/portfolio/proof/.

Then save the replication info. Type this and press Enter:

Command
docker exec redis-b redis-cli INFO replication > ../portfolio/proof/redis-promoted.txt

Word by word:

  • docker exec redis-b redis-cli INFO replication — ask the copy for its replication info, as in Drill Step 2.
  • > — redirect. It means "send the output into a file, instead of printing it on the screen". It overwrites the file if the file already exists.
  • ../portfolio/proof/redis-promoted.txt — the file to write. It lives in phase1/portfolio/proof/, and its name is redis-promoted.txt.

Then add the counter value to the same file. Type this and press Enter:

Command
docker exec redis-b redis-cli GET orders:count >> ../portfolio/proof/redis-promoted.txt

Word by word:

  • docker exec redis-b redis-cli GET orders:count — read the counter from the copy.
  • >> — redirect and append. It means "add the output to the end of the file, without erasing what is already there". One > overwrites. Two >> appends. That is the difference, and it matters here: the first command used one >, which created the file. This command uses two >>, which adds the counter to the end of the same file.
  • ../portfolio/proof/redis-promoted.txt — the same file as above.

Open the file and check it shows role:master and "3". That file is your proof. The "3" is the counter value from Step 4. If your counter shows a different number because you ran INCR extra times, that number is your proof. It must match what your own counter actually held.

What you should see: nothing in the terminal when you run the save commands. The output went into the file, not the screen. Silence means it worked.

If it breaks: if the file is empty, the drill did not run yet. Do the drill first (Drill Steps 1 to 3 above), then save again.
