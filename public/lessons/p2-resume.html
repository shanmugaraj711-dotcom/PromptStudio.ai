Resume Bullets — From Your Projects, In Simple Words

Phase 2 · The Rest of DevOps

What this is and why it matters

A resume bullet is one fact plus one result, in one line.

Think of it like a scorecard line in a match report: "I built X and it proved Y." Not "I know X". Not "I am good at X". One thing you built, and one thing it proved.

In real hiring, vague bullets get skipped — a bullet that names what you built and what it proved gets read.

This page turns your finished projects into honest bullets you can copy, and only for work you actually did.

One idea per line, before you start:

  • A resume is the one-page summary of your work that you send when you apply for a job.
  • A bullet is one short line in a list, starting with a dot or a dash.
  • One fact plus one result means: what you built, and what it proved. Example: "Built a website in a container (fact) and verified it in a browser (result)."
  • Containerised means "put inside a container". It is the same word as "containerized" with a different spelling. It means the website runs inside a Docker container, not directly on the machine.
  • A mapped port is a door connection: a door on your machine joined to a door inside the container, with -p 8080:80. Door 8080 is on your machine; door 80 is inside the container. Your browser knocks on http://localhost:8080 and reaches the website inside.
  • Local machine means your own computer — not a cloud server, not a shared machine.
  • GitHub Actions is the free automatic worker inside GitHub. It runs steps for you whenever you push code. (Full explanation: the portfolio-projects lesson, Project 2.)
  • The Actions tab is the page on GitHub, inside your repository, that shows pipeline runs. Green means passed, red means failed. A repository is your project folder on GitHub.

The honesty test — read this before you copy any bullet

For every bullet below, ask these three questions. All three must be "yes" before you copy it:

  1. Did I do it? Not watched, not read about — did it, with my own hands, on my own machine.
  2. Can I prove it? Is it on GitHub, in a screenshot, in a log, in a README I wrote?
  3. Can I explain it? If the interviewer says "tell me how you did that", can I walk through the steps out loud?

If any answer is "no", leave the bullet out until it is true. A short resume with five true bullets beats a long resume with twenty borrowed ones. Interviewers test bullets by asking about them — a borrowed bullet collapses at the first question.

The stakes, in plain words: if you write that you did something and you did not, that is lying on a job application. If the employer finds out in the interview — and they will, by asking how — you lose the job and your name is remembered. The lesson's rule "write only what you actually did" is not politeness. It is protection.

Rules before you copy anything

  • Write only what you actually did. Fill in the blanks with your real project details.
  • Never invent numbers, company names, or job titles.
  • One bullet = one fact + one result. Keep each bullet to one line.
  • If a bullet is not true for you yet, leave it out until it is.

From Project 1 — Website in a container

  • Built and ran a containerised website using Docker and nginx, reachable at a mapped port on a local machine.

What the words mean: Built and ran — you wrote the recipe (Dockerfile) and started the container. Containerised website — the website runs inside a Docker container. Docker — the tool that runs containers. nginx (say "engine-x") — the web server program inside the container that answers the browser. Reachable at a mapped port — a browser on your machine can open it, because you joined door 8080 on your machine to door 80 in the container. On a local machine — on your own computer, not on the internet.

Why an employer cares: it proves you can take a website from files to a running container and reach it in a browser. That is the smallest real DevOps job, done end to end.

When it is true: you finished Portfolio Project 1, opened http://localhost:8080, and saw your page.

  • Wrote a Dockerfile that builds the website image from a simple web page.

What the words mean: a Dockerfile is the short text recipe that tells Docker how to build the container. (Full explanation: the portfolio-projects lesson, Project 1, step 2.) The website image is the packed box the recipe produces. A container is the image running. A simple web page is your one index.html file.

Why an employer cares: it proves you understand the recipe, not just the run command.

When it is true: you wrote the two-line Dockerfile yourself and the build worked.

  • [Your detail:] Deployed the site image version [version] and verified it in a browser.

What the words mean: Deployed means put it running somewhere. Here, "somewhere" is your own machine. Image version [version] — the version label you gave the image, the part after the colon. If you built my-site:1.0, the version is 1.0. You find it in the build command you typed: docker build -t my-site:1.0 . Verified it in a browser — you opened the address and saw the page yourself.

Why an employer cares: it proves you checked your own work instead of assuming it worked.

How to fill in the blank: replace [version] with your real tag, for example 1.0. Do not invent a version you never built.

When it is true: you ran the container and opened the page.

From Project 2 — CI/CD pipeline

  • Set up a GitHub Actions pipeline that tests the site, then builds a Docker image on every push to the repository.

What the words mean: Set up — you created the workflow file and pushed it. GitHub Actions pipeline — the automatic chain of steps that runs on GitHub. CI/CD stands for Continuous Integration / Continuous Delivery: the automatic chain that tests and builds on every push. Tests the site, then builds — the order matters. The test step runs first. If the test fails, the build never runs. A pipeline that only builds is not a pipeline that tests. On every push — each time you send code to GitHub with git push, the chain runs again by itself. Repository — your project folder on GitHub.

Why an employer cares: it proves you can make quality checks automatic, so broken code stops itself instead of reaching users.

When it is true: you finished Portfolio Project 2 and watched a run turn green in the Actions tab.

  • Read a failed pipeline log, found the [error you fixed], and fixed it so the pipeline passed.

What the words mean: a failed pipeline log is the printed output of the step that failed, in the Actions tab. You open the failed run, click the failed step, and read the log. [Error you fixed] — the exact error line you found, in your own words. For example: "the test failed because the heading was missing from index.html" or "the build failed because the Dockerfile had a wrong image name".

Why an employer cares: it proves you can read a failure, find the cause, and fix it — the core of the job.

How to fill in the blank: use the break-it-on-purpose step from Portfolio Project 2. That step gives you a real failure, a real error line, and a real fix. If you never broke the pipeline on purpose, you have no true story for this bullet yet — do that step first.

When it is true: you saw a red run, read the log, fixed the one thing, pushed again, and watched it turn green.

  • Kept the project's build history visible in the repository's Actions tab.

What the words mean: Build history — the list of pipeline runs, newest first, each green or red. It is the record that your project was tested every time you pushed. Visible in the Actions tab — anyone who opens your repository on GitHub can click Actions and see the runs.

Why an employer cares: it proves your work is checkable. An employer can open your repository and see the green runs with their own eyes.

When it is true: your repository is public (or shared with the employer) and the Actions tab shows your runs.

From Project 3 — Terraform + monitoring

  • Wrote Terraform files that create a local container setup, and checked with terraform plan that a second run needed no changes.

What the words mean: Terraform files — files ending in .tf that describe what you want. (Full explanation: the portfolio-projects lesson, Project 3, step 2.) Local container setup — containers running on your own machine, created by Terraform, with no cloud account and no bill. terraform plan — the command that shows what would change, without changing anything. "A second run needed no changes" — after the first apply, you ran plan again and it said No changes. Your infrastructure matches the configuration. That line is the proof.

Why an employer cares: it proves you can write infrastructure as code and verify it — not just run a command once and hope.

When it is true: you ran apply, then plan, and saw the "No changes" line.

  • Added Prometheus and Grafana to watch the practice setup, with a chart showing [what your chart shows].

What the words mean: Prometheus collects numbers from your apps. Grafana turns those numbers into charts. Watch the practice setup — the three containers (Prometheus, Grafana, node-exporter) run together and report on each other. [What your chart shows] — what your chart actually showed. A truthful value is: "both monitoring targets are up: Prometheus and the practice machine". That means the up query returned 1 for both targets (1 means up, 0 means down).

Why an employer cares: it proves you can see whether a system is healthy, not just whether it started.

How to fill in the blank: write what your chart actually showed. If both targets were up, write that. If one was down, write that and what you did. Do not write "both targets up" if you never opened Grafana.

When it is true: you finished the monitoring part of Project 3 and saved a screenshot of the chart.

  • Ran the whole practice setup locally with no cloud bill.

What the words mean: The whole practice setup — Terraform plus the monitoring stack. Locally — on your own machine. No cloud bill — you used no paid cloud service. This is a fact about where it ran, not a feature you added. Nothing here ran on a paid service, and you never entered card details anywhere for it.

Why an employer cares: it proves you can learn and build without spending money — a skill employers value in a beginner.

When it is true: everything ran on your machine, and you never entered card details anywhere for it.

From the break-and-fix labs

Each bullet below comes from one break-and-fix lab. The lab is where the true story lives — if you have not done that lab, you do not have the bullet yet. The labs are in phase2/break-and-fix-labs.md.

  • Diagnosed a container that would not start by reading its error message and correcting the image name.

What the words mean: Diagnosed means found the cause by looking, not by guessing. The container never started because the image name in the command was wrong. You read Docker's error ("image not found" or similar), saw the wrong name, and corrected it.

When it is true: you did Lab 1 of the break-and-fix labs.

  • Fixed a port clash by finding the running container and changing the port mapping.

What the words mean: a port clash is when two containers want the same door on your machine — for example, both want door

  1. Only one can have it. You found the running container with docker ps (look at the PORTS column), stopped it or changed your mapping (for example from -p 8080:80 to -p 8081:80 — the same box, a different door on your machine), and the new container started.

When it is true: you did Lab 1 of the break-and-fix labs, second version — the one where a second container tries door 8080 and fails with "port is already allocated".

  • Debugged a container that exited at once by reading its logs and finding the bad command.

What the words mean: Debugged means found the cause step by step. The container stopped at once because its main program finished instantly or crashed. You ran docker logs, read the error, and found the bad command in the Dockerfile or the run command.

When it is true: you did Lab 2 of the break-and-fix labs.

  • Resolved a Git merge conflict by reading the conflict markers and keeping the correct lines.

What the words mean: a merge conflict is when two branches changed the same lines and Git stops to ask you. Conflict markers are the <<<<<<<, =======, >>>>>>> lines Git writes into the file. You read them, picked the right lines, deleted the markers, staged the file, and committed. (Full explanation: the interview-pack lesson, question 4.)

When it is true: you did Lab 4 of the break-and-fix labs.

  • Wrote a small Bash health-check script and made it runnable with chmod.

What the words mean: a Bash script is a text file full of commands, written to be run as a program. A health-check script is a small script that checks whether things are up — for example, the kit's own phase1/kit-doctor.sh, or a script you wrote yourself that checks your containers. Made it runnable with chmod means you ran chmod +x <file> to give it the "allowed to run" mark. (Full explanation: the cheat-sheets lesson, Linux section.)

When it is true: you wrote a script yourself — or ran and understood the kit's phase1/kit-doctor.sh — and made it runnable. If you only watched someone else do it, it is not true yet.

  • Found a missing port mapping when a running container did not answer in the browser.

What the words mean: the container was running (STATUS Up in docker ps), but the browser showed nothing. You checked the PORTS column in docker ps, saw no mapping, and realised the -p 8080:80 part was missing from the docker run command. Logs alone do not prove the browser can reach the app — the port mapping is the door.

When it is true: you did Lab 5 of the break-and-fix labs.

From the Phase 1 labs (data tier)

  • Ran two Kafka clusters on one machine, made a topic, sent and read messages, and copied the topic to the second cluster with MirrorMaker 2.

What the words mean: Kafka clusters — two separate Kafka setups running on your one machine, named kafka-a and kafka-b in the lab. A topic is a named line of messages. You made one called orders. Sent and read messages — you used the producer (sender) and the consumer (reader). MirrorMaker 2 — a Kafka tool that copies a topic from one cluster to another, so the second cluster holds the same messages. "Mirror" means copy. It is the tool the Phase 1 Kafka lab uses for the copy step.

When it is true: you finished the Phase 1 Kafka lab, including the MirrorMaker 2 copy step.

  • Ran a PostgreSQL primary and a standby with WAL streaming, proved the standby had the same data, and promoted it by hand when the primary died.

What the words mean: PostgreSQL is a database. The primary takes writes. The standby (replica) follows it and takes reads only. WAL streaming — the standby reads the primary's Write-Ahead Log (its diary of every change) continuously and copies each change. Proved the standby had the same data — you ran the same read question (SELECT * FROM orders ORDER BY id;) on both and compared the rows. Same rows = same data. Promoted it by hand — you typed the promote command yourself: SELECT pg_promote();, run inside the standby's container. "By hand" means a person typed it, as opposed to Patroni doing it automatically.

When it is true: you finished the Phase 1 PostgreSQL lab, including the failover step (Part 1, Step 5).

  • Ran a Patroni cluster that promoted the standby to leader by itself when the leader stopped.

What the words mean: Patroni is a watcher program. It watches the databases and promotes the standby by itself within seconds when the leader stops. By itself is the key phrase — nobody typed a command. That is the difference from the bullet above, where you promoted by hand. The leader is the database currently taking writes.

When it is true: you finished the Patroni part of the Phase 1 lab (Part 2) and watched the automatic promotion happen.

  • Used Redis as a cache and a counter, with keys that expire by themselves.

What the words mean: Redis is a fast memory store. A cache is a saved copy of an answer, kept close by so you do not have to compute it again. A counter is a number Redis adds to, with INCR. Keys that expire by themselves — values saved with SETEX that delete themselves after a number of seconds. You can check the seconds left with TTL.

When it is true: you finished the Phase 1 Redis lab, including the SETEX and TTL steps.

  • Ran two Moto object stores and set up a mirror that copies new files to the second store by itself.

What the words mean: Moto is a pretend object store that runs on your machine and acts like the real S3 store. An object store keeps whole files by name. A bucket is a named box inside the store that holds files. A mirror is a program that watches the first store and copies each new file to the second store automatically. "By itself" means nobody copies by hand. In the lab the mirror is the mirror.sh script, which runs in the mirror container and copies files every 10 seconds.

When it is true: you finished the Phase 1 object-store lab, including the mirror step, and saw a file appear in the second store.

  • Ran NGINX as a load balancer in front of three backends, killed one backend, and the site stayed up.

What the words mean: NGINX is the program doing the balancing. A load balancer stands in front of copies of your app and sends each visitor to a different copy. A backend is one copy of your app behind the balancer. There are three in the lab (web1, web2, web3). Killed one backend — you stopped one backend container with docker compose stop web2. The site stayed up — the balancer skipped the dead copy and used the two still alive, so visitors still got answers.

When it is true: you finished the Phase 1 load-balancer lab, including the kill-one-backend step.

  • Built an end-to-end pipeline where a fake order flows through an object store, Kafka, PostgreSQL and Redis, behind a load balancer — then proved failover by killing the main database and sending a new order through the standby.

What the words mean: End-to-end means the whole journey, from start to finish, in the lab's own order: a fake order file lands in a folder, is stored in Moto, sent to Kafka, saved in PostgreSQL, counted in Redis — while NGINX spreads visitors across three backends. Proved failover means you killed the main database, promoted the standby with pg_promote(), pointed a fresh worker at it, and sent a fifth order through the new main database — and it worked. The proof is the fifth order's row in the new main database, not your word. Fake order — the orders are pretend (notebook, pen, mug). That is the point: no real data was used.

When it is true: you finished Project 4, including the failover step, and have the filled proof files to show for it. The kit's templates are phase1/portfolio/proof/end-to-end-trace-TEMPLATE.txt and phase1/portfolio/proof/failover-log-TEMPLATE.txt — fill in a copy with your real run.

A short summary you can adapt

"Beginner DevOps learner. Built a containerised website, a CI/CD pipeline, a Terraform + monitoring demo, and a data pipeline with a proven failover, all on GitHub. Can read logs, fix failed builds, and explain my own projects."

What the words mean:

  • "Proven failover" means you did the failover step and have the proof (the fifth order's row in the new main database). It does not mean "I read about failover".
  • "Can read logs, fix failed builds, and explain my own projects" — three claims. Each one must be true: you have read logs and found errors, you have fixed a failed build, and you can explain each project out loud.

How to adapt it: delete any project you have not finished yet. If you have finished two of the four, the summary names two. A short true summary beats a long borrowed one.

What NOT to write

  • Do not write "expert" or "experienced DevOps engineer" unless a real job gave you that role. "Beginner DevOps learner" is the honest title, and it is a strong one — it says you know where you stand.
  • Do not list tools you only watched videos about. List tools you actually ran. Watching is not doing.
  • Do not copy someone else's project description. Yours is smaller and true — that is better.
  • Do not write numbers you did not measure. If you did not count it, do not state it.
  • Do not write a company name or a job title you never held.

The test, one more time: for each line on your resume, imagine the interviewer pointing at it and saying "tell me about this one". If you can tell the story — what you built, what broke, how you found it, how you fixed it, how you proved it — the line stays. If you cannot, the line goes. That is the whole rule.
