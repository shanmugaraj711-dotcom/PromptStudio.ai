PostgreSQL Lab — Main Database, Standby, Failover

Phase 1 · The Data Tier

What this is and why it matters

PostgreSQL is the main record book. It is a record store that keeps real records in tables and keeps them safe.

Think of it like a shop's big record book.

  • Each page is a table.
  • Each line on a page is one row: one order, with its number, its item, and its price.
  • The shop writes every new order in the book.
  • If the book is lost, every order is lost.

In real systems, the failure that hurts most is the main record store dying and taking every record with it.

This lab stops that from being the end of the story. You run two copies on your own computer: a main one and a standby copy that follows it live. You write fake orders into the main one, watch them appear on the standby, then kill the main one and promote the standby so work can continue. The last part shows Patroni — a watcher that does the promotion for you, by itself.

One idea per line, in order:

  • A record store keeps records in tables.
  • A table is a grid of rows and columns, like a spreadsheet page.
  • A row is one record in a table. Example: one order.
  • A column is one kind of detail. Example: the item name.
  • The main copy is called the primary. It takes writes.
  • A write is adding or changing a record.
  • The standby copy is called the replica. It takes reads only.
  • A read is asking for a record without changing it.
  • The replica copies every change from the primary, live.
  • Failover is the standby taking over as the new primary.

All data in this lab is fake: made-up orders, made-up names, made-up prices.

What this lab is

You will run two PostgreSQL record stores on your own machine: a main one (primary) and a standby copy (replica). You will write fake orders into the main one, watch them appear on the standby, then kill the main one and promote the standby so work can continue. The last part shows Patroni — a watcher that does the promotion for you.

What you need first

  • Docker running. Lesson 0 shows how to install it and check it.
  • The files in the folder phase1/postgresql-lab/ — verified on disk: docker-compose.yml, 01-replicator.sql, replica-entrypoint.sh, plus the folder phase1/postgresql-lab/patroni/. The patroni/ folder is used only in the last part. It holds Dockerfile, docker-compose.yml, patroni-1.yml, and patroni-2.yml, all verified on disk.
  • Do Lesson 0 first if you have not. Do the Kafka lab first if you are following the phase order.

Words you need, before you use them

  • PostgreSQL. The record store used in this lab. People often shorten its name to Postgres. The image name is postgres:16-alpine. The 16 is the version number. The word alpine means a small, light version of the recipe.
  • Primary — the main record store. It takes writes (new rows).
  • Replica / standby — a copy that follows the primary. It takes reads only. It becomes the new primary on failover.
  • WAL — short for write-ahead log. A list of every change, written down first, before the real data changes. The replica reads this list to stay in sync. WAL streaming means the replica reads the list live, as changes happen.
  • Replication slot — a bookmark the primary keeps, so it does not throw away WAL entries the replica still needs.
  • Failover — the standby taking over as the new primary.
  • Patroni — a program that watches the record stores and does the failover by itself.
  • etcd — a small notebook service that all the Patroni nodes share. Patroni writes "who is the leader right now" in etcd, so every node agrees. You do not type commands into etcd in this lab. It runs in the background as a third container in the Patroni folder.
  • Leader — the Patroni word for the primary. The leader takes writes. The other node is the replica.
  • Bootstrap — the first-time setup of a Patroni cluster. When Patroni starts for the first time, its bootstrap creates the record store from scratch. That is why the Patroni part uses a record store called postgres (the default name) instead of practice. The bootstrap does not create a store called practice.
  • JSON — short for JavaScript Object Notation. It is a plain-text way of writing structured data, with names in quotes and values after a colon, inside curly brackets. Example: {"name": "patroni-1", "role": "leader"} means the member named patroni-1 has the role leader. You do not need to learn JSON. You only need to find the role line in the cluster output.
  • curl — a small tool that asks a web address for its text and prints the answer in your terminal. If curl is not installed on your machine, open the same address in your browser instead — you see the same text.
  • Service — one running program in a Docker Compose file. Container is the sealed box that runs it. The two names are different, and this lab uses both. Example: the service is called primary, and its container is called pg-primary. The service name is what you use in docker compose stop primary. The container name is what you use in docker exec pg-primary ....
  • Volume — a named place on your machine where Docker keeps a container's data. The data lives in a volume, so it survives a restart. Wiping the volume wipes the data.
  • SQL — the language you use to talk to a record store. SQL commands end with a semicolon ;. CREATE TABLE makes a table. INSERT INTO adds rows. SELECT reads rows.
  • psql — the command-line tool for talking to PostgreSQL. It runs inside the container.
  • pg_basebackup — a PostgreSQL tool that copies all the data from a primary to make a new standby. The replica's start-up script uses it. You do not type it yourself in this lab.
  • pg_rewind — a PostgreSQL tool, mentioned in the "does NOT cover" section, that lets an old primary rejoin faster after a failover. The plain lab in Part 1 does not use it. That is why the old primary must be rebuilt there.
  • Practice logins — all logins in this lab are practice logins on your own machine, for learning only. The login name is learner. The practice password is set in the file phase1/postgresql-lab/docker-compose.yml. Never use these passwords anywhere real. You do not type the password in the commands below, because the commands run inside the container, where the login is already set up.

The two files you never type, but need to understand

phase1/postgresql-lab/01-replicator.sql

What this is: a short SQL file that runs once, when the primary record store is first created. Why it exists: it makes a special user called replicator. The replica uses that user to copy data. That user can read the change log (the WAL) and nothing else. The file sets a practice password for that user. You never open this file. The primary container runs it by itself the first time it starts. If this file is not readable, the primary fails to start. That is why Step 1 runs chmod first.

phase1/postgresql-lab/replica-entrypoint.sh

What this is: the replica's start-up script. A script is a saved list of commands in one file. Why it exists: it tells the replica what to do when it starts. In order, it (1) waits until the primary answers, (2) if the replica has no data yet, copies all data from the primary with pg_basebackup, and prints Copy done., and (3) starts PostgreSQL as a standby. If the replica already has data, step 2 is skipped. You never type this script's commands yourself. The replica container runs it by itself. The log line Copy done. in Step 1 comes from this script.

The doors (ports) in this lab

  • Part 1: the primary answers on door 5432 on your machine. The replica answers on door 5433 on your machine. Inside its own container, the replica still uses door 5432, but from outside you reach it on 5433. That is why two copies can run on one machine without fighting over the same door.
  • Part 2 (Patroni): patroni-1 answers on door 5432 for the record store and door 8008 for its status page. patroni-2 answers on door 5433 for the record store and door 8009 for its status page. The status page is the web address you ask with curl. Door 8008 asks patroni-1's status page. Door 8009 asks patroni-2's status page. Both pages show the same whole cluster, so either one tells you who the leader is.

Part 1 — Primary and replica

Step 1 — Start both record stores

First, move your terminal into the lab folder. The folder is phase1/postgresql-lab/. Open your terminal in that folder. If your terminal opens somewhere else, move into it first with cd followed by the path to that folder on your machine.

What this step is: two commands. The first makes the setup file readable. The second starts both record stores. Why we run them: the record store runs as its own user, and it cannot read a file that is private to you. The chmod command fixes that. Then Compose starts the primary and the replica together.

Type this first, then press Enter:

Try it Yourself »Open the practice terminal and run it yourself — nothing installs. Included with Phase 1. Simulation — practice version. Run the real lab with Docker to do it for real.
Command
chmod -R a+r .

Word by word:

  • chmod — short for "change mode". It changes who can read a file.
  • -R — means do this for every file in this folder, and in every folder inside it.
  • a+r — means everyone can read. The letter a means all users. The letter r means read. The + means add this permission.
  • . — means this folder, the one your terminal is in right now. A single dot is shorthand for "here".

What you should see: nothing. chmod prints nothing when it works. That is normal. Silence means it worked.

If it breaks: No such file or directory means you are in the wrong folder. Run ls and check you are inside the postgresql-lab folder, then try again. ls is a command that lists the files in the folder your terminal is in. You should see docker-compose.yml, 01-replicator.sql, and replica-entrypoint.sh in that list.

Then start both record stores. Type this, then press Enter:

Command
docker compose up -d

Word by word:

  • docker — the Docker tool.
  • compose — the part of Docker that starts several containers together from one file.
  • up — start everything listed in the file.
  • -d — short for detached. It means run in the background and give me my terminal back, instead of filling my screen with logs.

What you should see, line by line:

Command
[+] Running 2/2
 ✔ Container pg-primary  Started
 ✔ Container pg-replica  Started
  • [+] Running 2/2 — 2 out of 2 containers are running.
  • Container pg-primary Started — the primary container started.
  • Container pg-replica Started — the replica container started.
  • How to tell it worked: both lines say Started.

Now check they are both up. What this is: ps lists the containers Compose is running. Why we run it: the start lines scroll past fast, and this check proves both containers are still up right now.

Type this, then press Enter:

Command
docker compose ps

Word by word:

  • docker compose — the Docker Compose tool, as above.
  • ps — short for "process status". It lists the running containers.

What you should see: a table with pg-primary and pg-replica, each with STATUS Up. The real table has more columns than the example below. What matters is both names, each with STATUS Up.

Command
NAME          STATUS
pg-primary    Up
pg-replica    Up

The replica copies all data from the primary the first time it starts, so it takes about a minute. Check its log. What this is: logs shows what a container has printed. Why we run it: the replica's start-up script prints Copy done. when the first copy finishes. That line is the proof the copy finished.

Type this, then press Enter:

Command
docker compose logs replica

Word by word:

  • docker compose — the Docker Compose tool, as above.
  • logs — show the printed output (the log) of a container.
  • replica — the service name of the replica. Service names, not container names, go after logs.

What you should see, near the end of the log:

Command
No data here yet. Copying from the primary...
Copy done.
  • No data here yet. Copying from the primary... — the replica had no data, so it is copying all of it from the primary.
  • Copy done. — the first copy finished. That is the line that matters.

If it breaks: if the replica log shows waiting for the primary for more than two minutes, check the primary is up with docker compose ps. If the primary is up and the replica still waits, read the replica log from the top. The error line is usually about the password or the connection.

Step 2 — Write three fake rows on the primary

What this is: one long command that connects to the primary and runs SQL inside it. Why we run it: it creates a small table and puts three fake orders in it, so the next steps have something to copy and read.

Type this, then press Enter:

Command
docker exec pg-primary psql -U learner -d practice -c "CREATE TABLE orders (id INT, item TEXT, amount INT); INSERT INTO orders VALUES (101, 'notebook', 250), (102, 'pen', 40), (103, 'mug', 350);"

Word by word:

  • docker exec — run a command inside a container that is already running. exec means execute, or run.
  • pg-primary — the container name. This is the primary container. Check the name: pg-primary, not pg-replica.
  • psql — the tool for talking to PostgreSQL. It runs inside the container.
  • -U learner — log in as the user named learner. The -U flag means "user". learner is the practice login name.
  • -d practice — use the record store named practice. The -d flag means "database". practice is the name of the practice store.
  • -c "..." — run the SQL inside the quotes, then stop. The -c flag means "command". Everything inside the double quotes is one SQL command string.
  • Inside the quotes, the SQL itself, in order:
  • CREATE TABLE orders (id INT, item TEXT, amount INT); — make a table called orders. It has three columns. id holds a whole number (INT means integer, a whole number). item holds text (TEXT means text). amount holds a whole number. The semicolon ; ends one SQL command.
  • INSERT INTO orders VALUES (101, 'notebook', 250), (102, 'pen', 40), (103, 'mug', 350); — add three rows to the orders table. Row 101 is a notebook for 250. Row 102 is a pen for 40. Row 103 is a mug for 350. The numbers are fake prices in the lab's made-up units. VALUES means "here are the values to add".

What you should see, line by line:

Command
CREATE TABLE
INSERT 0 3
  • CREATE TABLE — the table was made.
  • INSERT 0 3 — 3 rows went in. The 0 is a counter PostgreSQL prints; the 3 is the number of rows added. That is the number that matters.
  • The data is fake — made up for this lab.

If it breaks: relation already exists means you already made the table. Relation is PostgreSQL's word for a table. Skip the CREATE part and just run the INSERT, or drop the table first with DROP TABLE orders; and start this step again. DROP TABLE means delete the whole table.

Step 3 — Read the same rows from the replica

What this is: the same kind of command, but aimed at the replica instead of the primary. Why we run it: it proves the replica already has the same rows, because it follows the primary live.

Type this, then press Enter:

Command
docker exec pg-replica psql -U learner -d practice -c "SELECT * FROM orders ORDER BY id;"

Word by word:

  • docker exec pg-replica — run a command inside the replica container. Check the name: pg-replica, not pg-primary.
  • psql -U learner -d practice — talk to PostgreSQL as user learner, in the store named practice, as in Step 2.
  • -c "SELECT * FROM orders ORDER BY id;" — run this SQL. SELECT means read. The star * means all columns. FROM orders means from the orders table. ORDER BY id means sort the rows by their id number, smallest first.

What you should see, line by line:

Command
 id  |   item   | amount
-----+----------+--------
 101 | notebook |    250
 102 | pen      |     40
 103 | mug      |    350
(3 rows)
  • The first line is the column names: id, item, amount.
  • The second line is a divider made of dashes and plus signs. It is only decoration.
  • Then the three rows, in id order: 101 notebook 250, 102 pen 40, 103 mug 350.
  • (3 rows) — three rows were returned. That is the number that matters.
  • How to tell it worked: the replica shows the same three rows you wrote on the primary. The copy is live.

If it breaks: if the replica shows 0 rows, wait 10 seconds and try again — the copy takes a moment. If it still shows 0 rows, check the replica is really a replica. Type this, then press Enter:

Command
docker exec pg-replica psql -U learner -d practice -c "SELECT pg_is_in_recovery();"

Word by word: SELECT pg_is_in_recovery(); means "ask: are you in recovery mode?" Recovery mode means "I am a standby, following a primary, not taking writes". You should see t, which means true. If it shows f, which means false, the replica is not following the primary. Stop and start it again with the command below. What this is: restart stops a service and starts it again. Why we run it: a fresh start makes the replica follow the primary again.

Command
docker compose restart replica

Word by word: docker compose restart replica — restart the service named replica.

Step 4 — Try to write on the replica (it must refuse)

What this is: an insert command aimed at the replica. Why we run it: a standby takes reads only. Trying a write and watching it fail is the proof. The error is the expected result. Do not try to fix it.

Type this, then press Enter:

Command
docker exec pg-replica psql -U learner -d practice -c "INSERT INTO orders VALUES (104, 'pen stand', 120);"

Word by word: INSERT INTO orders VALUES (104, 'pen stand', 120); means add one row to the orders table: id 104, item pen stand, amount 120.

What you should see:

Command
ERROR:  cannot execute INSERT in a read-only transaction
  • ERROR: — the command failed.
  • cannot execute INSERT in a read-only transaction — the replica refuses writes because it is read-only. A transaction is one batch of work the record store does together.
  • How to tell it worked: you see this error. The error IS the proof. The replica refuses writes. This is correct and expected.

If it breaks: if you see INSERT 0 1 instead of the error, you ran it on the primary by mistake. Check the container name in the command (pg-replica, not pg-primary) and try again.

Step 5 — Kill the primary and promote the replica

What this is: first stop the primary, then check the replica still answers, then promote the replica to be the new primary. Why we do it: this is failover by hand. It proves the data survived on the replica, and the replica can take over.

First, stop the primary. Type this, then press Enter:

Command
docker compose stop primary

Word by word:

  • docker compose stop — stop a service, but do not delete it. stop is different from down: stop leaves the container in place so you can start it again; down removes the containers.
  • primary — the service name. Use the service name here, not the container name pg-primary.

What you should see:

Command
✔ Container pg-primary  Stopped
  • The tick ✔ means done. Container pg-primary Stopped means the primary container stopped.

If it breaks: No such container means the name is wrong. Run docker compose ps and use the name it shows.

Now check the replica still answers reads. Type this, then press Enter:

Command
docker exec pg-replica psql -U learner -d practice -c "SELECT * FROM orders ORDER BY id;"

This is the same read command as Step 3. What you should see: the same 3 rows, 101, 102, and 103. The data survived — the replica has its own copy.

Now promote the replica to be the new primary. What this is: pg_promote() is a PostgreSQL function that tells a standby "stop following, become the primary". Why we run it: without this command, the replica stays a read-only standby forever. This command is the failover.

Type this, then press Enter:

Command
docker exec pg-replica psql -U learner -d practice -c "SELECT pg_promote();"

Word by word: SELECT pg_promote(); means run the promote function and show its answer.

What you should see:

Command
 pg_promote
------------
 t
  • pg_promote is the name of the answer column.
  • t means true. True means the promotion worked.

Check it is no longer in recovery. Type this, then press Enter:

Command
docker exec pg-replica psql -U learner -d practice -c "SELECT pg_is_in_recovery();"

What you should see:

Command
 pg_is_in_recovery
-------------------
 f
(1 row)
  • f means false. False means it is no longer in recovery. It is now a primary.
  • (1 row) means one answer row was returned.

Prove it takes writes now. Type this, then press Enter:

Command
docker exec pg-replica psql -U learner -d practice -c "INSERT INTO orders VALUES (104, 'pen stand', 120); SELECT * FROM orders ORDER BY id;"

Word by word: this runs two SQL commands in one -c string. First the INSERT adds row 104. Then the SELECT reads all rows in id order.

What you should see, line by line:

Command
INSERT 0 1
 id  |   item    | amount
-----+-----------+--------
 101 | notebook  |    250
 102 | pen       |     40
 103 | mug       |    350
 104 | pen stand |    120
(4 rows)
  • INSERT 0 1 — 1 row went in. The write worked.
  • Then 4 rows, including 104 | pen stand | 120.
  • (4 rows) — four rows returned. That is the number that matters.
  • Failover done — by hand.

If it breaks: if pg_promote() shows f, the replica was already promoted. That happens if you ran this step twice. Check with SELECT pg_is_in_recovery();. If it shows f, you are done.

Step 6 — The honest part: the old primary cannot just rejoin

What this is: a plain explanation, not a command. The old primary still has the old data. It does not know about row 104. It cannot rejoin as a replica by itself. In real work, you rebuild it from the new primary, the same way the replica was first built: copy the data with pg_basebackup, then start it as a standby. The commands are the same as the ones in the file phase1/postgresql-lab/replica-entrypoint.sh, which you read about above. For this lab, the simple way back is to wipe both and start fresh.

Type these two commands, one at a time, pressing Enter after each:

Command
docker compose down -v
docker compose up -d

Word by word:

  • docker compose down — stop the containers and remove them. down is stronger than stop: stop leaves the containers in place, down removes them.
  • -v — also wipe the volumes. A volume is the named place where the data lives. Without -v, the data survives in the volume and comes back. With -v, the data is wiped.
  • docker compose up -d — start everything again in the background, as in Step 1.

What you should see: the containers stop, the data is wiped, then both record stores start fresh with STATUS Up. Check with docker compose ps if you want to see the Up status again.

If it breaks: if up -d fails with port is already allocated, the old containers did not stop yet. Port is already allocated means door 5432 or 5433 is still held by an old container. Wait a few seconds and run docker compose up -d again.

That wipes both record stores and starts fresh. The data was fake, so losing it is fine.

Part 2 — Patroni does the failover for you (advanced)

What Patroni is

In Part 1 you promoted the replica by hand. Patroni is a watcher program that does that job by itself: it watches the main record store, and if it dies, Patroni promotes the standby within seconds. It keeps its notes in etcd — a small notebook service that all the Patroni nodes share. You do not type commands into etcd. It starts by itself as a third container in the Patroni folder.

Do Part 1 first. Part 2 is a separate cluster in a separate folder. Do not run Part 1 and Part 2 at the same time on the same doors, because both want door 5432. Stop Part 1 first with docker compose down from inside the phase1/postgresql-lab/ folder, or the Patroni start will fail with port is already allocated.

Step 1 — Start the Patroni cluster

First, move your terminal into the Patroni folder. The folder is phase1/postgresql-lab/patroni/. From inside phase1/postgresql-lab/, type cd patroni and press Enter.

What this is: start the Patroni cluster and build its image the first time. Why we run it: the cluster is two Patroni nodes plus etcd. The first start builds the Patroni image from the file phase1/postgresql-lab/patroni/Dockerfile, so it takes a few minutes.

Type this, then press Enter:

Command
docker compose up -d --build

Word by word:

  • docker compose up -d — start everything in the background, as in Part 1, Step 1.
  • --build — build the image first, before starting. Build means turn the Dockerfile recipe into a runnable image. Without --build, Compose would reuse an old image. The first start needs the build.

What you should see: the build lines scroll past, then both Patroni nodes start. The first start builds the Patroni image, so it takes a few minutes.

Now check the cluster. What this is: curl asks the status page for its text. Why we run it: the status page tells you who the leader is and who the replica is.

Type this, then press Enter:

Command
curl http://localhost:8008/cluster

Word by word:

  • curl — a small tool that asks a web address for its text and prints the answer.
  • http://localhost:8008/cluster — the address. http:// means a web page. localhost means this machine. 8008 is the door number of patroni-1's status page. /cluster means "show me the cluster".

What you should see: JSON with two members, one with "role": "leader" and one with "role": "replica". JSON is a plain-text way of writing structured data. The real answer is longer than the example below. The two lines that matter are the role lines.

Command
{ "members": [
  {"name": "patroni-1", "role": "leader"},
  {"name": "patroni-2", "role": "replica"} ] }
  • {"name": "patroni-1", "role": "leader"} — patroni-1 is the leader. The leader takes writes.
  • {"name": "patroni-2", "role": "replica"} — patroni-2 is the replica. It follows the leader.
  • How to tell it worked: one member says "role": "leader" and the other says "role": "replica".

If curl is not installed on your machine, open http://localhost:8008/cluster in your browser instead. You see the same text.

If it breaks: if the page does not load, wait a minute. The first node builds the record store from scratch. Check the logs with the command below. What this is: logs shows what a container printed. The service name here is patroni-1.

Command
docker compose logs patroni-1

Step 2 — Write a row, watch it copy

What this is: write one fake row on the leader, then read it from the second node. Why we run it: it proves the second node copies the leader's data.

Type this, then press Enter:

Command
docker exec patroni-1 psql -U learner -d postgres -c "CREATE TABLE orders (id INT, item TEXT); INSERT INTO orders VALUES (201, 'stapler');"

Word by word:

  • docker exec patroni-1 — run a command inside the container named patroni-1. This is the leader.
  • psql -U learner — talk to PostgreSQL as user learner.
  • -d postgres — use the record store named postgres. This is the default store name. Patroni's first-time setup (its bootstrap) does not create a store called practice. That is why the name is different from Part 1, where the store was called practice.
  • -c "CREATE TABLE orders (id INT, item TEXT); INSERT INTO orders VALUES (201, 'stapler');" — make a table called orders with two columns (id, a whole number; item, text), then add one row: id 201, item stapler.

What you should see:

Command
CREATE TABLE
INSERT 0 1
  • CREATE TABLE — the table was made.
  • INSERT 0 1 — 1 row went in.

Now read it from the second node. Type this, then press Enter:

Command
docker exec patroni-2 psql -U learner -d postgres -c "SELECT * FROM orders;"

Word by word: run a command inside the container named patroni-2, and read all rows from the orders table. There is no ORDER BY here because there is only one row.

What you should see:

Command
 id  |  item
-----+---------
 201 | stapler
(1 row)
  • One row: 201, stapler.
  • (1 row) — one row returned.

If it breaks: if the second node shows 0 rows, wait 10 seconds and try again — the copy takes a moment. If it still shows 0 rows, check the cluster with curl http://localhost:8008/cluster and confirm one member is the leader.

Step 3 — Kill the leader and watch Patroni promote the other one

What this is: stop the leader, wait, then check the cluster again on the second node's status page. Why we do it: this is the whole point of Patroni. Nobody promotes the standby by hand. Patroni does it by itself.

Type this, then press Enter:

Command
docker compose stop patroni-1

Word by word: docker compose stop patroni-1 — stop the service named patroni-1. stop leaves the container in place so you can start it again later.

What you should see:

Command
✔ Container patroni-1  Stopped

Wait 30 seconds. Then check the cluster again. Type this, then press Enter:

Command
curl http://localhost:8009/cluster

Word by word: curl asks the status page, as in Step 1. This time the door is 8009, which is patroni-2's status page. You ask patroni-2 because patroni-1 is stopped and cannot answer. Both status pages show the same whole cluster.

What you should see: patroni-2 now has "role": "leader". The real answer is longer. The lines that matter are the role lines.

Command
{ "members": [
  {"name": "patroni-2", "role": "leader"},
  {"name": "patroni-1", "role": "replica"} ] }
  • patroni-2 is now the leader.
  • patroni-1 is listed as a replica. It is stopped, so it is not really following yet. It becomes a real replica again when you start it in Step 4.
  • Patroni promoted it by itself. No command from you did the promotion.

Prove the new leader takes writes. Type this, then press Enter:

Command
docker exec patroni-2 psql -U learner -d postgres -c "INSERT INTO orders VALUES (202, 'ruler'); SELECT * FROM orders;"

Word by word: inside the container named patroni-2, add row 202 (ruler), then read all rows.

What you should see:

Command
INSERT 0 1
 id  |  item
-----+---------
 201 | stapler
 202 | ruler
(2 rows)
  • INSERT 0 1 — 1 row went in.
  • Both rows are there: 201 stapler, 202 ruler.
  • (2 rows) — two rows returned.

If it breaks: if patroni-2 still shows "role": "replica" after a minute, Patroni has not finished the promotion yet. Wait another minute and check again. If it never changes, read the logs with docker compose logs patroni-2.

Step 4 — Bring the old leader back

What this is: start the old leader again and watch it rejoin as a replica. Why we do it: it proves Patroni also handles the return. The old leader does not fight for the top job. It rejoins as a follower and copies the new data.

Type this, then press Enter:

Command
docker compose start patroni-1

Word by word:

  • docker compose start — start a service that was stopped with stop. start is different from up: up creates and starts containers from the file; start only starts containers that already exist and were stopped.
  • patroni-1 — the service name.

What you should see:

Command
✔ Container patroni-1  Started

Wait a minute, then check the cluster. Type this, then press Enter:

Command
curl http://localhost:8008/cluster

What you should see: patroni-1 back, now as a "replica", and patroni-2 still the leader.

Command
{ "members": [
  {"name": "patroni-1", "role": "replica"},
  {"name": "patroni-2", "role": "leader"} ] }
  • patroni-1 rejoined by itself and copied the new data from the leader.
  • That is what Patroni is for.

If it breaks: if patroni-1 does not come back, read its log with docker compose logs patroni-1. The error line names the problem.

Clean up — Part 2

What this is: stop everything and wipe the data. Why we run it: the data was fake, and the next run should start fresh.

Type this, while you are inside the phase1/postgresql-lab/patroni/ folder, then press Enter:

Command
docker compose down -v

Word by word: docker compose down stops the containers and removes them. -v also wipes the volumes, so the data is gone.

What you should see: the Patroni containers stop and the data is wiped.

If it breaks: No such container means the services are already stopped. Nothing to do.

That stops everything and wipes the data. The data was fake.

What you can now say, truthfully

"I ran a PostgreSQL primary and a standby with WAL streaming, proved the standby had the same data, promoted it by hand when the primary died, and ran a Patroni cluster that did the same failover by itself."

What this lab does NOT cover

  • Real clusters run three or more record store nodes, not two.
  • pg_rewind (used in the Patroni setup) lets an old primary rejoin faster. The plain lab in Part 1 does not use it. That is why the old primary must be rebuilt there.
  • Backups are a different job from replication. Replication protects you when a machine dies. Backups protect you when data is deleted by mistake. You need both in real work.

Save your proof

The proof for this lab is the failover log: the cluster output showing the new leader, and the row count before and after.

Save the cluster output with this command, run from inside the patroni/ folder, after the drill. What this is: two commands joined by a redirect. Why we run it: it saves the cluster output into a file, instead of printing it on the screen.

First, make the proof folder if it does not exist. Type this and press Enter:

Command
mkdir -p ../../portfolio/proof

Word by word:

  • mkdir — short for "make directory". It makes a new folder.
  • -p — make the parent folders too, if they are missing, and do not complain if the folder already exists.
  • ../../portfolio/proof — the path to the folder. Each .. means "go up one folder". You are in phase1/postgresql-lab/patroni/. The first .. takes you up to phase1/postgresql-lab/. The second .. takes you up to phase1/. Then portfolio/proof takes you down into the portfolio folder, then into the proof folder inside it. So the full folder is phase1/portfolio/proof/.

Then save the cluster output. Type this and press Enter:

Command
curl http://localhost:8009/cluster > ../../portfolio/proof/failover-log.txt

Word by word:

  • curl http://localhost:8009/cluster — ask patroni-2's status page for the cluster text, as in the drill.
  • > — redirect. It means "send the output into a file, instead of printing it on the screen". It overwrites the file if the file already exists.
  • ../../portfolio/proof/failover-log.txt — the file to write. It lives in phase1/portfolio/proof/, and its name is failover-log.txt.

What you should see: nothing in the terminal when you run the save command. The cluster output went into the file, not the screen. Silence means it worked.

A note on the template: the folder phase1/portfolio/proof/ also holds a file called failover-log-TEMPLATE.txt, verified on disk. That template is the full format for the proof. Read this carefully: the curl command above already creates a file called failover-log.txt with the raw cluster output. If you copy the template over that same name, it overwrites the saved cluster output. So do one or the other. Either keep the raw saved output as your proof, or copy the template to a new name and fill it in by hand with the cluster output and the row counts. Do not copy the template over the file you just saved unless you have already pasted the cluster output into it.

If it breaks: if the file is empty, the cluster was not up on port 8009 when you ran it. Check the cluster with curl http://localhost:8009/cluster first, then save again.
