Object Store Lab — A File Cupboard

Phase 1 · The Data Tier

What this is and why it matters

An object store is a big file cupboard. You put a file in by giving it a name. You ask for the file back by using the same name. The cupboard does not care what is inside the file. A photo, a receipt, a video — to the cupboard, each one is just a named file.

A bucket is one named box inside the cupboard. Files live inside buckets. This lab uses one bucket called incoming. Think of a labelled drawer: the cupboard is the store, the drawer is the bucket, the files are the papers inside the drawer.

In this lab you run TWO cupboards on your own machine. You put fake receipt files into the first cupboard. A helper called the mirror copies every new file into the second cupboard by itself. You never copy anything twice. If the first cupboard breaks, the copy in the second cupboard is still there. That is the whole point: one copy is risky, two copies are safe.

All files in this lab are fake. Nothing here is a real receipt, a real order, or real money.

What this lab is

You will run two file stores on your own machine with Moto — a free S3-compatible stand-in that works the same way as the paid stores. You will put fake receipt files into the first store and watch them appear in the second store by themselves. All files are fake.

Words you need here

Read this list first. Every word below is used in the steps. Nothing here is used before it is defined.

  • Docker — a tool that runs small sealed boxes on your machine. Each box holds one program and everything that program needs. You need Docker running before Step 1. How to check is in "What you need first" below.
  • Container — one sealed box run by Docker. In this lab there are four boxes: moto-a, moto-b, mirror, and awscli. Each box does one job.
  • Image — the recipe Docker uses to build a box. A box is a running image. The awscli box is built from a small image described in the file Dockerfile.
  • Service — one named job in the file docker-compose.yml. Each service becomes one container. The four services here are moto-a, moto-b, mirror, and awscli.
  • docker-compose.yml — a recipe file. It lists the four services, what image each one uses, and how they talk to each other. It lives in the folder phase1/object-store-lab.
  • Dockerfile — a second recipe file. It tells Docker how to build the small aws image used by the awscli and mirror boxes. It lives in the same folder.
  • mirror.sh — a small script file. It is the mirror's job list: wait for both stores, make the bucket on both sides, then copy new files from the first store to the second every 10 seconds. It lives in the same folder. You never run it yourself — the mirror box runs it.
  • Object store — a big file cupboard. You store a file by a name and ask for it back by the same name.
  • Bucket — a named box inside the store. Files live in buckets. This lab uses one bucket called incoming.
  • Moto — a free stand-in for Amazon S3. S3 is a paid file-cupboard service. Moto speaks the same S3 language, so what you learn here transfers to the real thing. Moto keeps everything in memory: stop the lab and the files are gone. That is fine for learning.
  • S3 — the name of the paid file-cupboard service this lab copies. You do not need an S3 account. Moto pretends to be S3 on your own machine.
  • aws — the command tool for S3 stores. It works like the cp (copy) and ls (list) commands, but for buckets. Every command below says which store it talks to.
  • Endpoint — the address of one store. The first store's address inside the boxes is http://moto-a:5000. The second store's address is http://moto-b:5000. The number 5000 is the door number the store listens on inside its box.
  • Port — a door number on a machine. On your own machine the first store is reached on door 9000 and the second on door 9010. Inside the boxes, both stores listen on door 5000. That is why the commands below use 5000: they run inside a box, not on your machine directly.
  • Mirror — a copy that follows the original. When a new file lands in the first store, the mirror copies it to the second store.
  • Terminal — the black window where you type commands. Every command in this lesson is typed in the terminal, then you press Enter.
  • Folder / directory — the same thing. A folder holds files. This lesson says "folder" every time.

What you need first

  • Docker running on your machine. The lesson points to Phase 2, zero-cost-lab.md, for setting Docker up. Do that first if Docker is not installed yet.
  • How to tell Docker is running: open your terminal and type docker ps, then press Enter. docker is the tool. ps means "show the boxes that are running". If Docker is running, you see a list — even an empty list — with no error. If you see an error about the daemon, Docker is not running yet. A daemon is just a background program — here, the Docker program itself running behind the scenes.
  • The files in the folder phase1/object-store-lab. That folder holds docker-compose.yml, Dockerfile, mirror.sh, and a folder called files/ with two fake receipts: files/receipt-001.txt and files/receipt-002.txt. All four paths were checked to exist on disk.

Getting into the right folder

Every command in this lab is run from inside the folder phase1/object-store-lab.

  • What: cd means "change folder". It moves your terminal into a folder.
  • Why: the commands below look for docker-compose.yml in the folder your terminal is sitting in. If you are in the wrong folder, they fail.
  • How: open your terminal in the folder phase1/object-store-lab on your machine. If your terminal opens somewhere else, type cd followed by the path to that folder on your machine, then press Enter.
  • Check you are in the right place: type ls and press Enter. ls means "list the files here". You should see docker-compose.yml, Dockerfile, mirror.sh, and files in the list. If you do not see them, you are in the wrong folder. Move again until ls shows them.

Step 1 — Start both stores

What this step does: it builds a small image and starts all four boxes: the two stores, the mirror, and the helper box that holds the file commands.

Why: nothing else works until the stores are running. The bucket, the uploads, and the mirror all need live stores.

The command, word by word, before you run it:

Try it Yourself »Open the practice terminal and run it yourself — nothing installs. Included with Phase 1. Simulation — practice version. Run the real lab with Docker to do it for real.
Command
docker compose up -d --build
  • docker — the tool that runs boxes.
  • compose — read the recipe file docker-compose.yml and run everything it lists.
  • up — start everything in the recipe.
  • -d — run in the background. Short for "detached". It means: start the boxes and give me my terminal back, so I can type the next command. Without -d, the boxes would hold your terminal and you could not type anything else.
  • --build — build the small aws image first, from the Dockerfile, before starting. Needed on the first run. On later runs it just reuses the image.

Run it now, from inside the folder phase1/object-store-lab.

What you should see: first, build lines for the small aws image. The first start builds it, so it takes a couple of minutes. Then the boxes start, one line each. Wait until the lines stop.

How to tell it worked: run the check command below.

The check command, word by word:

Command
docker compose ps
  • docker compose — the tool, reading the recipe file.
  • ps — show the boxes from this recipe and their state.

What you should see: a table with four names, each with STATUS "Up". "Up" means the box is running.

Command
NAME       STATUS
moto-a     Up
moto-b     Up
mirror     Up
awscli     Up

The real table has more columns than this. What matters is all four names, each with STATUS "Up".

  • moto-a is the first store. moto-b is the second store.
  • mirror is the box that copies files from the first store to the second.
  • awscli is a helper box. It holds the aws file commands. It does nothing on its own — it just sits there, awake, so you can run commands inside it. That is why it was started with the order "sleep forever".

If it breaks: if docker compose ps shows a box as "Exited", that box stopped. "Exited" means it ran and then stopped, usually because of an error. Read its log with the command below. A log is the box's diary — lines it printed while it ran.

Command
docker compose logs <name>
  • docker compose logs — show the diary lines for one box.
  • <name> — replace this with the real box name, for example mirror. So the real command is docker compose logs mirror. Look for the error line — it usually says what went wrong in plain words.

One more check — does the first store answer? The mirror waits for both stores, so give it a minute first. Then run:

Command
docker compose exec awscli aws --endpoint-url http://moto-a:5000 s3 ls

Word by word:

  • docker compose exec — run a command inside one box from this recipe. exec means "run this inside the box".
  • awscli — the box to run inside. We use this box because it holds the aws tool.
  • aws — the file-command tool for S3 stores.
  • --endpoint-url http://moto-a:5000 — talk to this store. http://moto-a:5000 is the first store's address inside the boxes. moto-a is the store's name, 5000 is its door number.
  • s3 — use the S3 file commands.
  • ls — list. With no bucket name after it, it lists all buckets.

What you should see: nothing, and no error. An empty answer with no error means the store is up and there are no buckets yet. That is correct at this point — you have not made the bucket yet.

Step 2 — Make the bucket (once)

What this step does: it makes the bucket called incoming in the first store.

Why: files live inside buckets. You cannot put a file into a store that has no bucket. The bucket is made once. If you run this step twice, the store says it already exists — that is fine, skip the step.

The command, word by word:

Command
docker compose exec awscli aws --endpoint-url http://moto-a:5000 s3 mb s3://incoming
  • docker compose exec awscli — run a command inside the awscli box. Same as Step 1.
  • aws --endpoint-url http://moto-a:5000 — the file tool, talking to the first store.
  • s3 — use the S3 file commands.
  • mb — make bucket. Short for "make bucket".
  • s3://incoming — the bucket to make. s3:// means "a bucket in an S3 store". incoming is the bucket's name.

What you should see:

Command
make_bucket: incoming

That one line means the bucket now exists. make_bucket is the tool's way of saying "bucket made".

If it breaks: if you see "BucketAlreadyExists", it means you already made the bucket — skip this step, nothing is wrong. Note: the mirror box also makes this bucket on both stores by itself when it starts (that is written in the file mirror.sh), so seeing "already exists" is normal. If the command fails another way, the store is not up yet — wait a minute and try again.

Step 3 — Put a fake file in

What this step does: it copies the first fake receipt into the bucket in the first store.

Why: this is the file the mirror will copy. No file in, nothing to mirror.

The command, word by word:

Command
docker compose exec awscli aws --endpoint-url http://moto-a:5000 s3 cp /files/receipt-001.txt s3://incoming/
  • docker compose exec awscli aws --endpoint-url http://moto-a:5000 s3 — same as Step 2: run the file tool inside the awscli box, talking to the first store.
  • cp — copy.
  • /files/receipt-001.txt — the file to copy. This path is INSIDE the awscli box, not on your machine. The folder files/ on your machine is shared into the box under the name /files, so /files/receipt-001.txt is the same file as files/receipt-001.txt in the folder phase1/object-store-lab. That sharing is written in the recipe file docker-compose.yml.
  • s3://incoming/ — where to put it: inside the bucket called incoming. The / at the end means "inside this bucket".

What you should see:

Command
upload: /files/receipt-001.txt to s3://incoming/receipt-001.txt

That line means the file went up into the bucket. upload means "sent up into the store".

If it breaks: "NoSuchBucket" means the bucket was never made — go back to Step 2 and make it. "No such file" means the receipt file is missing — check the files/ folder in phase1/object-store-lab holds receipt-001.txt. Run ls files to see what is in it.

Prove it is there — list the bucket:

Command
docker compose exec awscli aws --endpoint-url http://moto-a:5000 s3 ls s3://incoming/
  • s3 ls s3://incoming/ — list the files inside the bucket called incoming. The rest of the command is the same as before.

What you should see: one line, like this:

Command
2026-11-20 00:00:00        126 receipt-001.txt

Line by line — it has four parts:

  • 2026-11-20 00:00:00 — the date and time the file was put in. Your date and time will match when YOU ran it, not the line above.
  • 126 — the file's size in bytes. A byte is the smallest unit of file size. 126 just means the receipt file is 126 bytes long. Your number should be 126 too, because it is the same file.
  • receipt-001.txt — the file's name.

If it breaks: if the list is empty, the upload in the step above did not happen — run the cp command again and check it prints the upload: line.

Step 4 — Watch it appear in the second store

What this step does: it lists the bucket in the SECOND store, to prove the mirror copied the file by itself.

Why: this is the payoff of the whole lab. You put the file in the first store once. The mirror — the box running the script in mirror.sh — checks every 10 seconds and copies new files to the second store. You did not copy it twice. The 10 seconds comes from the file mirror.sh: it ends with a loop that copies, then waits 10 seconds, then copies again.

Wait 30 seconds first. The mirror checks every 10 seconds, so 30 seconds gives it three chances.

The command, word by word:

Command
docker compose exec awscli aws --endpoint-url http://moto-b:5000 s3 ls s3://incoming/

This is the same list command as Step 3, except the address is now http://moto-b:5000 — the SECOND store, moto-b, instead of the first store, moto-a. Everything else is the same.

What you should see: receipt-001.txt there too:

Command
2026-11-20 00:00:00        126 receipt-001.txt

Same four parts as before: date and time (yours will differ), size 126, file name. The copy happened by itself — you did not copy it twice.

If it breaks: if the file is missing, wait another minute and list again — the mirror checks every 10 seconds. If it is still missing, check the mirror's diary:

Command
docker compose logs mirror

Look for the word "ERROR" in the lines. "ERROR" means something failed, and the words after it usually say what. The most common cause is that the mirror started before the stores were ready. Fix it by restarting the mirror:

Command
docker compose restart mirror
  • docker compose restart — stop one box and start it again.
  • mirror — the box to restart.

Then wait a minute and list the second store again.

Step 5 — Add a second file and watch it follow

What this step does: it puts the second fake receipt into the first store, then checks the second store again.

Why: one copy could be luck. Two files following by themselves proves the mirror keeps working, not just once.

The command, word by word:

Command
docker compose exec awscli aws --endpoint-url http://moto-a:5000 s3 cp /files/receipt-002.txt s3://incoming/

Same copy command as Step 3, but the file is now receipt-002.txt — the second fake receipt. It goes into the FIRST store (moto-a).

What you should see:

Command
upload: /files/receipt-002.txt to s3://incoming/receipt-002.txt

If it breaks: "NoSuchBucket" means the bucket was never made — go back to Step 2. "No such file" means the receipt file is missing — check the files/ folder in phase1/object-store-lab holds receipt-002.txt.

Wait 30 seconds, then list the SECOND store:

Command
docker compose exec awscli aws --endpoint-url http://moto-b:5000 s3 ls s3://incoming/

What you should see: both files now:

Command
2026-11-20 00:00:00        126 receipt-001.txt
2026-11-20 00:00:00        120 receipt-002.txt

Two lines, one per file. The dates and times will match when you ran it, not the lines above. The sizes are different because the two files are different lengths: receipt-001.txt is 126 bytes and receipt-002.txt is 120 bytes. New files follow by themselves.

Step 6 — Download a file back

What this step does: it downloads the first receipt from the SECOND store and prints it on your screen.

Why: a name in a list could be an empty shell. Downloading the file and reading its words proves the file in the second store is a real copy, not just a name in a list.

The command, word by word:

Command
docker compose exec awscli aws --endpoint-url http://moto-b:5000 s3 cp s3://incoming/receipt-001.txt -
  • docker compose exec awscli aws --endpoint-url http://moto-b:5000 s3 cp — run the copy tool inside the awscli box, talking to the SECOND store.
  • s3://incoming/receipt-001.txt — the file to copy: receipt-001.txt inside the bucket incoming in the second store.
  • - — a single dash. It means "print the file on the screen instead of saving it to a file". Without the dash, the tool would need a place to save the file. With the dash, the file's words appear in your terminal.

What you should see: the fake receipt text:

Command
Fake receipt for practice only. Not a real document.
Order: order-101
Item: notebook
Amount: 250
Buyer: Asha
Date: 2026-11-20

Line by line: a warning that the receipt is fake, then the order number order-101, the item notebook, the amount 250, the buyer Asha, and the date. This is the same text as the file files/receipt-001.txt in the folder phase1/object-store-lab. If the words match, the copy is real.

If it breaks: "NoSuchKey" means the file is not in the second store yet. "Key" is the S3 word for a file's name inside a bucket. Wait a minute — the mirror copies every 10 seconds — and try again.

Clean up

What this step does: it stops all four boxes and removes them.

Why: the lab is done. The boxes would otherwise keep running and using your machine. The files live only in memory, so stopping the lab wipes them. That is fine — the files were fake. Run the steps again any time you want to practise.

The command, word by word:

Command
docker compose down
  • docker compose — the tool, reading the recipe file.
  • down — stop all the boxes in the recipe and remove them. Different from stop, which stops them but keeps them around. down clears them away.

Run it from inside the folder phase1/object-store-lab.

What you should see:

Command
✔ Container moto-a  Removed
✔ Container moto-b  Removed
✔ Container mirror  Removed
✔ Container awscli  Removed

Four lines, one per box. ✔ is a tick mark. Removed means the box is gone. If you see all four, the clean-up worked.

Save your proof

The proof for this lab is the same file listed in both stores. Save both listings into one file with these commands, run from inside the folder phase1/object-store-lab.

First command — make the proof folder, word by word:

Command
mkdir -p ../portfolio/proof
  • mkdir — make a folder. Short for "make directory".
  • -p — make the parent folders too if they are missing, and do not complain if the folder already exists.
  • ../portfolio/proof — the folder to make. .. means "go up one folder" — from phase1/object-store-lab up to phase1. Then portfolio/proof is the folder inside phase1/portfolio. The full path is phase1/portfolio/proof, and it holds the proof files. That folder was checked to exist on disk.

Second command — save the first store's list:

Command
docker compose exec awscli aws --endpoint-url http://moto-a:5000 s3 ls s3://incoming/ > ../portfolio/proof/object-store-mirror.txt

This is the Step 3 list command, with one extra piece at the end:

  • > — send the output into a file instead of onto the screen. It overwrites the file if the file already exists.
  • ../portfolio/proof/object-store-mirror.txt — the file to write into. object-store-mirror.txt is a plain text file.

Third command — add the second store's list to the same file:

Command
docker compose exec awscli aws --endpoint-url http://moto-b:5000 s3 ls s3://incoming/ >> ../portfolio/proof/object-store-mirror.txt
  • >> — send the output into the same file, but ADD it at the end instead of overwriting. Two > signs mean "append". One > sign means "overwrite". That is the only difference between the second and third commands.

What you should see: nothing in the terminal when you run the save commands. That is correct — the listings went into the file, not the screen. Silence means it worked here.

Check the file: open phase1/portfolio/proof/object-store-mirror.txt and check both receipt-001.txt and receipt-002.txt appear twice — once per store. That file is your proof.

If it breaks: if the file lists each receipt only once, the mirror had not copied yet when you saved — wait a minute, then run the save commands again.

What you can now say, truthfully

"I ran two Moto object stores (a free S3 stand-in), made a bucket, uploaded files with the aws tool, and set up a mirror that copies new files to the second store by itself."

What this lab does NOT cover

  • Real stores use access keys per app, not one shared login. An access key is like a separate password for each app, so one app cannot use another app's key. This lab uses one shared login on purpose — the name learner and the password are written in the recipe file docker-compose.yml — so you can learn. Do not copy that habit into real work.
  • The mirror here copies one way only, from the first store to the second. Two-way sync, where each side copies to the other, is a different setup.
  • Large files, versioning (keeping old copies of a file when it changes) and lifecycle rules (rules that delete old files by themselves) are later topics. The ideas are the same; the setup is bigger.
