Kubernetes Lab — Your App on a Small Local Cluster

Phase 2 · The Rest of DevOps

What this is and why it matters

Kubernetes runs your app for you. You say how many copies you want, and it keeps that many running.

Think of a school bus driver with a list: "12 children must be on this bus." If one child gets off, the driver goes and gets a replacement. Kubernetes is the driver. Your app copies are the children.

In real work, a crashed app that stays down until someone restarts it by hand is the failure that wakes people up.

This lab runs a small cluster on your own machine. A Service is the stable front door to your app. Front door means: one address that always leads to your app, even when the copies behind it change.

You will also break it on purpose and fix it, the same way you did in the break-and-fix labs.

What is a pod, in plain words?

A pod is the smallest thing Kubernetes runs, usually one container. A container is a small sealed box that holds one program. So a pod is usually one box, running one program.

A pod has a name that changes every time it is made, like my-site-7d9f8b6c4-abc12. The random letters at the end are normal. Copy the real name from your screen each time. Never guess it.

What is a node, in plain words?

A node is one machine in the cluster. In this lab there is one node, called devops-practice-control-plane. Control-plane means the node that is in charge: it decides what runs where. In a small practice cluster, the same node is in charge and also runs your app.

What is a deployment, in plain words?

A deployment is a written instruction that says "keep this many copies of my app running". You write it in a file. Kubernetes reads the file and does what it says. If a copy dies, the deployment makes a new one by itself.

What is a service, in plain words?

A service gives your app a stable address inside the cluster, even when pods come and go. Pods come and go because their names change and they get replaced. The service address stays the same. Other things inside the cluster use that address to find your app.

What this lab is

You will run your Project 1 website on a small Kubernetes cluster that lives on your own machine. No cloud account, no bill. You will also break it on purpose and fix it, the same way you did in the break-and-fix labs.

Why kind?

This kit uses kind, short for "Kubernetes in Docker". kind runs a whole cluster as containers on your machine, so it needs only Docker, which you already have. The other common choice is minikube, but this kit uses kind only, so every command below matches kind. minikube is another tool that runs a small cluster on your machine. You do not need it here. Do not install it.

Where do the files in this lab live?

The files you make in this lab (deployment.yaml and service.yaml) live in the folder you are standing in when you make them. Work inside ~/devops-practice/my-site for this whole lab, unless a step says otherwise. That is the Project 1 folder, and it is where your image was built.

Step 1 — Install kubectl and kind (Linux AMD64)

  • WHAT we are doing: downloading two tools and putting them where the computer can find them.
  • WHY: kubectl is the tool you use to talk to a cluster. kind is the tool that creates the cluster. Without them, you cannot do any step below.
  • These download links are for AMD64 Linux. AMD64 is the type of processor in most desktop and laptop computers. ARM64 is the type in some newer laptops and in most phones.
  • How to know which one you have: run uname -m in your terminal.
  • WHAT uname -m is: print your machine type.
  • WHY: it tells you which download link to use.
  • If it prints x86_64, you have AMD64. Use the links below.
  • If it prints aarch64 or arm64, you have ARM64. Swap amd64 for arm64 in the links below, and check kind's install page if a link fails. ARM64 steps are unverified in this kit.
  • Mac and Windows install steps differ (Homebrew or choco) and are unverified in this kit.
  • Homebrew is the Mac app installer. Choco (Chocolatey) is a Windows app installer. This lesson gives no Mac or Windows commands for this step, because the lesson does not verify them. Check kind's install page for your system if you are on a Mac or Windows.

1a. Install kubectl

Command
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
chmod +x kubectl
sudo mv kubectl /usr/local/bin/kubectl
  • Line 1: the long curl line.
  • WHAT: download the newest stable kubectl for Linux AMD64.
  • WHY: kubectl is how you talk to the cluster. You need the tool on your machine before you can use it.
  • Word by word: curl (download a file from the internet) + -LO (save it with its own name, and follow redirects if the address moves) + the address in quotes (the place to download from).
  • Inside the address, $(curl -L -s https://dl.k8s.io/release/stable.txt) is a command inside a command. It downloads a tiny text file that holds the newest version number, like v1.29.0, and pastes that number into the address. $(...) means "run this and paste the result here". -L means follow redirects. -s means quiet, print no progress.
  • So the full address means: "the newest kubectl, for Linux, for AMD64 processors".
  • Line 2: chmod +x kubectl.
  • WHAT: mark the downloaded file as runnable.
  • WHY: a downloaded file is not runnable yet. The computer will refuse to run it until you mark it.
  • Word by word: chmod (change the file's permissions) + +x (add the "can run" permission) + kubectl (the file).
  • This is the same chmod +x you met in zero-cost-lab.md Step 8.
  • Line 3: sudo mv kubectl /usr/local/bin/kubectl.
  • WHAT: move the file into the folder /usr/local/bin.
  • WHY: /usr/local/bin is a folder the computer always looks in when you type a command name. Once kubectl is there, you can type kubectl from any folder and the computer finds it. That list of folders the computer searches is called the PATH.
  • Word by word: sudo (as administrator — moving into this folder needs administrator power) + mv (move a file) + kubectl (the file, in the folder you are standing in) + /usr/local/bin/kubectl (the destination: the same name, inside /usr/local/bin).
  • You should see: a download progress line, then your prompt back. The mv step prints nothing when it works. That is normal.
  • If it breaks: "Permission denied" on the mv step means you forgot sudo. Run the mv line again with sudo in front. If the download fails, check your internet connection and try again.

  • WHY: kind is the tool that creates your cluster.

  • WHAT: mark the downloaded file as runnable.
  • WHY: same reason as kubectl above.
  • Word by word: chmod + +x (add "can run") + ./kind (the file called kind in this folder).
  • Line 3: sudo mv ./kind /usr/local/bin/kind.
  • WHAT: move kind into /usr/local/bin, the folder the computer searches for commands.
  • WHY: so you can type kind from any folder.
  • Word by word: sudo (as administrator) + mv (move) + ./kind (the file in this folder) + /usr/local/bin/kind (the destination).
  • You should see: a download progress line, then your prompt back. Again, the mv step prints nothing when it works.
  • If it breaks: "404 Not Found" means that kind version link is old. Take the newest link from kind's install page.

Command
kind version
kubectl version --client
  • Line 1: kind version.
  • WHAT: ask kind for its version number.
  • WHY: if it prints a version, kind is installed and found.
  • Line 2: kubectl version --client.
  • WHAT: ask kubectl for its own version number.
  • WHY: --client means "only your tool on this machine, not the cluster". There is no cluster yet, so we only check the tool.

kind v0.23.0 go1.21.5 linux/amd64

Step 2 — Start the cluster

  • WHAT we are doing: telling kind to create a cluster called devops-practice.
  • WHY: the cluster is where your app will run. Nothing below works until it exists.
Command
kind create cluster --name devops-practice
  • Word by word: kind (the cluster tool) + create cluster (make a cluster) + --name devops-practice (call it devops-practice).
  • You should see: lines scroll past as the cluster starts, then "Creating cluster ..." and your prompt back.
  • If it breaks: "failed to create cluster" usually means Docker is not running. Start Docker and try again.
  • The first run downloads the cluster's node image, so it takes a few minutes. A node image is the ready-made machine picture the cluster runs on. Be patient. Do not press Ctrl+C while it downloads.
  • Then check it:
Command
kubectl get nodes
  • WHAT: list the machines (nodes) in the cluster.
  • WHY: to prove the cluster started and has a working node.
  • Word by word: kubectl (talk to the cluster) + get (list) + nodes (the machines).
  • You should see one node with STATUS Ready:
Command
NAME                              STATUS   ROLES           AGE   VERSION
devops-practice-control-plane     Ready    control-plane   2m    v1.29.2
  • How to read it, column by column:
  • NAME (devops-practice-control-plane): the node's name.
  • STATUS (Ready): the node is ready to run work. This is the column that matters. If it says Ready, the cluster works.
  • ROLES (control-plane): this node is in charge of the cluster.
  • AGE (2m): the node was made 2 minutes ago. Yours will differ.
  • VERSION (v1.29.2): the Kubernetes version on the node. Yours will be different. That is fine.

Step 3 — Load your image into the cluster

  • WHAT we are doing: copying your my-site:1.0 image into the cluster.
  • WHY: a kind cluster cannot see images sitting in your local Docker by itself. This is the step most beginners forget. Without it, the cluster would try to download your image from the internet and fail, because your image only exists on your machine.
Command
kind load docker-image my-site:1.0 --name devops-practice
  • Word by word: kind load (load something into the cluster) + docker-image (the thing is a Docker image) + my-site:1.0 (the image name and version) + --name devops-practice (into the cluster called devops-practice).
  • You should see:
Command
Image: "my-site:1.0" with ID "sha256:abc123..." not yet present on node "devops-practice-control-plane", loading...
  • How to read it: it says the image was not on the node yet, and it is loading it now. Your image ID will be different. That is fine. sha256:abc123... is the image's fingerprint code. You do not need to remember it.
  • If it breaks: "image not found" means the image was never built. Go back to "What you need first" and build my-site:1.0.

Step 4 — Run your app with a Deployment

  • WHAT we are doing: writing a file that tells Kubernetes "keep one copy of my app running", then telling Kubernetes to read it.
  • WHY: the file is the instruction. Kubernetes only does what the file says.

4a. Make the file deployment.yaml

  • Make a file called deployment.yaml in ~/devops-practice/my-site (see "Where do the files in this lab live?" above for how).
  • deployment.yaml is a settings file in YAML. YAML is a plain-text way of writing settings with indentation. Spaces matter. Never use the Tab key.
Command
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-site
spec:
  replicas: 1
  selector:
    matchLabels:
      app: my-site
  template:
    metadata:
      labels:
        app: my-site
    spec:
      containers:
        - name: web
          image: my-site:1.0
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 80
  • How to read this file, line by line:
  • apiVersion: apps/v1 — WHAT: the version of the Deployment rules Kubernetes should use. WHY: Kubernetes has many versions of its rules. This line picks the right one. Copy it exactly.
  • kind: Deployment — WHAT: this file describes a Deployment. WHY: it tells Kubernetes what sort of thing this file is.
  • metadata: — WHAT: details about this Deployment. WHY: the next lines name it.
  • name: my-site — WHAT: call this Deployment my-site. WHY: so you can refer to it by name in later commands.
  • spec: — WHAT: the wanted state. WHY: everything under spec says what Kubernetes must keep true.
  • replicas: 1 — WHAT: keep 1 copy running. WHY: one copy is enough while learning. replicas means copies.
  • selector: — WHAT: how Kubernetes finds the pods this Deployment owns. WHY: it matches pods by their label, in the next lines.
  • matchLabels: — WHAT: match pods with these labels. WHY: a label is a small tag stuck on a pod, like app: my-site.
  • app: my-site — WHAT: the label is app with the value my-site. WHY: the Deployment's pods carry this label, so the Deployment can find them.
  • template: — WHAT: the pattern for making each pod. WHY: when Kubernetes needs a new copy, it follows this pattern.
  • metadata: (inside the template) — WHAT: details about each pod. WHY: the next lines give the pod its label.
  • labels: — WHAT: the labels to stick on each pod. WHY: the label must match the selector above, or the Deployment cannot find its own pods.
  • app: my-site — WHAT: stick the label app: my-site on each pod. WHY: this is the label the selector looks for.
  • spec: (inside the template) — WHAT: what goes inside each pod. WHY: the next lines describe the container.
  • containers: — WHAT: the list of containers in the pod. WHY: a pod usually holds one container. Here it holds one.
  • - name: web — WHAT: call the container web. WHY: so you can refer to it. The - starts one item in the list.
  • image: my-site:1.0 — WHAT: run the image my-site:1.0. WHY: this is your Project 1 image, loaded in Step 3.
  • imagePullPolicy: IfNotPresent — WHAT: use the image if it is already here; only download it if it is missing. WHY: your image only exists on your machine. Without this line, Kubernetes would try to download it from the internet and fail.
  • ports: — WHAT: the list of doors this container listens on. WHY: the next line names the door.
  • - containerPort: 80 — WHAT: the container listens on door
  • WHY: door 80 is the door web servers normally listen on, and your Project 1 site is a web server. The - starts one item in the list.

4b. Apply it and look at your pods

Command
kubectl apply -f deployment.yaml
kubectl get pods
  • Line 1: kubectl apply -f deployment.yaml.
  • WHAT: give Kubernetes the file deployment.yaml and tell it to make it real.
  • WHY: writing the file alone does nothing. apply is the step that hands it to Kubernetes.
  • Word by word: kubectl (talk to the cluster) + apply (make this real) + -f (the file follows) + deployment.yaml (the file name).
  • Line 2: kubectl get pods.
  • WHAT: list the pods.
  • WHY: to see whether your app's pod started.
  • Word by word: kubectl + get (list) + pods (the pods).
  • You should see one pod named like my-site-xxxx, with READY 1/1 and STATUS Running:
Command
NAME                      READY   STATUS    RESTARTS   AGE
my-site-7d9f8b6c4-abc12   1/1     Running   0          30s
  • How to read it, column by column:
  • NAME (my-site-7d9f8b6c4-abc12): the pod's name. The random letters at the end change every time. Copy the real name from your screen for the commands below. Never guess it.
  • READY (1/1): 1 copy ready out of 1 wanted. This is the column that matters. 1/1 means ready. 0/1 means not ready yet.
  • STATUS (Running): the pod is running.
  • RESTARTS (0): the pod has not restarted. A high number here means it keeps crashing.
  • AGE (30s): the pod was made 30 seconds ago.
  • If it breaks: if the pod shows ImagePullBackOff, the image was not loaded into the cluster. Go back to Step 3.
  • ImagePullBackOff means "I tried to download the image, failed, and I am waiting before trying again". BackOff means waiting.
  • If it shows Pending, wait a minute and run kubectl get pods again. Pending means "waiting to start". It usually clears on its own.
  • If it shows ErrImagePull, it means the same as ImagePullBackOff: the image could not be pulled (downloaded).

4c. Open your app in the browser (through the Deployment)

Command
kubectl port-forward deployment/my-site 8080:80
  • WHAT: connect door 8080 on your machine to door 80 on your app, through the Deployment.
  • WHY: your app runs inside the cluster. Your browser cannot reach inside the cluster by itself. Port-forward is a temporary tunnel from your machine to your app, so you can look at it.
  • Word by word: kubectl (talk to the cluster) + port-forward (make a tunnel for a door) + deployment/my-site (the Deployment called my-site) + 8080:80 (door 8080 on your machine leads to door 80 in the app).
  • You should see:
Command
Forwarding from 127.0.0.1:8080 -> 80
Forwarding from [::1]:8080 -> 80
  • How to read it: 127.0.0.1 is another name for localhost, which means "this machine". [::1] is the same idea in the newer address style. Both lines say the same thing: door 8080 on your machine now leads to door 80 in your app.
  • If it breaks: "address already in use" means another port-forward is already running. Stop it with Ctrl+C first, then try again.
  • WHAT Ctrl+C is: hold Ctrl and press C. It stops the command running in this terminal.
  • WHY: two tunnels cannot use the same door 8080 at the same time.
  • This connects port 8080 on your machine to your app. Open http://localhost:8080. You should see your Project 1 site.
  • Keep this terminal open while you look. Stopping it with Ctrl+C only stops the forwarding, not your app. Your app keeps running inside the cluster.

4d. Expose it with a Service

  • WHAT we are doing: making a second file that gives your app a stable address inside the cluster.
  • WHY: the Deployment's pods change names and get replaced. The Service address stays the same, so other things inside the cluster can always find your app.
  • Make a file called service.yaml in the same folder (~/devops-practice/my-site):
Command
apiVersion: v1
kind: Service
metadata:
  name: my-site
spec:
  selector:
    app: my-site
  ports:
    - port: 80
  • How to read this file, line by line:
  • apiVersion: v1 — WHAT: the version of the Service rules. WHY: copy it exactly, the same idea as in the Deployment file.
  • kind: Service — WHAT: this file describes a Service. WHY: it tells Kubernetes what sort of thing this file is.
  • metadata: — WHAT: details about this Service. WHY: the next line names it.
  • name: my-site — WHAT: call this Service my-site. WHY: so you can refer to it by name.
  • spec: — WHAT: the wanted state. WHY: everything under it says what the Service must do.
  • selector: — WHAT: which pods this Service leads to. WHY: it matches pods by their label.
  • app: my-site — WHAT: send traffic to pods labelled app: my-site. WHY: that is the same label your Deployment gives its pods, so the Service finds them. If the label does not match, the Service leads nowhere.
  • ports: — WHAT: the list of doors this Service offers. WHY: the next line names the door.
  • - port: 80 — WHAT: the Service listens on door 80. WHY: door 80 is the door your app listens on inside its pod.
  • Apply and check:
Command
kubectl apply -f service.yaml
kubectl get services
  • Line 1: kubectl apply -f service.yaml.
  • WHAT: give Kubernetes the Service file and make it real.
  • WHY: same as the Deployment file. Writing it alone does nothing.
  • Line 2: kubectl get services.
  • WHAT: list the services.
  • WHY: to see whether your Service exists and what address it got.
  • You should see my-site with a CLUSTER-IP:
Command
NAME      TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE
my-site   ClusterIP   10.96.123.45   <none>        80/TCP    10s
  • How to read it, column by column:
  • NAME (my-site): the Service's name.
  • TYPE (ClusterIP): this Service is only reachable inside the cluster. ClusterIP is the default type. It means "an address inside the cluster only".
  • CLUSTER-IP (10.96.123.45): the stable address inside the cluster. Yours will be different. That is fine. This address is for things inside the cluster. Your browser cannot open it directly.
  • EXTERNAL-IP (<none>): there is no outside address. <none> means "none". That is normal for a ClusterIP Service. It does not mean something is broken.
  • PORT(S) (80/TCP): the Service offers door 80, using TCP network traffic.
  • AGE (10s): the Service was made 10 seconds ago.
  • If it breaks: if my-site is missing, check the file name and run kubectl apply -f service.yaml again.
  • Stop the first port-forward with Ctrl+C first. Both port-forwards use port 8080, so they cannot run at the same time. Stopping it ends only the forwarding, not your app.

4e. Open it through the Service instead of the Deployment

Command
kubectl port-forward service/my-site 8080:80
  • WHAT: make a tunnel from door 8080 on your machine to the Service.
  • WHY: this proves the Service works. Before, you reached the app through the Deployment. Now you reach it through the Service.
  • Word by word: kubectl + port-forward (make a tunnel) + service/my-site (the Service called my-site) + 8080:80 (door 8080 on your machine leads to door 80).
  • You should see the same two "Forwarding from" lines as before.
  • If it breaks: "address already in use" means the first port-forward is still running. Stop it with Ctrl+C first.
  • Open http://localhost:8080 again. Same site, now reached through the Service. This is the address other things inside the cluster would use. Your browser reaches it here only through the port-forward above. That does not expose the app publicly. Publicly means anyone on the internet could open it. They cannot. Only your machine can, through this tunnel.

4f. Read about your pod

Command
kubectl describe pod <pod-name>
kubectl logs <pod-name>
  • Line 1: kubectl describe pod <pod-name>.
  • WHAT: show details and recent events for one pod.
  • WHY: when something breaks, the Events at the bottom usually name the problem.
  • Word by word: kubectl + describe (show details) + pod (a pod) + <pod-name> (the pod's real name — replace the whole thing, brackets included, with the name you copied from kubectl get pods).
  • The brackets < > mean "replace this with the real value". Never type the brackets themselves.
  • Line 2: kubectl logs <pod-name>.
  • WHAT: show what your app printed.
  • WHY: the app's own words tell you what it did, and what went wrong.
  • Word by word: kubectl + logs (show printed lines) + <pod-name> (the pod's real name, as above).
  • You should see: details and recent events for your pod (describe), and what your app printed (logs).
  • If it breaks: "No resources found" means the pod name is wrong. Pod names change every time, so copy the real name from kubectl get pods. Replace <pod-name> with it, without the brackets.
  • describe shows details and recent events. logs shows what your app printed. When something breaks, these two commands are where you look first.

Step 5 — Break it, then fix it

  • WHAT we are doing: changing the image name to one that does not exist, watching the pod fail, finding the cause in the Events, then changing it back.
  • WHY: this proves the Deployment controls the pod. The pod only does what its Deployment says. Fix the Deployment, and the pod follows.

5a. Break it

  • Change the image in deployment.yaml to a tag that does not exist, for example my-site:badtag.
  • HOW: open deployment.yaml in nano (or your text editor), find the line image: my-site:1.0, change 1.0 to badtag, save, and close. A tag is the version label after the colon. badtag is not a real version, so no such image exists.
  • Then apply it again:
Command
kubectl apply -f deployment.yaml
kubectl get pods
  • Line 1: kubectl apply -f deployment.yaml.
  • WHAT: hand the changed file to Kubernetes.
  • WHY: Kubernetes only knows what you tell it. Until you apply, it still uses the old file.
  • Line 2: kubectl get pods.
  • WHAT: list the pods, to see the failure.
  • WHY: the pod list is where the broken status shows up.
  • You should see your pod not reaching Running. Its STATUS will show something like ImagePullBackOff or ErrImagePull, and its restarts may climb:
Command
NAME                      READY   STATUS             RESTARTS   AGE
my-site-7d9f8b6c4-abc12   0/1     ImagePullBackOff   0          30s
  • How to read it: READY 0/1 means 0 ready out of 1 wanted — not ready. STATUS ImagePullBackOff means "I tried to download the image, failed, and I am waiting before trying again". ErrImagePull means the same thing in shorter form: error pulling (downloading) the image.
  • If it breaks: if the pod still shows Running, the bad tag was not applied. Check deployment.yaml really says my-site:badtag, then apply again.

5b. Find it

Command
kubectl describe pod <pod-name>
  • WHAT: show details and recent events for the broken pod.
  • WHY: the Events at the bottom say the image could not be pulled or was not found. That names the cause.
  • Replace <pod-name> with the real pod name from kubectl get pods, without the brackets. Note: after the bad apply, the pod name may have changed. Copy the new name from the latest kubectl get pods.
  • You should see: an event at the bottom saying the image could not be pulled or was not found.
  • If it breaks: if there are no Events yet, wait 30 seconds and describe the pod again. Events take a moment to appear.
  • Read the Events at the bottom. They will say the image could not be pulled or was not found. The lesson: the Deployment file is wrong, not the pod. A pod only does what its Deployment says.

5c. Fix it

  • Change the image back to my-site:1.0 in deployment.yaml, apply it again, and check:
Command
kubectl apply -f deployment.yaml
kubectl rollout status deployment/my-site
kubectl get pods
  • Line 1: kubectl apply -f deployment.yaml.
  • WHAT: hand the fixed file to Kubernetes.
  • WHY: this tells Kubernetes to go back to the real image.
  • Line 2: kubectl rollout status deployment/my-site.
  • WHAT: wait and report whether the new version finished rolling out.
  • WHY: kubectl apply alone does not mean the app is healthy yet. A rollout is the slow swap from the old copies to the new copies. This command watches it and tells you when it is done.
  • Word by word: kubectl + rollout status (report the rollout) + deployment/my-site (the Deployment called my-site).
  • Line 3: kubectl get pods.
  • WHAT: list the pods, to confirm the fix.
  • WHY: the pod list proves a healthy pod is running.
  • You should see the rollout finish, then a pod with READY 1/1 and STATUS Running:
Command
deployment "my-site" successfully rolled out
NAME                      READY   STATUS    RESTARTS   AGE
my-site-7d9f8b6c4-def34   1/1     Running   0          20s
  • How to read it: successfully rolled out means the swap finished. The pod name is different from before — that is normal. A new pod was made. READY 1/1 and STATUS Running mean healthy.
  • If it breaks: if the rollout hangs, describe the pod and read the Events. The error line names the problem.
  • Wait for the rollout to finish: the expected result is a pod with READY 1/1 and STATUS Running. kubectl apply alone does not mean the app is healthy yet. If the rollout fails, read the pod Events and status again.
  • A new pod starts and reaches Running. Deleting the broken pod alone would NOT have fixed it. The Deployment would simply have made the same broken pod again. Fix the Deployment, and the pod follows.

5d. Try self-healing once

  • On the healthy pod, run kubectl delete pod <pod-name>, then kubectl get pods again.
  • WHAT kubectl delete pod <pod-name> is: delete one pod.
  • WHY: to watch the Deployment make a replacement by itself, to keep your chosen number of copies running. That is self-healing: the system fixes the missing copy on its own.
  • Replace <pod-name> with the real pod name, without the brackets.
  • You should see: the old pod is gone, and a new pod with a different name appears, reaching READY 1/1 and STATUS Running.
  • That is not proof the app itself is healthy. Replacing a pod and knowing it works are different things. Later, learn readiness and liveness probes, which are how Kubernetes checks real health.
  • A readiness probe is a check that asks "are you ready to take traffic?" A liveness probe asks "are you still alive?" You do not need them yet. Just know the words for later.

Clean up

Remove your app but keep the cluster

Command
kubectl delete -f deployment.yaml
kubectl delete -f service.yaml
  • Line 1: kubectl delete -f deployment.yaml.
  • WHAT: delete everything the Deployment file made.
  • WHY: this removes your app's pods, but keeps the cluster itself.
  • Word by word: kubectl + delete (remove) + -f (the file follows) + deployment.yaml (the file that describes what to delete).
  • Line 2: kubectl delete -f service.yaml.
  • WHAT: delete the Service.
  • WHY: same idea. The Service goes, the cluster stays.
  • You should see:
Command
deployment.apps "my-site" deleted
service "my-site" deleted
  • How to read it: each line names what was deleted. deployment.apps is the full name for a Deployment. service is the full name for a Service.
  • If it breaks: "not found" means it was already deleted. That is fine. Move on.

Remove the whole cluster when you are done with this lab

Command
kind delete cluster --name devops-practice
  • WHAT: delete the whole cluster called devops-practice.
  • WHY: when you are done with this lab, the cluster only uses disk space and memory. Deleting it frees both.
  • Word by word: kind + delete cluster (remove a cluster) + --name devops-practice (the cluster called devops-practice).
  • You should see:
Command
Deleting cluster "devops-practice" ...
Deleted nodes: ["devops-practice-control-plane"]
  • How to read it: it says the cluster is being deleted, then lists the node that was deleted. Deleted nodes lists the machines that were removed.
  • If it breaks: "no cluster with name" means it was already deleted. Nothing to do.
  • Your Docker images stay on your machine, so you can start again any time with kind create cluster --name devops-practice.
  • WHAT that means: deleting the cluster does not delete your images. Your my-site:1.0 image is still in Docker, ready to load again.
