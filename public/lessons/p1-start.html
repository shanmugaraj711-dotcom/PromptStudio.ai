Start Here — Phase 1: The Data Tier

Phase 1 · The Data Tier

What this is and why it matters

Phase 1 teaches you how data moves, copies itself, and survives a crash.

In real systems, the worst moment is losing data or going down when one machine dies.

You run small practice systems on your own computer, using fake data, and finish with one fake order flowing through five tools.

Think of it like a small shop.

  • Orders come in at the front desk.
  • The orders wait in a line until a worker picks them up.
  • The worker writes each order in a record book.
  • A second record book copies every line, in case the first book is lost.
  • A fast notebook on the counter keeps small answers ready, so nobody has to open the big book for every small question.
  • Files like receipts go in a big file cupboard.
  • A traffic guard at the door sends each visitor to a different worker, so no one worker gets all the visitors.
  • If the main record book is destroyed, the copy takes over, and work continues.

Phase 1 builds that shop on your own computer, with fake orders and fake names.

Words you need, before you use them

  • Service. One running program in a Docker Compose file. Example: one record store is one service. A service is the name in the recipe file. A container is the running box that the service starts. One service usually starts one container.
  • Container. A small sealed box that holds one program and what it needs to run.
  • Compose. A tool that starts several containers together from one file. That file is called docker-compose.yml.
  • Topic. A named line of messages in Kafka. Example: a topic called orders is one named line, like order slips on a kitchen rail.
  • Producer. A program that puts messages into Kafka.
  • Consumer. A program that takes messages out of Kafka and does the work.
  • Primary. The main copy of a record store. It takes writes. A write is adding or changing a record.
  • Replica / standby. A copy that follows the primary. It takes reads only. A read is asking for a record without changing it. The standby becomes the new primary on failover.
  • Replication. Keeping a second copy up to date. The main record store writes down everything it does, and the standby copy reads that list and does the same things, so it is almost as new as the main one.
  • WAL. Short for write-ahead log. The list of changes a record store writes down first, before it changes the real data. The replica reads this list to stay in sync. WAL streaming means the replica reads that list live, as changes happen, instead of in one big batch later.
  • Failover. The standby taking over. When the main one dies, the standby becomes the new main one, and work continues.
  • Port. A numbered door on your computer. 5432 is the usual door for PostgreSQL (the main database; its standby copy answers on door 5433), 6379 for Redis, 9092 for Kafka, 9000 for the object store (Moto), 80 for a website.
  • localhost. This machine. When a lab says open http://localhost:8080, it means your own machine, door number 8080. The http:// part means "open this as a web page". The number 8080 is a real door number in this phase — the load-balancer lab uses it — but it is only one lab's door. Each lab names its own door numbers; do not assume 8080 works everywhere.
  • Kafka. A message queue. Think of it as a line of messages waiting in order. One program puts a message in the line. Another program takes messages out of the line and does the work. If the worker is slow or stops, the messages wait safely in the line.
  • PostgreSQL. The main record book. A record store that keeps your real records (orders, users, settings) in tables, and keeps them safe even when the power goes out. A table is a grid of rows and columns, like a spreadsheet page.
  • Patroni. A watcher for PostgreSQL. It watches the main record store. If the main one dies, Patroni promotes the standby copy to be the new main one, by itself. "By itself" means nobody types a command — that is the difference from the PostgreSQL lab's first part, where you promote the standby by hand with your own command (SELECT pg_promote();). The lab's Part 1 is by hand; its Part 2 is Patroni doing it for you.
  • Redis. A fast memory store. It keeps small answers in memory so your app can read them in a blink, instead of asking the record store every time. It is also used as a simple counter and a short-term waiting room.
  • Object store. A big file cupboard. It stores files (pictures, documents, uploads) by name. You ask for a file by its name and you get it back.
  • Moto. The free stand-in used in this kit for an object store. It speaks the same S3 language as the paid stores, so what you learn here transfers. S3 is the name of a well-known paid file storage service. "Speaks the same language" means Moto accepts the same commands as that paid service. You do not need an S3 account. Moto runs on your own machine.
  • Load balancer. A traffic guard. It stands in front of three copies of your app and sends each visitor to a different copy, so no single copy gets all the work. If one copy dies, it sends visitors to the copies that are still alive.
  • NGINX. A free program that does the load balancer job in this kit. It teaches the same idea as the paid boxes that do this job in big companies. One paid box the lesson names is called F5. F5 is a brand name for a paid traffic-guard box. You do not need F5. The kit uses NGINX instead, because it is free.
  • MirrorMaker 2. A tool that copies messages from one Kafka to a second Kafka. The Kafka lab teaches it, in its own steps. You do not need to know it before that lab.
  • Terminal. A plain window where you type commands instead of clicking.

The map — what each thing does, in plain words

Read this first. One idea per line.

  • Kafka — a message queue. Think of it as a line of messages waiting in order. One program puts a message in the line. Another program takes messages out of the line and does the work. If the worker is slow or stops, the messages wait safely in the line.
  • PostgreSQL — the main record book. A database that stores your real records (orders, users, settings) in tables, and keeps them safe even when the power goes out.
  • Patroni — a watcher for PostgreSQL. It watches the main database. If the main one dies, Patroni promotes the standby copy to be the new main one, by itself.
  • Redis — a fast memory store. It keeps small answers in memory so your app can read them in a blink, instead of asking the database every time. It is also used as a simple counter and a short-term waiting room.
  • Object store — a big file cupboard. It stores files (pictures, documents, uploads) by name. You ask for a file by its name and you get it back. Moto is the free stand-in used in this kit — it speaks the same S3 language as the paid stores, so what you learn here transfers.
  • Load balancer — a traffic guard. It stands in front of three copies of your app and sends each visitor to a different copy, so no single copy gets all the work. If one copy dies, it sends visitors to the copies that are still alive. A paid box called F5 does this job in big companies. This kit uses NGINX instead — it is free, and it teaches the same idea.
  • Replication — keeping a second copy up to date. The main database writes down everything it does, and the standby copy reads that list and does the same things, so it is always almost as new as the main one.
  • Failover — the standby taking over. When the main one dies, the standby becomes the new main one, and work continues.

How they fit together — one generic system

  1. A visitor arrives. The load balancer sends them to one of three copies of the app.
  2. The app takes the order and puts a message on Kafka. The message waits in line.
  3. A worker takes the message from Kafka and saves the order in PostgreSQL.
  4. The worker also writes a quick count in Redis, so the app can show "how many orders" without asking the database.
  5. Any files (like a receipt) go into the object store.
  6. PostgreSQL copies every change to its standby. Kafka copies its messages to its standby too.
  7. If the main database dies, Patroni (or your own command in the lab) promotes the standby. Work continues. In the PostgreSQL lab, Part 1 is your own command; Part 2 is Patroni.

The order — do the labs in this order

  1. kafka-lab.md — send and receive messages, then copy them to a second Kafka with MirrorMaker 2. (About 1 day.)
  2. postgresql-lab.md — a main database and a standby copy, streaming replication, then failover. Includes a Patroni part. (About 2 days.)
  3. redis-lab.md — a fast cache, expiry, counters, and what two-way sync means. (About half a day.) A cache is a fast copy of an answer, kept so you do not have to ask the slow record store again. Expiry is a time limit after which a saved answer deletes itself. Two-way sync means two stores both accept writes and merge them.
  4. object-store-lab.md — store files in Moto, copy them to a second store. (About half a day.)
  5. load-balancer-lab.md — NGINX in front of three backends. Kill one backend and watch the site stay up. (About half a day.) A backend is one copy of your app that sits behind the load balancer and does the work.
  6. end-to-end-lab.md — all of it together, on one machine, with one command. A fake order flows from a file to the database, then you kill the main database and watch the standby take over. (About 1 day.)

Rough total: about 1 week at 1–2 hours a day, after Phase 2. "About 1 day" means one study session of 1–2 hours, not a full 24 hours. "Done" for a lab means you saw every "you should see" output in that lab, and you saved its proof.

What you need before you start

  • Docker running on your machine. Lesson 0 shows how to install it and check it. Phase 2 also teaches it from zero.
  • A terminal. All commands run in a terminal.
  • About 4 GB of free disk space. The lab images are big. An image is the recipe Docker uses to build a container. To check your free space, use the way your own computer shows storage — on Windows, open Settings, then Storage; on Mac, open the Apple menu, then About This Mac, then Storage. The kit doctor script in Step 3 below also checks disk space for you and prints a FIX line if it is short. If you have less than 4 GB free, free space first.
  • A machine with at least 4 GB of memory. Memory is the fast working space your computer uses while programs run. The end-to-end lab runs eleven small services at once. Here they are, each with its job: kafka (the message line), postgres-primary (the main record store), postgres-replica (its standby copy), redis (the fast memory store), moto (the file cupboard), lb (the traffic guard), web1, web2, web3 (the three copies of the app behind the guard), ingest (reads a new order file and sends it on), and worker (takes orders from the line, saves them, and updates the count). You will meet all eleven inside the end-to-end lab. On a 2 GB machine it will be slow. If it is slow, run the single-topic labs one at a time instead.

Step 2 — Make the lab files readable

What this is: chmod changes who can read a file.

Why we run it: some lab files must be readable by the programs inside the containers, and a zip file can strip that permission. If a file is not readable, the program inside the container cannot open it, and the lab fails.

Run this once, from inside the kit folder. "The kit folder" here means the phase1 folder. Move your terminal into phase1 first, then type this and press Enter:

Command
chmod -R a+r .

Word by word:

  • chmod — short for "change mode". It changes who can read a file.
  • -R — means do this for every file in this folder, and in every folder inside it.
  • a+r — means everyone can read. The letter a means all users. The letter r means read. The + means add this permission.
  • . — means this folder, the one your terminal is in right now. A single dot is shorthand for "here".

What you should see: nothing. chmod prints nothing when it works. That is normal. Silence means it worked. If a lab later says a file is not readable, you probably ran this command in the wrong folder. Move into the phase1 folder and run it again.

Two labs in this phase call for this same step in their own steps, so you will meet it again there: the PostgreSQL lab (Part 1, Step 1) and the end-to-end lab. Running it once here covers both, but follow each lab's step when you reach it.

Step 3 — Run the kit doctor script

What this is: kit-doctor.sh is a saved list of checks. It checks Docker, ports, disk, and memory, and prints a plain-English FIX line for anything wrong.

Why we run it: it finds setup problems before you start a lab, instead of halfway through one.

Type this in your terminal, while you are inside the phase1 folder, then press Enter:

Command
bash kit-doctor.sh

Word by word:

  • bash — the program that runs script files. It reads the script and runs its commands one by one.
  • kit-doctor.sh — the name of the script file. It lives in the phase1 folder. That is why you must be inside phase1 first.

What you should see: a line starting with OK: for every check. Your numbers will be different from the example in Lesson 0. What matters is OK on every line, not the exact words. A line starting with FIX means that one check failed. Do what the FIX line says, then run the script again.

Step 4 — Start the first lab

What this is: the first lab in the order, Kafka.

Why we start here: the map builds in order. Kafka is the line of messages. Everything after it uses that idea.

Open the file phase1/kafka-lab.md and follow it step by step, one step at a time, in order. Do not jump to the end-to-end lab before you can run Kafka and PostgreSQL alone.

Step 5 — If you get stuck

Do these three steps, in order.

  1. Run the doctor script again, as in Step 3, from inside the phase1 folder. It prints a FIX line for each problem.
  2. Look the exact error line up in the Error Decoder. That is the file phase1/error-decoder.md. Copy the error line from your terminal, find it in that file, and follow the fix it gives.
  3. Email support@promptstudioai.in with the exact error line and the step you were on. The lesson says the team replies within 24 hours.
