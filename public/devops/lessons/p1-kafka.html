What this lab is

You will run two small Kafka clusters on your own machine, send messages into the first one, read them back, then watch MirrorMaker 2 copy them to the second one. All data is fake: order numbers and item names you make up.

What you need first

  • Docker running (Phase 2, zero-cost-lab.md).
  • The files in this folder: docker-compose.yml, connect-standalone.properties, mm2.properties.

Words you need here

  • Topic — a named line of messages. This lab uses one topic called orders.
  • Producer — a program that puts messages into a topic.
  • Consumer — a program that takes messages out of a topic.
  • Broker — one Kafka server. A cluster is one or more brokers.
  • MirrorMaker 2 (MM2) — a tool that copies topics from one cluster to another.

One important thing first

Kafka tells every client the address to come back to. In this lab that address is the container's own name (kafka-a), so Kafka commands must run *inside* the container with docker exec. Do not run them from your own terminal — your machine does not know the name kafka-a. This is normal. The lab shows every command with docker exec already in it.

Step 1 — Start both clusters

From inside this folder:

docker compose up -d

You should see three containers start: kafka-a, kafka-b, mm2. Check:

docker compose ps

You should see all three with STATUS "Up" (mm2 may take a minute — it waits for both clusters). If a container shows "Exited", run docker compose logs mm2 and read the last lines before moving on.

If it breaks: docker compose down then docker compose up -d again. The first start downloads the Kafka image, so it takes a few minutes the first time.

Step 2 — Make the topic

A topic is the line messages wait in. Make one called orders on cluster a:

docker exec kafka-a /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic orders --partitions 1 --replication-factor 1

You should see:

Created topic orders.

If it breaks: "Topic 'orders' already exists" means you already made it — skip this step. "Connection refused" means kafka-a is not up yet — wait a minute and run docker compose ps again.

Step 3 — Send three fake messages

The producer reads lines you type and sends each line as one message. Run it, type three lines, then press Ctrl+C to stop it:

docker exec -it kafka-a /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders

Type these three lines (fake orders — made up for this lab):

order-101, notebook, 250
order-102, pen, 40
order-103, mug, 350

Then press Ctrl+C. Each line you typed is now one message in the topic, in order. Nothing prints while you type — that is normal.

If it breaks: if the producer exits at once with an error about the topic, go back to Step 2 and check the topic exists with:

docker exec kafka-a /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list

You should see orders in the list.

Step 4 — Read the messages back

A consumer reads from the start of the topic and prints every message:

docker exec kafka-a /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders --from-beginning

You should see your three lines, in order:

order-101, notebook, 250
order-102, pen, 40
order-103, mug, 350

Press Ctrl+C to stop it. This proves the messages are stored in Kafka, not just sent and lost.

If it breaks: if you see nothing, check you typed the messages into the same topic (orders) and the same cluster (kafka-a). Kafka keeps messages even after you read them once, so reading again with --from-beginning shows them again.

Step 5 — Watch MirrorMaker 2 copy them

MirrorMaker 2 is already running in the mm2 container. It copies the orders topic from cluster a to cluster b. The copy appears on cluster b with the source name in front: a.orders.

List the topics on cluster b:

docker exec kafka-b /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list

You should see a.orders in the list (plus small topics MM2 makes for itself — those start with mm2- or heartbeats). Now read the copied messages from cluster b:

docker exec kafka-b /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic a.orders --from-beginning

You should see the same three lines. Press Ctrl+C to stop it. The same messages now live on two clusters. If cluster a dies, cluster b still has the copy.

If it breaks: if a.orders is missing, wait one minute (MM2 copies every few seconds, not instantly) and list the topics again. If it is still missing, check the MM2 logs:

docker compose logs mm2

Look for the word "ERROR" in the last lines. The most common cause is that MM2 started before kafka-b was ready — restart it with docker compose restart mm2 and wait a minute.

Step 6 — Send one more message and watch it follow

Send a fourth message to cluster a (same producer command as Step 3):

docker exec -it kafka-a /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders

Type:

order-104, mouse pad, 150

Press Ctrl+C. Wait 30 seconds, then read cluster b again:

docker exec kafka-b /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic a.orders --from-beginning

You should see all four messages, including order-104. The copy follows new messages by itself. Press Ctrl+C.

Clean up

docker compose down

This stops and removes the three containers. The messages are gone — that is fine, they were fake. Run docker compose up -d any time to start again.

What you can now say, truthfully

"I ran two Kafka clusters on my own machine, made a topic, sent messages with a producer, read them with a consumer, and copied the topic to a second cluster with MirrorMaker 2."

What this lab does NOT cover

  • Real clusters run three or more brokers, not one. The ideas are the same; the setup is bigger.
  • MirrorMaker 2 can also copy in the other direction. This lab copies one way only, on purpose.
  • Kafka keeps messages for a set time, then deletes them. This lab does not change that setting.
