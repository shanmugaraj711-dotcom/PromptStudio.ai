What this lab is

You will run three small backends and one NGINX load balancer in front of them. You will ask the load balancer for the page six times and see a different backend answer each time. Then you will kill one backend and watch the site stay up.

What you need first

  • Docker running (Phase 2, zero-cost-lab.md).
  • The files in this folder: docker-compose.yml, nginx.conf.

Words you need here

  • Load balancer — a traffic guard. It stands in front of copies of your app and sends each visitor to a different copy.
  • Backend — one copy of your app, behind the load balancer.
  • Upstream — NGINX's word for the list of backends.
  • Round robin — taking turns: backend 1, then 2, then 3, then 1 again. That is how NGINX shares the work by default.
  • F5 — a paid box that does this job in big companies. This lab uses NGINX instead. It is free, and it teaches the same idea. The lab says so honestly wherever it matters.

Step 1 — Start the guard and the three backends

From inside this folder:

Command
docker compose up -d

Check:

Command
docker compose ps

You should see lb, web1, web2, web3 with STATUS "Up".

If it breaks: if lb shows "Exited", the NGINX settings file has a mistake. Read the log with docker compose logs lb — the error line names the line number in nginx.conf. Fix the line and run docker compose up -d again.

Step 2 — Ask for the page six times

Ask the load balancer for the page:

Command
curl http://localhost:8080/
Expected output
Hostname: web1

The Hostname line tells you which backend answered. Ask again, five more times:

Command
curl http://localhost:8080/
curl http://localhost:8080/
curl http://localhost:8080/
curl http://localhost:8080/
curl http://localhost:8080/

You should see the Hostname line take turns: web1, web2, web3, web1, web2, web3 (the order may start on a different backend, but all three appear). That is round robin — the guard shares the work evenly.

If it breaks: if curl says "connection refused", the lb is not up yet — wait and try again. If every answer is the same backend, check docker compose ps — one of the backends may have failed to start, so the guard is only using the ones that are alive. That is still the guard working correctly, but fix the dead backend first (read its log) and try again.

Step 3 — Kill one backend and watch the site stay up

Stop backend 2:

Command
docker compose stop web2

Ask for the page six more times. On Windows, run this in Git Bash, not PowerShell:

Command
for i in 1 2 3 4 5 6; do curl -s http://localhost:8080/ | grep Hostname; done

You should see only "Hostname: web1" and "Hostname: web3". Backend 2 never answers — the guard skips it by itself. The site stays up with two backends. That is the whole point of a load balancer: one copy can die and nobody notices.

Bring it back:

Command
docker compose start web2

Ask again:

Command
curl http://localhost:8080/

Backend 2 answers again within a few seconds.

Step 4 — See the guard's view (optional)

Look at what NGINX thinks:

Command
docker compose logs lb

You will see one line per visit, with the visitor's address and the answer code 200 (which means "OK"). There is no line that says which backend answered — NGINX's normal log does not record that. The curl answers in Step 2 are the proof, not the log.

Clean up

Command
docker compose down

What you can now say, truthfully

"I ran NGINX as a load balancer in front of three backends, watched it share visitors round robin, killed one backend, and the site stayed up."

What this lab does NOT cover

  • Real load balancers also check backend health on their own (health checks) and can share work by least-busy instead of round robin. NGINX can do both — this lab keeps the default, so you learn the idea first.
  • HTTPS (the locked version of web traffic) is a later topic. This lab uses plain HTTP on your own machine only.
  • A paid F5 box has more features than NGINX. The idea — spread traffic, skip dead backends — is the same.

Failure drill — Lose a backend, stay up

This drill proves the site stays up when one backend dies, because the guard skips the dead one by itself.

Do Steps 1 and 2 first, so all three backends are answering.

Step 1 — Stop backend 2. Run this from inside this folder:

Command
docker compose stop web2
Expected output
✔ Container web2  Stopped

Step 2 — Ask for the page six times:

Command
for i in 1 2 3 4 5 6; do curl -s http://localhost:8080/ | grep Hostname; done
Expected output
Hostname: web1
Hostname: web3
Hostname: web1
Hostname: web3
Hostname: web1
Hostname: web3

Backend 2 never answers. The guard skips it by itself. The site stays up with two backends.

Step 3 — Bring backend 2 back:

Command
docker compose start web2
Expected output
✔ Container web2  Started

Ask again:

Command
curl http://localhost:8080/

Backend 2 answers again within a few seconds.

Checklist — tick each one when you have seen it:

  • ☐ The site stayed up with web2 stopped.
  • ☐ Only web1 and web3 answered the six curls — web2 never did.
  • ☐ Web2 answered again after it was started back.

Reset — run this from the phase1 folder to wipe the drill and start fresh:

Command
bash reset.sh load-balancer-lab

Or, from inside this folder, the plain way: run docker compose down. That stops the guard and the three backends.

Save your proof

The proof for this lab is the curl loop with web2 missing: six answers, only web1 and web3. Save it with this command, run from inside this folder while web2 is still stopped (Step 2 of the drill):

Command
mkdir -p ../portfolio/proof
for i in 1 2 3 4 5 6; do curl -s http://localhost:8080/ | grep Hostname; done > ../portfolio/proof/load-balancer-web2-down.txt

Open the file and check web2 never appears in it. That file is your proof.
