Phase 1 · The Data Tier

What this is and why it matters

Phase 1 teaches you how data moves, copies itself, and survives a crash.

In real systems, the worst moment is losing data or going down when one machine dies.

You run small practice systems on your own computer, using fake data, and finish with one fake order flowing through five tools.

Who this is for

A beginner who can already use a terminal and Docker (if you cannot yet, do Phase 2 first — it teaches Linux, Git and Docker from zero). You need only a computer and internet. No paid tool is needed anywhere in this phase. Every lab runs on your own machine with Docker. No cloud account. No card.

Fake data only

Every example in this phase uses made-up data: fake orders, fake names, fake file names. Nothing here is real data from any real system or company. When you build your own version later, use your own test data the same way — never copy real data into a practice setup.

The map — what each thing does, in plain words

Read this first. One idea per line.

  • Kafka — a message queue. Think of it as a line of messages waiting in order. One program puts a message in the line. Another program takes messages out of the line and does the work. If the worker is slow or stops, the messages wait safely in the line.
  • PostgreSQL — the main record book. A database that stores your real records (orders, users, settings) in tables, and keeps them safe even when the power goes out.
  • Patroni — a watcher for PostgreSQL. It watches the main database. If the main one dies, Patroni promotes the standby copy to be the new main one, by itself.
  • Redis — a fast memory store. It keeps small answers in memory so your app can read them in a blink, instead of asking the database every time. It is also used as a simple counter and a short-term waiting room.
  • Object store — a big file cupboard. It stores files (pictures, documents, uploads) by name. You ask for a file by its name and you get it back. Moto is the free stand-in used in this kit — it speaks the same S3 language as the paid stores, so what you learn here transfers.
  • Load balancer — a traffic guard. It stands in front of three copies of your app and sends each visitor to a different copy, so no single copy gets all the work. If one copy dies, it sends visitors to the copies that are still alive. A paid box called F5 does this job in big companies. This kit uses NGINX instead — it is free, and it teaches the same idea.
  • Replication — keeping a second copy up to date. The main database writes down everything it does, and the standby copy reads that list and does the same things, so it is always almost as new as the main one.
  • Failover — the standby taking over. When the main one dies, the standby becomes the new main one, and work continues.

How they fit together — one generic system

  1. A visitor arrives. The load balancer sends them to one of three copies of the app.
  2. The app takes the order and puts a message on Kafka. The message waits in line.
  3. A worker takes the message from Kafka and saves the order in PostgreSQL.
  4. The worker also writes a quick count in Redis, so the app can show "how many orders" without asking the database.
  5. Any files (like a receipt) go into the object store.
  6. PostgreSQL copies every change to its standby. Kafka copies its messages to its standby too.
  7. If the main database dies, Patroni (or your own command in the lab) promotes the standby. Work continues.

The order — do the labs in this order

  1. kafka-lab.md — send and receive messages, then copy them to a second Kafka with MirrorMaker 2. (About 1 day.)
  2. postgresql-lab.md — a main database and a standby copy, streaming replication, then failover. Includes a Patroni part. (About 2 days.)
  3. redis-lab.md — a fast cache, expiry, counters, and what two-way sync means. (About half a day.)
  4. object-store-lab.md — store files in Moto, copy them to a second store. (About half a day.)
  5. load-balancer-lab.md — NGINX in front of three backends. Kill one backend and watch the site stay up. (About half a day.)
  6. end-to-end-lab.md — all of it together, on one machine, with one command. A fake order flows from a file to the database, then you kill the main database and watch the standby take over. (About 1 day.)

Rough total: about 1 week at 1–2 hours a day, after Phase 2.

What you need before you start

  • Docker running on your machine (Phase 2, zero-cost-lab.md).
  • A terminal. All commands run in a terminal.
  • About 4 GB of free disk space — the lab images are big.
  • A machine with at least 4 GB of memory. The end-to-end lab runs eleven small services at once; on a 2 GB machine it will be slow. If it is slow, run the single-topic labs one at a time instead.
  • After unzipping, run chmod -R a+r . in the kit folder once. Some lab files must be readable by the programs inside the containers, and a zip can strip that. The labs remind you where it matters. chmod prints nothing when it works — that is normal. If a lab later says a file is not readable, you probably ran it in the wrong folder: move into the kit folder and run it again.

What is inside your downloaded zip

This kit is a hands-on learning environment that lets you practice real DevOps tasks directly on your own computer.

You download it so you can run databases, message queues, and deployment setups locally without paying for cloud servers or risking breaking live production systems.

Inside your download, you will find lab folders containing ready-to-run setup recipes, step-by-step Markdown lessons, and proof template files to record your completed work.

If you hit an issue while running a lab, a built-in doctor script checks your machine health, and an error decoder shows you how to resolve common failures.

The Phase 1 zip unzips into one folder called phase1. It holds:

  • start-here.md — this file: the map of the whole phase.
  • lesson-0.md — the true-beginner start: what the words mean, how to install Docker, first checks.
  • The 6 lab guides: kafka-lab.md, postgresql-lab.md, redis-lab.md, object-store-lab.md, load-balancer-lab.md, end-to-end-lab.md.
  • error-decoder.md — find your error message, read the fix.
  • portfolio/ — a README template and blank proof forms. When a lab says "save your proof", the proof goes in there.
  • One folder per lab (kafka-lab, postgresql-lab, redis-lab, object-store-lab, load-balancer-lab, end-to-end), each with its docker-compose.yml — the list of containers for that lab. You do not read or change it; the lab steps tell you the commands to run.
  • kit-doctor.sh — checks your machine before you start (see "If you get stuck" below). reset.sh — wipes one lab's data and starts it fresh.

If you get stuck

  1. Run bash kit-doctor.sh in the phase1 folder — it checks Docker, ports, disk, and memory, and prints a plain-English FIX line for anything wrong.
  2. Look the exact error line up in the Error Decoder (error-decoder.md).
  3. Email support@promptstudioai.in with the exact error line and the step you were on. We reply within 24 hours.

The one rule

One step at a time, in order. Do not jump to the end-to-end lab before you can run Kafka and PostgreSQL alone. At every step, do the commands yourself. Reading alone is not enough.

How to use these files

  • Every lab follows the same shape: what it is, what you need, then numbered steps. Each step says what to do, what you should see, and what to do if it breaks.
  • Every command is copy-paste ready. Type it exactly as shown.
  • "You should see" lines show the real output. If yours looks different, read the fix box under that step before moving on.
  • All passwords in this phase are practice passwords on your own machine, for learning only. Never use them anywhere real.

Words you will see a lot

  • Service — one running program in a Docker Compose file.
  • Container — a small box that holds one program and what it needs to run.
  • Compose — a tool that starts several containers together from one file (docker-compose.yml).
  • Topic — a named line of messages in Kafka.
  • Producer — a program that puts messages into Kafka.
  • Consumer — a program that takes messages out of Kafka.
  • Primary — the main copy of a database. It takes writes.
  • Replica / standby — a copy that follows the primary. It takes reads. It becomes the new primary on failover.
  • WAL — the write-ahead log. The list of changes a database writes down first, before it changes the real data. The replica reads this list to stay in sync.
  • Port — a numbered door. 5432 is the usual door for PostgreSQL, 6379 for Redis, 9092 for Kafka, 9000 for the object store (Moto), 80 for a website.
  • localhost — this machine. When a lab says open http://localhost:8080, it means your own machine, port 8080.

Test status — read this first

This phase was written on 20 November 2026. Every lab file in this phase has its own test status at the top. The status means one of three things, and the file says which one:

  • Run end-to-end — the lab was run start to finish on a clean machine and every "you should see" line matched.
  • Syntax-checked only — the files were checked for correct syntax (YAML, shell, Python), but the lab was not run end-to-end. Follow it, and if a step fails, read the error first — that is the real skill.
  • Not tested — the step is written from the tool's own docs and is marked clearly. Do not trust it blindly; check the tool's docs if it fails. No lab in this kit claims a test that did not happen.
