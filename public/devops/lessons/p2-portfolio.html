Project 1 — A website in a container

Build it

  1. Make a folder called my-site inside ~/devops-practice and put one index.html page in it that says what the site is. Then move into that folder before you build:
cd ~/devops-practice/my-site

Example content for index.html (make it with the method in zero-cost-lab.md, "How to make a file"):

<h1>My DevOps practice site</h1>
<p>This site runs in a Docker container I built myself.</p>
  1. Add a Dockerfile — the recipe file that tells Docker how to build your container:
FROM nginx
COPY index.html /usr/share/nginx/html/index.html
  1. From inside the my-site folder, build and run it:
docker build -t my-site:1.0 .
docker run -d -p 8080:80 --name my-site my-site:1.0

If port 8080 is already in use, stop the container using it or run with -p 8081:80 instead and open http://localhost:8081. Clean up when done: docker stop my-site, then docker rm my-site.

  1. Open http://localhost:8080 and check it works.
  2. Push the folder to GitHub (first time: follow zero-cost-lab.md Step 7; after that, git add ., git commit, git push).

Project 2 — A pipeline that tests and builds

Build it

  1. Use Project 1's repository.
  2. Make the folder for the workflow file, then add .github/workflows/build.yml (see zero-cost-lab.md, "How to make a file", for how to create files):
mkdir -p .github/workflows
name: build
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Test the site
        run: |
          test -f index.html
          grep -q "My DevOps practice site" index.html
      - name: Build the image
        run: docker build -t my-site:1.0 .

The test step runs BEFORE the build: it fails if index.html is missing or does not hold the site's heading, so a broken site never gets built. A pipeline that only builds is not a pipeline that tests — the test step is the point.

  1. Push, open the Actions tab on GitHub, and watch the pipeline run. Break it once on purpose (for example, delete the heading from index.html so the test step fails, or a typo in the Dockerfile so the build fails), read the log, fix it, and push again.

Project 3 — Infrastructure as code + monitoring, zero-cost

Build it

  1. Install Terraform (the tool that creates infrastructure from files). Its install steps differ by system, so follow the official Terraform install docs for your machine — this step is unverified in this kit.
  2. Write a small Terraform file called main.tf (Terraform reads every .tf file in the folder) that creates a local container using the Docker provider (Terraform talks to Docker on your own machine — no cloud account, no bill):
terraform {
  required_providers {
    docker = {
      source = "kreuzwerker/docker"
    }
  }
}

resource "docker_image" "web" {
  name = "nginx:latest"
}

resource "docker_container" "web" {
  image = docker_image.web.image_id
  name  = "terraform-web"
  ports {
    internal = 80
    external = 8080
  }
}

Run terraform init, then terraform apply, and check http://localhost:8080. init downloads the Docker provider the file asks for. Once you have a working run, pin the provider version: add a version line inside the docker provider block with the version you tested, and keep the .terraform.lock.hcl file init creates — do not delete it casually. No version is pinned here because none was tested end-to-end yet.

To check nothing changed, run terraform plan after the first apply — it should report no changes. If the plan shows changes, read it before you apply; something drifted or changed.

Clean up when you are done: first check you are in the right folder and read the plan with terraform plan -destroy. Then terraform destroy removes what Terraform created. Run it only on your own practice setup, never on anything shared or real.

  1. Add monitoring with Docker Compose (a tool that starts several containers together from one file). You will run three small programs on your own machine: Prometheus (collects numbers), Grafana (turns numbers into charts), and node-exporter (reports numbers from inside its own container). This demo shows container monitoring — it does not measure your whole host machine. On a Linux host you can add host mounts later; on Docker Desktop or WSL2, the numbers describe the Linux container environment, not your Windows or Mac host. No cloud account, no bill.

Make a folder called monitoring inside ~/devops-practice and put two files in it.

File 1 — docker-compose.yml:

services:
  prometheus:
    image: prom/prometheus
    ports:
      - "127.0.0.1:9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
  node-exporter:
    image: prom/node-exporter
    ports:
      - "127.0.0.1:9100:9100"
  grafana:
    image: grafana/grafana
    ports:
      - "127.0.0.1:3000:3000"

Ports are bound to 127.0.0.1 (this machine only) on purpose — this is a local learning stack, not a shared service. Images here have no version tags, so a later pull may change them. Once you have a working run, pin the versions you used and record them in the README.

File 2 — prometheus.yml (the file that tells Prometheus what to watch — a "scrape" is Prometheus visiting an address every 15 seconds and writing down numbers):

global:
  scrape_interval: 15s
scrape_configs:
  - job_name: "prometheus"
    static_configs:
      - targets: ["localhost:9090"]
  - job_name: "practice-machine"
    static_configs:
      - targets: ["node-exporter:9100"]

A "job" is just a named thing to watch. node-exporter:9100 works because Docker Compose lets containers reach each other by service name. localhost:9090 works for Prometheus itself because it is watching its own container.

Start it all:

cd ~/devops-practice/monitoring
docker compose up -d
docker compose ps

All three should show as running. If docker compose fails, older Docker uses docker-compose (with a hyphen) — try that instead.

Check Prometheus first: open http://localhost:9090, click Status, then Targets. Both jobs should show UP, with the target address and last-scrape time beside them. If a target shows DOWN, work in this order: docker compose ps (is the container running?), docker compose logs <service> (what did it print?), then the error line under the target in Prometheus.

Now open Grafana: http://localhost:3000. Log in with username admin and password admin, and change that default password at first login — this stack is local learning only, not secured for sharing. If it asks you to set a new password, set one you will remember.

Add Prometheus as the data source: go to Connections, then Data sources, then Add data source, choose Prometheus, and set the URL to http://prometheus:9090 — Grafana reaches Prometheus by its service name, not by localhost. Then Save & test. It should say the data source is working.

Make your first chart: create a new Dashboard, add a Visualization, choose Prometheus, type the query up, and run it. The chart shows 1 for every target that is up and 0 for one that is down. up = 1 means Prometheus successfully scraped that target. It does not prove the website itself works — only that the target answered the scrape. Save the dashboard and keep a screenshot of it.

Stop everything when you are done: docker compose down. Your files stay, so docker compose up -d starts it again later.

Note: Grafana's menu words can differ slightly by version — if a button name differs, look for the closest match. This exact stack was not run end-to-end while writing this kit, so if a step fails, read the error message first.

  1. Push to GitHub — but not everything. First make a .gitignore file in the project folder with at least these lines, then run git status and check nothing private is staged:
.terraform/
*.tfstate
*.tfstate.*
crash.log

Commit: the .tf files, .terraform.lock.hcl, the Compose file, prometheus.yml, and the README. Never commit state files, the provider cache, or secrets — state can hold private values.

A clear warning

Terraform with a cloud provider (AWS, Azure, and similar) can cost real money. Do the local Docker version first. Only try a cloud version if you understand that provider's free tier and you destroy what you create afterwards. This kit does not promise any setup is free on the cloud.

Project 4 — A data-tier pipeline, end to end (Phase 1)

Build it

This project is the Phase 1 end-to-end lab, done as a portfolio piece. Do the Phase 1 single-topic labs first (Kafka, PostgreSQL, Redis, object store, load balancer), then run the end-to-end lab in the Phase 1 folder:

  1. Start it with one command: docker compose up -d --build.
  2. Watch three fake orders flow from files to Kafka to PostgreSQL, with the counter in Redis and the files in Moto.
  3. Add a fourth order yourself and watch it flow through.
  4. Kill the main database, promote the standby, point a fresh worker at it, and send a fifth order through the new main database.
  5. Push the lab folder to GitHub (the compose file, the two Python programs, the sample order files, and the README below). Do not push any real data — the sample orders are fake, and that is the point.

README template — fill in the blanks

# Order pipeline demo (Kafka + PostgreSQL + Redis + Moto + NGINX)
What it is: [one line]
How it works: a fake order file lands in incoming/, ingest stores
  it in Moto and sends it to Kafka, worker saves it in PostgreSQL
  and updates the Redis counter, NGINX spreads visitors across
  three backends.
Tools used: Docker Compose, Kafka, PostgreSQL, Redis, Moto, NGINX, Python
Failover I proved: killed the main database, promoted the standby
  with pg_promote(), sent a new order through the new main database.
Cost: local only, no cloud bill.

You have: a running container app, a working pipeline, an infrastructure-as-code setup with a monitoring chart, and a data pipeline with a proven failover — all on GitHub, all runnable, all explained in your own words. That is the proof this kit is built to give you.
