What this lab is

You will run two Redis stores on your own machine: a main one and a copy that follows it. You will save fake values, set expiry times, use a counter, and see what happens when you try to write to the copy. All data is fake.

What you need first

  • Docker running (Phase 2, zero-cost-lab.md).
  • The file in this folder: docker-compose.yml.

Words you need here

  • Redis — a store that keeps data in memory, so reads are very fast. It is used for caches, counters and short-term data.
  • Key and value — Redis stores things by name. The name is the key, the thing stored is the value. Example: key user:101, value Asha.
  • Cache — a fast copy of an answer, kept so you do not have to ask the slow database again.
  • Expiry (TTL) — a time limit on a key. When the time runs out, Redis deletes the key by itself.
  • Replica — a copy that follows the main store. It takes reads only.
  • CRDT — a way for two stores to accept writes at the same time and merge them. It is a paid feature. This lab shows the idea in plain words and shows the free one-way copy instead.

Step 1 — Start both stores

From inside this folder:

docker compose up -d

Check:

docker compose ps

You should see redis-a and redis-b with STATUS "Up". Check they answer:

docker exec redis-a redis-cli ping

You should see:

PONG

If it breaks: if ping shows nothing, wait 10 seconds and try again. Redis starts fast, but the first start downloads the image.

Step 2 — Save and read a value

Save a fake user:

docker exec redis-a redis-cli SET user:101 Asha

You should see:

OK

Read it back:

docker exec redis-a redis-cli GET user:101

You should see:

"Asha"

The quotes are part of how redis-cli shows a value. The value stored is Asha.

Step 3 — Set a value that deletes itself

Save a login code that lasts 60 seconds:

docker exec redis-a redis-cli SETEX login-code:101 60 482913

You should see OK. Check how long is left:

docker exec redis-a redis-cli TTL login-code:101

You should see a number near 60 (it counts down — 58, 57, and so on). Wait 65 seconds and read it again:

docker exec redis-a redis-cli GET login-code:101

You should see:

(nil)

(nil) means "nothing here" — the key deleted itself when its time ran out. This is how login codes and short-lived sessions work: the store cleans up by itself.

Step 4 — Use a counter

Counters are the simplest thing Redis does well. Make one:

docker exec redis-a redis-cli SET orders:count 0
docker exec redis-a redis-cli INCR orders:count
docker exec redis-a redis-cli INCR orders:count
docker exec redis-a redis-cli INCR orders:count
docker exec redis-a redis-cli GET orders:count

You should see:

"3"

Each INCR adds 1. In the end-to-end lab, a worker does this every time an order is saved — that is how the app shows "how many orders" without asking the database.

Step 5 — Read the same values from the copy

The copy follows the main store. Read from it:

docker exec redis-b redis-cli GET user:101
docker exec redis-b redis-cli GET orders:count

You should see "Asha" and "3". The copy has the same data. Now check what the copy thinks it is:

docker exec redis-b redis-cli INFO replication

You should see a line role:slave (older Redis still calls a replica "slave") and a line master_host:redis-a. That is the proof it is following the main store.

Step 6 — Try to write on the copy (it must refuse)

docker exec redis-b redis-cli SET user:102 Ravi

You should see an error like:

(error) READONLY You can't write against a read only replica.

That error is the proof. A one-way copy takes reads only. This is correct and expected — do not try to fix it.

Step 7 — The two-way idea, in plain words

What if two stores both accept writes at the same time? Then they must merge the changes. That merge rule is called a CRDT. It is a paid feature in Redis products. The free Redis in this lab does not have it. The idea is the same as a shared document: if two people change the same line at the same time, the system needs a rule for which change wins. With a CRDT, the rule is built into the data itself, so both copies end up the same without arguing. For this lab, remember this: one-way copy is free and simple; two-way copy is a paid feature with rules you must understand before you use it.

Clean up

docker compose down

The data is in named volumes, so it survives a restart. Run docker compose down -v to wipe it. The data was fake.

What you can now say, truthfully

"I ran two Redis stores, saved and read values, set keys that expire by themselves, used a counter, and proved a replica takes reads only."

What this lab does NOT cover

  • Redis Cluster (many nodes sharing the data) is a bigger setup. The ideas are the same; the setup is bigger.
  • Redis persistence (saving to disk) is on in this lab with --appendonly yes, so data survives a restart. In real work, check the disk settings before you trust it.
