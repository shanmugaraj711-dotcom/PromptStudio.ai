Redis Lab — A Fast Memory Store

Phase 1 · The Data Tier

What this is and why it matters

Redis is a fast memory store: it keeps small answers in memory so they can be read in a blink.

In real systems, asking the main database for every small answer is slow — a memory store takes that load off it.

This lab runs a main store and a copy that follows it, then the copy stops following and becomes a main store itself.

Test status

What this lab is

You will run two Redis stores on your own machine: a main one and a copy that follows it. You will save fake values, set expiry times, use a counter, and see what happens when you try to write to the copy. All data is fake.

What you need first

  • Docker running (Phase 2, zero-cost-lab.md).
  • The file in this folder: docker-compose.yml.

Words you need here

  • Redis — a store that keeps data in memory, so reads are very fast. It is used for caches, counters and short-term data.
  • Key and value — Redis stores things by name. The name is the key, the thing stored is the value. Example: key user:101, value Asha.
  • Cache — a fast copy of an answer, kept so you do not have to ask the slow database again.
  • Expiry (TTL) — a time limit on a key. When the time runs out, Redis deletes the key by itself.
  • Replica — a copy that follows the main store. It takes reads only.
  • CRDT — a way for two stores to accept writes at the same time and merge them. It is a paid feature. This lab shows the idea in plain words and shows the free one-way copy instead.

Step 1 — Start both stores

From inside this folder:

Try it Yourself »Open the practice terminal and run it yourself — nothing installs. Included with Phase 1. Simulation — practice version. Run the real lab with Docker to do it for real.
Command
docker compose up -d
Expected output
[+] Running 2/2
 ✔ Container redis-a  Started
 ✔ Container redis-b  Started

Check:

Command
docker compose ps
Expected output
NAME       STATUS
redis-a    Up
redis-b    Up

(The real table has more columns. What matters is both names, each with STATUS "Up".) Check they answer:

Command
docker exec redis-a redis-cli ping
Expected output
PONG

If it breaks: if ping shows nothing, wait 10 seconds and try again. Redis starts fast, but the first start downloads the image.

Step 2 — Save and read a value

Save a fake user:

Command
docker exec redis-a redis-cli SET user:101 Asha
Expected output
OK

If it breaks: "Could not connect" means redis-a is not up yet — run docker compose ps and wait until it shows "Up".

Read it back:

Command
docker exec redis-a redis-cli GET user:101
Expected output
"Asha"

The quotes are part of how redis-cli shows a value. The value stored is Asha.

If it breaks: if you see (nil) ("nothing here"), the SET step never saved — run the SET command again and check it prints OK.

Step 3 — Set a value that deletes itself

Save a login code that lasts 60 seconds:

Command
docker exec redis-a redis-cli SETEX login-code:101 60 482913
Expected output
OK

Check how long is left:

Command
docker exec redis-a redis-cli TTL login-code:101
Expected output
58

If it breaks: if TTL shows -2, the key is already gone — its 60 seconds ran out before you checked. Run the SETEX command again. Wait 65 seconds and read it again:

Command
docker exec redis-a redis-cli GET login-code:101
Expected output
(nil)

(nil) means "nothing here" — the key deleted itself when its time ran out. This is how login codes and short-lived sessions work: the store cleans up by itself.

If it breaks: if the code is still there after 65 seconds, check you waited long enough — the key lives for a full 60 seconds from the SETEX command, not from when you first read it.

Step 4 — Use a counter

Counters are the simplest thing Redis does well. Make one:

Command
docker exec redis-a redis-cli SET orders:count 0
docker exec redis-a redis-cli INCR orders:count
docker exec redis-a redis-cli INCR orders:count
docker exec redis-a redis-cli INCR orders:count
docker exec redis-a redis-cli GET orders:count
Expected output
"3"

Each INCR adds 1. In the end-to-end lab, a worker does this every time an order is saved — that is how the app shows "how many orders" without asking the database.

If it breaks: if GET shows "0", the first SET step was skipped — run SET orders:count 0 first, then the three INCRs.

Step 5 — Read the same values from the copy

The copy follows the main store. Read from it:

Command
docker exec redis-b redis-cli GET user:101
docker exec redis-b redis-cli GET orders:count
Expected output
"Asha"
"3"

If it breaks: if either shows (nil), the copy has not caught up yet — wait 10 seconds and read again.

Now check what the copy thinks it is:

Command
docker exec redis-b redis-cli INFO replication
Expected output
# Replication
role:slave
master_host:redis-a
master_port:6379

That is the proof it is following the main store.

If it breaks: if the role shows master, the copy never linked to the main store — restart it with docker compose restart redis-b and wait 10 seconds.

Step 6 — Try to write on the copy (it must refuse)

Command
docker exec redis-b redis-cli SET user:102 Ravi
Expected output
(error) READONLY You can't write against a read only replica.

That error is the proof. A one-way copy takes reads only. This is correct and expected — do not try to fix it.

If it breaks: if the SET returns OK instead of the READONLY error, you ran it on redis-a by mistake — check the container name in the command (redis-b, not redis-a) and try again.

Step 7 — The two-way idea, in plain words

What if two stores both accept writes at the same time? Then they must merge the changes. That merge rule is called a CRDT. It is a paid feature in Redis products. The free Redis in this lab does not have it. The idea is the same as a shared document: if two people change the same line at the same time, the system needs a rule for which change wins. With a CRDT, the rule is built into the data itself, so both copies end up the same without arguing. For this lab, remember this: one-way copy is free and simple; two-way copy is a paid feature with rules you must understand before you use it.

Clean up

Command
docker compose down
Expected output
✔ Container redis-a  Removed
✔ Container redis-b  Removed

If it breaks: "No such container" means the stores are already stopped — nothing to do.

The data is in named volumes, so it survives a restart. Run docker compose down -v to wipe it. The data was fake.

What you can now say, truthfully

"I ran two Redis stores, saved and read values, set keys that expire by themselves, used a counter, and proved a replica takes reads only."

What this lab does NOT cover

  • Redis Cluster (many nodes sharing the data) is a bigger setup. The ideas are the same; the setup is bigger.
  • Redis persistence (saving to disk) is on in this lab with --appendonly yes, so data survives a restart. In real work, check the disk settings before you trust it.

Failure drill — Promote the copy

This drill proves a copy can become a main store, and take writes, when you tell it to stop following.

Do Steps 1 to 5 first, so the copy already holds the same data as the main store.

Step 1 — Tell the copy to stop following. Run this from inside this folder:

Command
docker exec redis-b redis-cli REPLICAOF NO ONE
Expected output
OK

If it breaks: if it shows an error, redis-b is not up — run docker compose ps and wait until it shows "Up".

Step 2 — Check what the copy thinks it is now:

Command
docker exec redis-b redis-cli INFO replication
Expected output
role:master

The copy is now a main store. It no longer follows redis-a.

If it breaks: if the role still shows slave, wait 10 seconds and check again — the change takes a moment.

Step 3 — Prove it takes writes now:

Command
docker exec redis-b redis-cli SET user:102 Ravi
Expected output
OK

Read it back:

Command
docker exec redis-b redis-cli GET user:102
Expected output
"Ravi"

The copy saved a value of its own.

If it breaks: if the SET still shows the READONLY error, Step 1 did not take — run REPLICAOF NO ONE again and check it prints OK.

Checklist — tick each one when you have seen it:

  • ☐ The copy stopped following: REPLICAOF NO ONE printed OK.
  • ☐ The copy is now a main store: INFO replication shows role:master.
  • ☐ The copy takes writes: the new value saved and read back.

Reset — run this from the phase1 folder to wipe the drill and start fresh:

Command
bash reset.sh redis-lab

You should see: the script stops both stores and wipes the data, then prints that it is done.

If it breaks: "Permission denied" means the script is not marked runnable — run chmod +x reset.sh and try again.

Or, from inside this folder, the plain way: run docker compose down -v. That stops both stores and wipes the data. The data was fake.

One honest note: after this drill you have two main stores, redis-a and redis-b, and they do not talk to each other. A value saved on one does not appear on the other. That is why the reset matters — start fresh before the next lab.

Save your proof

The proof for this lab is the promoted copy: role:master in its replication info, and the counter value it holds. Save both with these commands, run from inside this folder, after the drill:

Command
mkdir -p ../portfolio/proof
docker exec redis-b redis-cli INFO replication > ../portfolio/proof/redis-promoted.txt
docker exec redis-b redis-cli GET orders:count >> ../portfolio/proof/redis-promoted.txt

Open the file and check it shows role:master and "3". That file is your proof.

You should see: nothing in the terminal when you run the save commands — the output went into the file, not the screen.

If it breaks: if the file is empty, the drill did not run yet — do the drill first (Steps 1 to 3 above), then save again.
