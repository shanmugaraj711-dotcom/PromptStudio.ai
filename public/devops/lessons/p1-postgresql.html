What this lab is

You will run two PostgreSQL databases on your own machine: a main one (primary) and a standby copy (replica). You will write fake orders into the main one, watch them appear on the standby, then kill the main one and promote the standby so work can continue. The last part shows Patroni — a watcher that does the promotion for you.

What you need first

  • Docker running (Phase 2, zero-cost-lab.md).
  • The files in this folder: docker-compose.yml, 01-replicator.sql, replica-entrypoint.sh. The patroni/ folder is used only in the last part.

Words you need here

  • Primary — the main database. It takes writes (new rows).
  • Replica / standby — a copy that follows the primary. It takes reads only. It becomes the new primary on failover.
  • WAL — the write-ahead log. A list of every change, written down first, before the real data changes. The replica reads this list to stay in sync. WAL streaming means the replica reads the list live, as changes happen.
  • Replication slot — a bookmark the primary keeps, so it does not throw away WAL entries the replica still needs.
  • Failover — the standby taking over as the new primary.
  • Patroni — a program that watches the databases and does the failover by itself.

Part 1 — Primary and replica

Step 1 — Start both databases

From inside this folder, first make the database setup file readable. The database runs as its own user, and it cannot read a file that is private to you. This one command fixes that. chmod is short for "change mode" — it changes who can read a file. -R means every file in this folder, and a+r means everyone can read.

Command
chmod -R a+r .

Then start both databases:

Command
docker compose up -d

Check:

Command
docker compose ps

You should see pg-primary and pg-replica with STATUS "Up". The replica copies all data from the primary the first time it starts, so it takes about a minute. Check its log:

Command
docker compose logs replica

You should see the line "Copy done." near the end.

If it breaks: if the replica log shows "waiting for the primary" for more than two minutes, check the primary is up with docker compose ps. If the primary is up and the replica still waits, read the replica log from the top — the error line is usually about the password or the connection.

Step 2 — Write three fake rows on the primary

Connect to the primary and make a small table:

Command
docker exec pg-primary psql -U learner -d practice -c "CREATE TABLE orders (id INT, item TEXT, amount INT); INSERT INTO orders VALUES (101, 'notebook', 250), (102, 'pen', 40), (103, 'mug', 350);"
Expected output
CREATE TABLE
INSERT 0 3

"INSERT 0 3" means 3 rows went in. The data is fake — made up for this lab.

If it breaks: "relation already exists" means you already made the table — skip the CREATE part and just run the INSERT, or drop the table first with DROP TABLE orders; and start this step again.

Step 3 — Read the same rows from the replica

Now ask the replica. It should already have the same rows, because it follows the primary live:

Command
docker exec pg-replica psql -U learner -d practice -c "SELECT * FROM orders ORDER BY id;"
Expected output
 id  |   item   | amount
-----+----------+--------
 101 | notebook |    250
 102 | pen      |     40
 103 | mug      |    350
(3 rows)

If it breaks: if the replica shows 0 rows, wait 10 seconds and try again — the copy takes a moment. If it still shows 0 rows, check the replica is really a replica: run docker exec pg-replica psql -U learner -d practice -c "SELECT pg_is_in_recovery();" You should see t (true). If it shows f, the replica is not following the primary — stop and start it again with docker compose restart replica.

Step 4 — Try to write on the replica (it must refuse)

A standby takes reads only. Try an insert on the replica:

Command
docker exec pg-replica psql -U learner -d practice -c "INSERT INTO orders VALUES (104, 'pen stand', 120);"
Expected output
ERROR:  cannot execute INSERT in a read-only transaction

That error is the proof. The replica refuses writes. This is correct and expected — do not try to fix it.

Step 5 — Kill the primary and promote the replica

Stop the primary:

Command
docker compose stop primary

Check the replica still answers reads:

Command
docker exec pg-replica psql -U learner -d practice -c "SELECT * FROM orders ORDER BY id;"

You should see the same 3 rows. The data survived — the replica has its own copy.

Now promote the replica to be the new primary:

Command
docker exec pg-replica psql -U learner -d practice -c "SELECT pg_promote();"
Expected output
 pg_promote
------------
 t

t means true — the promotion worked. Check it is no longer in recovery:

Command
docker exec pg-replica psql -U learner -d practice -c "SELECT pg_is_in_recovery();"

You should see f (false). It is now a primary.

Prove it takes writes now:

Command
docker exec pg-replica psql -U learner -d practice -c "INSERT INTO orders VALUES (104, 'pen stand', 120); SELECT * FROM orders ORDER BY id;"

You should see 4 rows, including 104 | pen stand | 120. Failover done — by hand.

If it breaks: if pg_promote() shows f, the replica was already promoted (maybe you ran this step twice) — check with SELECT pg_is_in_recovery();. If it shows f, you are done.

Step 6 — The honest part: the old primary cannot just rejoin

The old primary still has the old data. It does not know about row 104. It cannot rejoin as a replica by itself. In real work, you rebuild it from the new primary, the same way the replica was first built — copy the data with pg_basebackup, then start it as a standby. The commands are the same as the ones in replica-entrypoint.sh. For this lab, the simple way back is:

Command
docker compose down -v
docker compose up -d

That wipes both databases and starts fresh. The data was fake, so losing it is fine.

Part 2 — Patroni does the failover for you (advanced)

What Patroni is

In Part 1 you promoted the replica by hand. Patroni is a watcher program that does that job by itself: it watches the main database, and if it dies, Patroni promotes the standby within seconds. It keeps its notes in etcd — a small notebook service that all the Patroni nodes share.

Step 1 — Start the Patroni cluster

From inside the patroni/ folder:

Command
docker compose up -d --build

The first start builds the Patroni image, so it takes a few minutes. Check the cluster:

Command
curl http://localhost:8008/cluster

You should see JSON with two members, one with "role": "leader" and one with "role": "replica". (If curl is not installed on your machine, open http://localhost:8008/cluster in your browser instead — same text.)

If it breaks: if the page does not load, wait a minute — the first node builds the database from scratch. Check the logs with docker compose logs patroni-1.

Step 2 — Write a row, watch it copy

Command
docker exec patroni-1 psql -U learner -d postgres -c "CREATE TABLE orders (id INT, item TEXT); INSERT INTO orders VALUES (201, 'stapler');"

You should see CREATE TABLE and INSERT 0 1. Now read it from the second node:

Command
docker exec patroni-2 psql -U learner -d postgres -c "SELECT * FROM orders;"

You should see row 201. (The database name here is postgres, the default — Patroni's bootstrap does not create a database called practice.)

Step 3 — Kill the leader and watch Patroni promote the other one

Command
docker compose stop patroni-1

Wait 30 seconds, then check the cluster again:

Command
curl http://localhost:8009/cluster

You should see patroni-2 now has "role": "leader". Patroni promoted it by itself — no command from you. Prove it takes writes:

Command
docker exec patroni-2 psql -U learner -d postgres -c "INSERT INTO orders VALUES (202, 'ruler'); SELECT * FROM orders;"

You should see both rows, 201 and 202.

Step 4 — Bring the old leader back

Command
docker compose start patroni-1

Wait a minute, then check the cluster:

Command
curl http://localhost:8008/cluster

You should see patroni-1 back, now as a "replica". It rejoined by itself and copied the new data from the leader. That is what Patroni is for.

Clean up

Command
docker compose down -v

That stops everything and wipes the data. The data was fake.

What you can now say, truthfully

"I ran a PostgreSQL primary and a standby with WAL streaming, proved the standby had the same data, promoted it by hand when the primary died, and ran a Patroni cluster that did the same failover by itself."

What this lab does NOT cover

  • Real clusters run three or more database nodes, not two.
  • pg_rewind (used in the Patroni setup) lets an old primary rejoin faster. The plain lab in Part 1 does not use it — that is why the old primary must be rebuilt there.
  • Backups are a different job from replication. Replication protects you when a machine dies. Backups protect you when data is deleted by mistake. You need both in real work.

Failure drill — Kill the leader, watch Patroni promote

This drill proves Patroni promotes the standby by itself when the leader dies, and no rows are lost.

Do Part 2 first, up to Step 2, so row 201 is already saved.

Step 1 — Go into the Patroni folder and stop the leader:

Command
cd patroni
docker compose stop patroni-1
Expected output
✔ Container patroni-1  Stopped

Step 2 — Wait 30 seconds, then check the cluster on the second node's port:

Command
curl http://localhost:8009/cluster
Expected output
{ "members": [
  {"name": "patroni-2", "role": "leader"},
  {"name": "patroni-1", "role": "replica"} ] }

(The real answer is longer. The two lines above are the part that matters.)

Step 3 — Prove the new leader takes writes:

Command
docker exec patroni-2 psql -U learner -d postgres -c "INSERT INTO orders VALUES (202, 'ruler'); SELECT * FROM orders;"
Expected output
INSERT 0 1
 id  |  item
-----+---------
 201 | stapler
 202 | ruler
(2 rows)

Both rows are there. Row 201 survived, and row 202 is new.

Step 4 — Bring the old leader back:

Command
docker compose start patroni-1
Expected output
✔ Container patroni-1  Started

Wait a minute, then check the cluster:

Command
curl http://localhost:8008/cluster

You should see patroni-1 back, now as a "replica".

Checklist — tick each one when you have seen it:

  • ☐ The leader changed: patroni-2 became the leader.
  • ☐ No rows lost: row 201 is still there after the failover.
  • ☐ New row saved: row 202 was written to the new leader.

Reset — run this from the phase1 folder to wipe the drill and start fresh:

Command
bash reset.sh postgresql-lab/patroni

Or, from inside the patroni folder, the plain way:

Command
docker compose down -v && docker compose up -d

That stops everything and wipes the data. The data was fake.

Save your proof

The proof for this lab is the failover log: the cluster output showing the new leader, and the row count before and after. Save the cluster output with this command, run from inside the patroni/ folder, after the drill:

Command
mkdir -p ../../portfolio/proof
curl http://localhost:8009/cluster > ../../portfolio/proof/failover-log.txt

Then open portfolio/proof/failover-log-TEMPLATE.txt, copy it to failover-log.txt if you want the full format, and add the row counts by hand. That file is your proof.
