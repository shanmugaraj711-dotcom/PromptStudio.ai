Object Store Lab — A File Cupboard

Phase 1 · The Data Tier

What this is and why it matters

An object store is a big file cupboard: you store a file by a name and ask for it back by the same name.

In real systems, the failure that hurts is losing uploaded files when one store goes down.

This lab runs two file stores, and a mirror copies every new file from the first store to the second by itself.

What this lab is

You will run two file stores on your own machine with Moto — a free S3-compatible stand-in that works the same way as the paid stores. You will put fake receipt files into the first store and watch them appear in the second store by themselves. All files are fake.

What you need first

  • Docker running (Phase 2, zero-cost-lab.md).
  • The files in this folder: docker-compose.yml, Dockerfile, mirror.sh, and the files/ folder with two fake receipts.

Words you need here

  • Object store — a big file cupboard. You store a file by a name, and you ask for it back by the same name. It does not care what is inside the file.
  • Bucket — a named box inside the store. Files live in buckets. This lab uses one bucket called incoming.
  • Moto — a free stand-in for Amazon S3. It speaks the same S3 language as the paid stores, so what you learn here transfers. It keeps everything in memory: stop the lab and the files are gone. That is fine for learning.
  • aws — the command tool for S3 stores. It works like the cp and ls commands, but for buckets. Every command below says which store it talks to, with --endpoint-url.
  • Mirror — a copy that follows the original. When a new file lands in the first store, the mirror copies it to the second store.

Step 1 — Start both stores

From inside this folder:

Command
docker compose up -d --build

You should see: the build lines for the small aws image, then the containers start. The first start builds the small aws image, so it takes a couple of minutes. Check:

Command
docker compose ps
Expected output
NAME       STATUS
moto-a     Up
moto-b     Up
mirror     Up
awscli     Up

(The real table has more columns. What matters is all four names, each with STATUS "Up".) The mirror service waits for both stores, so give it a minute. Check the first store answers:

Command
docker compose exec awscli aws --endpoint-url http://moto-a:5000 s3 ls

You should see nothing (no buckets yet) and no error. An empty answer with no error means the store is up.

If it breaks: if docker compose ps shows a container as "Exited", read its log with docker compose logs <name> and look for the error line.

Step 2 — Make the bucket (once)

The awscli container holds the file commands. Make the bucket in the first store:

Command
docker compose exec awscli aws --endpoint-url http://moto-a:5000 s3 mb s3://incoming
Expected output
make_bucket: incoming

If it breaks: "BucketAlreadyExists" means you already made it — skip this step. If the command fails, the store is not up yet — wait and try again.

Step 3 — Put a fake file in

Copy the first fake receipt into the bucket:

Command
docker compose exec awscli aws --endpoint-url http://moto-a:5000 s3 cp /files/receipt-001.txt s3://incoming/
Expected output
upload: /files/receipt-001.txt to s3://incoming/receipt-001.txt

If it breaks: "NoSuchBucket" means the bucket was never made — go back to Step 2 and make it. "No such file" means the receipt file is missing — check the files/ folder holds receipt-001.txt.

List the bucket to prove it is there:

Command
docker compose exec awscli aws --endpoint-url http://moto-a:5000 s3 ls s3://incoming/
Expected output
2026-11-20 00:00:00        126 receipt-001.txt

(The date and time will match when you ran it, not the line above.)

If it breaks: if the list is empty, the upload in the step above did not happen — run the cp command again and check it prints the upload: line.

Step 4 — Watch it appear in the second store

The mirror service copies new files from a to b every 10 seconds. Wait 30 seconds, then list the second store:

Command
docker compose exec awscli aws --endpoint-url http://moto-b:5000 s3 ls s3://incoming/
Expected output
2026-11-20 00:00:00        126 receipt-001.txt

(The date and time will match when you ran it, not the line above.) The copy happened by itself — you did not copy it twice.

If it breaks: if the file is missing, wait another minute and list again — the mirror checks every 10 seconds. If it is still missing, check the mirror log with docker compose logs mirror and look for the word "ERROR". The most common cause is that the mirror started before the stores were ready — restart it with docker compose restart mirror and wait a minute.

Step 5 — Add a second file and watch it follow

Command
docker compose exec awscli aws --endpoint-url http://moto-a:5000 s3 cp /files/receipt-002.txt s3://incoming/
Expected output
upload: /files/receipt-002.txt to s3://incoming/receipt-002.txt

If it breaks: "NoSuchBucket" means the bucket was never made — go back to Step 2. "No such file" means the receipt file is missing — check the files/ folder holds receipt-002.txt.

Wait 30 seconds, then:

Command
docker compose exec awscli aws --endpoint-url http://moto-b:5000 s3 ls s3://incoming/
Expected output
2026-11-20 00:00:00        126 receipt-001.txt
2026-11-20 00:00:00        126 receipt-002.txt

(The dates and times will match when you ran it, not the lines above.) New files follow by themselves.

Step 6 — Download a file back

Command
docker compose exec awscli aws --endpoint-url http://moto-b:5000 s3 cp s3://incoming/receipt-001.txt -
Expected output
Fake receipt for practice only. Not a real document.
Order: order-101
Item: notebook
Amount: 250
Buyer: Asha
Date: 2026-11-20

This proves the file in the second store is a real copy, not just a name in a list.

If it breaks: "NoSuchKey" means the file is not in the second store yet — wait a minute (the mirror copies every 10 seconds) and try again.

Clean up

Command
docker compose down
Expected output
✔ Container moto-a  Removed
✔ Container moto-b  Removed
✔ Container mirror  Removed
✔ Container awscli  Removed

The files live only in memory, so stopping the lab wipes them. That is fine — the files were fake. Run the steps again any time you want to practise.

What you can now say, truthfully

"I ran two Moto object stores (a free S3 stand-in), made a bucket, uploaded files with the aws tool, and set up a mirror that copies new files to the second store by itself."

What this lab does NOT cover

  • Real stores use access keys per app, not one shared login. This lab uses one login on purpose, so you can learn.
  • The mirror here copies one way only. Two-way sync is a different setup.
  • Large files, versioning and lifecycle rules (auto-deleting old files) are later topics. The ideas are the same; the setup is bigger.

Save your proof

The proof for this lab is the same file listed in both stores. Save both listings with these commands, run from inside this folder:

Command
mkdir -p ../portfolio/proof
docker compose exec awscli aws --endpoint-url http://moto-a:5000 s3 ls s3://incoming/ > ../portfolio/proof/object-store-mirror.txt
docker compose exec awscli aws --endpoint-url http://moto-b:5000 s3 ls s3://incoming/ >> ../portfolio/proof/object-store-mirror.txt

Open the file and check both receipt-001.txt and receipt-002.txt appear twice — once per store. That file is your proof.

You should see: nothing in the terminal when you run the save commands — the listings went into the file, not the screen.

If it breaks: if the file lists each receipt only once, the mirror had not copied yet when you saved — wait a minute, then run the save commands again.
