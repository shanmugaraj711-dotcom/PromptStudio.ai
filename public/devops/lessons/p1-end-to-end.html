End-to-End Lab — One Fake Order, All the Way Through

Phase 1 · The Data Tier

What this is and why it matters

This lab is the whole pipeline: one fake order travelling through five tools, on one machine, with one start.

In real systems, the pieces only prove themselves together — the real test is when the main database dies mid-flow.

A file lands in a folder, is stored, sent as a message, saved as a row and counted, and then the standby takes over.

What this lab is

You will run a small order pipeline with one command. A fake order file lands in a folder. A program stores the file, sends the order to Kafka, and another program saves it in PostgreSQL and updates a counter in Redis. A load balancer spreads visitors across three backends. Then you kill the main database and watch the standby take over — and a new order still flows through.

What you need first

  • Docker running (Phase 2, zero-cost-lab.md).
  • The single-topic labs (kafka, postgresql, redis, object store, load balancer) done first. This lab uses all of them at once.
  • The files in this folder: docker-compose.yml, Dockerfile, requirements.txt, ingest.py, worker.py, nginx.conf, postgres/, incoming/ with three fake orders.

The fake shop, in plain words

A small online shop sells stationery. A customer places an order. The order is a small file like this:

Command
{"id": 101, "item": "notebook", "amount": 250, "buyer": "Asha"}

The order travels like this:

  1. The file lands in incoming/.
  2. ingest sees it, stores a copy of the file in the object store (Moto, a free S3-compatible stand-in, bucket incoming), and sends the order to Kafka (topic orders).
  3. worker reads the order from Kafka, saves it in PostgreSQL (table orders), and adds 1 to the counter in Redis (orders:count).
  4. The file moves to processed/ — done.
  5. Meanwhile, the load balancer (lb) spreads visitors across three backends (web1, web2, web3).
  6. PostgreSQL copies every change to its standby, live.

All names, items and amounts are made up for this lab.

Step 1 — Start everything with one command

From inside this folder, first make the database setup file readable. The database runs as its own user, and it cannot read a file that is private to you. This one command fixes that:

Command
chmod -R a+r .

You should see: nothing — chmod prints nothing when it works. That is normal.

If it breaks: "No such file or directory" means you are in the wrong folder — run ls and check you are inside the end-to-end folder, then try again.

Then start everything:

Command
docker compose up -d --build

You should see: the build lines for the small Python image, then the services start, one line each. The first start builds the small Python image and downloads the others, so it takes a few minutes. Check all eleven services:

Command
docker compose ps
Expected output
NAME                 STATUS
kafka                Up
postgres-primary     Up
postgres-replica     Up
redis                Up
moto                 Up
lb                   Up
web1                 Up
web2                 Up
web3                 Up
ingest               Up
worker               Up

(The real table has more columns. What matters is all eleven names, each with STATUS "Up".)

If it breaks: if any container shows "Exited", read its log with docker compose logs <name> and look for the error line. The most common cause on the first run is a slow download — wait a minute and run docker compose up -d again.

Step 2 — Watch the three orders flow

The incoming/ folder already holds three fake orders. The ingest program should pick them up within seconds. Watch it:

Command
docker compose logs ingest
Expected output
Connected to Kafka.
Connected to the object store.
Watching /incoming for new order files...
Sent order-001.json: {'id': 101, 'item': 'notebook', 'amount': 250, 'buyer': 'Asha'}
Sent order-002.json: {'id': 102, 'item': 'pen', 'amount': 40, 'buyer': 'Ravi'}
Sent order-003.json: {'id': 103, 'item': 'mug', 'amount': 350, 'buyer': 'Meena'}

Now watch the worker:

Command
docker compose logs worker
Expected output
Connected to PostgreSQL.
Connected to Redis.
Connected to Kafka. Waiting for orders...
Saved order 101: notebook (250)
Saved order 102: pen (40)
Saved order 103: mug (350)

If it breaks: if the worker says "Waiting for PostgreSQL..." for more than two minutes, the database is not up yet — check docker compose ps. If the ingest log shows no "Sent" lines, check the incoming/ folder still holds the files. If the files are gone but nothing was saved, read the worker log from the top — the error line is usually about a connection.

Step 3 — Prove it in four places

Check the database:

Command
docker compose exec postgres-primary psql -U learner -d practice -c "SELECT * FROM orders ORDER BY id;"
Expected output
 id  |   item   | amount | buyer
-----+----------+--------+-------
 101 | notebook |    250 | Asha
 102 | pen      |     40 | Ravi
 103 | mug      |    350 | Meena
(3 rows)

Check the counter:

Command
docker compose exec redis redis-cli GET orders:count
Expected output
"3"

Check the file store — the ingest log is the proof. Ingest only prints "Sent ..." after it has stored the file, so the three "Sent" lines in Step 2 mean all three files are in the object store (bucket incoming). Moto has no web page to open, so the log is the check. The object-store lab shows you how to list files with the aws tool.

Check the load balancer:

Command
for i in 1 2 3 4 5 6; do curl -s http://localhost:8080/ | grep Hostname; done
Expected output
Hostname: web1
Hostname: web2
Hostname: web3
Hostname: web1
Hostname: web2
Hostname: web3

That is the guard sharing the work.

If it breaks: if the database shows fewer than 3 rows, wait 30 seconds and try again — the worker may still be catching up. If the counter shows less than 3, same fix. If the files are missing from the object store, check the ingest log — it prints a line for every file it sends.

Step 4 — Add a fourth order yourself

Make a new order file:

Command
cat > incoming/order-004.json << 'EOF'
{"id": 104, "item": "pen stand", "amount": 120, "buyer": "Kumar"}
EOF

You should see: nothing — the file is written silently. That is normal.

Wait 10 seconds, then check the database again:

Command
docker compose exec postgres-primary psql -U learner -d practice -c "SELECT * FROM orders ORDER BY id;"
Expected output
 id  |   item    | amount | buyer
-----+-----------+--------+-------
 101 | notebook  |    250 | Asha
 102 | pen       |     40 | Ravi
 103 | mug       |    350 | Meena
 104 | pen stand |    120 | Kumar
(4 rows)

And the counter:

Command
docker compose exec redis redis-cli GET orders:count
Expected output
"4"

A new order flows through the whole pipeline by itself — file in, database row out.

If it breaks: if the database still shows 3 rows, wait 30 seconds and try again — the worker may still be catching up. If order 104 is still missing, run ls incoming/ and check order-004.json is there; if the file is gone but no row was saved, read the worker log from the top with docker compose logs worker.

Step 5 — Kill the main database

Stop the main database:

Command
docker compose stop postgres-primary
Expected output
✔ Container postgres-primary  Stopped

If it breaks: "No such container" means the name is wrong — run docker compose ps and use the name it shows.

The worker will crash (it cannot reach the database any more) and Docker will restart it. It will keep printing "Waiting for PostgreSQL..." — that is correct. It is waiting for a database that is gone.

Check the standby still has the data:

Command
docker compose exec postgres-replica psql -U learner -d practice -c "SELECT * FROM orders ORDER BY id;"
Expected output
 id  |   item    | amount | buyer
-----+-----------+--------+-------
 101 | notebook  |    250 | Asha
 102 | pen       |     40 | Ravi
 103 | mug       |    350 | Meena
 104 | pen stand |    120 | Kumar
(4 rows)

The standby has its own copy.

If it breaks: if the standby shows fewer than 4 rows, wait 10 seconds and try again — the copy takes a moment.

Step 6 — Promote the standby

Command
docker compose exec postgres-replica psql -U learner -d practice -c "SELECT pg_promote();"
Expected output
 pg_promote
------------
 t
(1 row)

Check it is no longer a standby:

Command
docker compose exec postgres-replica psql -U learner -d practice -c "SELECT pg_is_in_recovery();"
Expected output
 pg_is_in_recovery
-------------------
 f
(1 row)

It is now the main database.

If it breaks: if pg_promote() shows f, the standby was already promoted — check with SELECT pg_is_in_recovery();. If that shows f, you are done.

Step 7 — Point a worker at the new main database

Stop the old worker (it is still waiting for the dead database):

Command
docker compose stop worker
Expected output
✔ Container worker  Stopped

If it breaks: "No such container" means the worker is already stopped — that is fine, move on.

Start a fresh worker that talks to the new main database. The --no-deps flag matters: without it, Compose would restart the dead main database too.

Command
docker compose run --no-deps --rm -e PG_HOST=postgres-replica worker

This runs in your terminal (not in the background), so you will see its logs live.

You should see:

Command
Connected to PostgreSQL.
Connected to Redis.
Connected to Kafka. Waiting for orders...

Leave that terminal open. It is now the live worker.

If it breaks: if it prints "Waiting for PostgreSQL..." for more than a minute, the new main database is not up — check with docker compose ps that postgres-replica shows "Up".

Step 8 — Send a fifth order through the new main database

In a second terminal, from the same folder, make a new order:

Command
cat > incoming/order-005.json << 'EOF'
{"id": 105, "item": "ruler", "amount": 60, "buyer": "Divya"}
EOF

You should see: nothing — the file is written silently. That is normal.

Wait 10 seconds. In the first terminal (the worker), you should see:

Command
Saved order 105: ruler (60)

If it breaks: if the worker shows nothing after 30 seconds, the temporary worker from Step 7 is not running — go back and start it again.

Check the new main database:

Command
docker compose exec postgres-replica psql -U learner -d practice -c "SELECT * FROM orders ORDER BY id;"
Expected output
 id  |   item    | amount | buyer
-----+-----------+--------+-------
 101 | notebook  |    250 | Asha
 102 | pen       |     40 | Ravi
 103 | mug       |    350 | Meena
 104 | pen stand |    120 | Kumar
 105 | ruler     |     60 | Divya
(5 rows)

The order flowed through the standby that is now the main database. Failover done — end to end.

Stop the temporary worker with Ctrl+C in the first terminal.

Step 9 — The honest part

The old main database is still stopped, and it still has the old data (4 orders, not 5). It cannot rejoin by itself. In real work, you rebuild it from the new main database with pg_basebackup, the same way the standby was first built. For this lab, the simple way back is to wipe everything and start fresh:

Command
docker compose down -v

You should see: all eleven services stop and the data is deleted.

If it breaks: "No such container" means the services are already stopped — nothing to do.

That stops all services and deletes the data. The data was fake.

Clean up

Command
docker compose down -v

You should see: all eleven services stop and the data is deleted.

If it breaks: "No such container" means the services are already stopped — nothing to do.

What you can now say, truthfully

"I built a pipeline where a fake order file flows through an object store, Kafka, PostgreSQL and Redis, behind a load balancer — then I killed the main database, promoted the standby, and a new order still flowed through."

What this lab does NOT cover

  • Real pipelines run each part on its own machines, not all on one machine. The ideas are the same; the setup is bigger.
  • Moto keeps files in memory only. If you stop the lab, the files are gone. The database rows and the Redis counter live in named volumes, so they survive a restart — the files do not.
  • This lab has no automatic failover (no Patroni here). The promotion in Step 6 is by hand. The Patroni part of the PostgreSQL lab shows the automatic version.
  • The load balancer here serves three tiny backends. A real app behind it is a bigger setup — but the guard works the same way.

Fill in the map

Draw the order flow from memory. Each blank is one hop: what travels, and which tool holds it. Write your answers on paper or in a text file, then check them at the end of this section.

Command
A customer places a fake order.

  incoming/order-005.json
  (a small file: id, item, amount, buyer)
            |
            v
  1. ___ holds a copy of the file
            |
            v
  2. ___ carries the order as a message
            |
            v
  3. ___ saves the order as a row
            |
            v
  4. ___ counts the orders (orders:count)
            |
            v
  The order is saved, and the counter says 5.

Meanwhile, on the front door:

  visitor --> 5. ___ --> web1 / web2 / web3

Fill in each blank with the tool name:

  1. ___ — which tool holds the copy of the file?
  2. ___ — which tool carries the order as a message?
  3. ___ — which tool saves the order as a row?
  4. ___ — which tool counts the orders?
  5. ___ — which tool spreads visitors across the three backends?

Answers (no peeking)

  1. Object store (Moto, bucket incoming) — ingest stores a copy of the file there.
  2. Kafka (topic orders) — ingest sends the order there, and the worker reads it from there.
  3. PostgreSQL (table orders) — the worker saves the order as a row there.
  4. Redis (key orders:count) — the worker adds 1 to the counter there each time an order is saved.
  5. Load balancer (NGINX, the lb service) — it spreads visitors across web1, web2 and web3.

Save your proof

The proof for this lab is the 5-row order table and the counter at 5. Save both with these commands, run from inside this folder after Step 8:

Command
mkdir -p ../portfolio/proof
docker compose exec postgres-replica psql -U learner -d practice -c "SELECT * FROM orders ORDER BY id;" > ../portfolio/proof/end-to-end-trace.txt
docker compose exec redis redis-cli GET orders:count >> ../portfolio/proof/end-to-end-trace.txt

Open the file and check it shows 5 rows, including order 105, and the counter "5". Then add the hostnames from the curl loop by hand, using portfolio/proof/end-to-end-trace-TEMPLATE.txt. That file is your proof.

You should see: nothing in the terminal when you run the save commands — the table and the counter went into the file, not the screen.

If it breaks: if the file shows fewer than 5 rows, Step 8 did not finish yet — wait 30 seconds, then run the save commands again.
